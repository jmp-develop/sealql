# hardened 유한 목록 전후 측정

채택: 후보 토큰 조건이 하나도 없는 술어는 scope·keyset·salt proof를 적용하고 row_id로 정렬해 LIMIT을 거는 한 companion 스캔을 사용한다. 기본·혼합 token SQL은 바꾸지 않는다. `9f19c2e` 직전 구현과 최종 변경을 **같은 부모·companion 물리 테이블, 키, salt, 질의, ID 정렬, LIMIT 20, 이름·전화 2칸 투영**으로 비교했다.

일회용 DB에서 disposablePool의 assertDisposable·실제 포트 56439 확인 후 전용 hardened_list_perf 스키마만 생성·삭제했다. 원본 bench_realistic_100k 10만 행은 SELECT로만 읽었고 전후 hash가 같다. 기존 현재 형식 test_p1_verify 파생본에서 같은 model=customers·field·key·scope·row의 암호문·proof를 복사하고 hardened token 칼럼만 생략했다. 각 모델 첫 10행의 두 칸을 인증 복호화해 원본과 대조했다. 1만/10만 companion·부모·평문 테이블은 각각 **실제 물리 행 수**다.

첫 호출을 별도 기록하고 예열 2회·경로 순서를 번갈아 교차 7회로 측정했다. 각 반복의 반환 ID 순서·이름·전화를 평문과 비교했고 별도 count도 평문 기대 count와 비교했다. 총 1,420개 비교가 통과했다. SQL은 Client.query 요청~응답 왕복 합계, 전체는 API 시작~결과 시간, ±MAD는 7회 중앙 절대 편차다. 두 시간 중앙값은 서로 합산하지 않는다. 캐시를 비우지 않았으므로 첫 호출을 콜드 캐시라 부르지 않는다. SQL 횟수·반환 행·실제 Sealer.open 호출, 첫 호출, 7회 원시값, EXPLAIN(ANALYZE,BUFFERS)은 [raw.json](raw.json)에 있다. EXPLAIN은 별도 1회이며 중앙값이 아니다.

## 원인과 잔여 병목

원래 quick는 완전한 ID 앞부분을 판정하고 fallback은 그 마지막 ID 뒤만 판정했다. 같은 행의 전체 재판정이 원인은 아니었다. 후보 토큰 없는 조건도 sample materialization과 proof 배열을 넘기는 ordered fallback을 거쳐 불필요한 중간 처리가 있었다. 최종 경로는 이를 제거한다. 다만 희귀·0건 목록은 정렬용 index로 대부분의 heap 행을 방문한다. 같은 테이블의 count는 row 정렬 없이 sequential/parallel 경로를 사용할 수 있어 여전히 빠르다. 첫 직접 스캔 실험의 계획·원자료도 [별도 보존](../list-plan-direct/raw.json)했다.

예를 들어 최종 phone-eq list20은 10만 companion의 1행을 반환하려고 99,999행을 filter에서 제외한다. 원래 경로의 sample 256 + fallback 99,744행과 같은 총 범위이며, 배열 전달·CTE를 줄였지 전체 proof 작업을 없앤 것은 아니다. 이름·전화 LIKE와 0건도 같은 제약을 가진다. **결과가 적은 목록 조회는 count보다 느릴 수 있으므로 큰 범위에서는 다른 인덱스 조건과 함께 사용한다.**

남은 행을 먼저 판정하고 일치 ID만 정렬하는 대안은 [다른 교차 실험](../list-plan-rejected/raw.json)에서 10만 전화 0건 645.48→216.81 ms, LIKE 1309.58→568.30 ms를 얻었지만 contains-2 목록은 7.63→214.21 ms로 퇴행했다. contains-3·endsWith도 전 범위 판정으로 퇴행했다. 작은 prefix에서 최종 결과가 부족하더라도 이후 행에 충분한 일치가 있을 수 있기 때문이다. 같은 SQL에서 결과 빈도를 알 근거가 없으므로 새 임계값·추측·설정이나 두 경로 자동 선택을 도입하지 않고 기각했다. 두 실험 세션의 before 값 자체가 달라 직접 서로 비교하지 않는다.

## 재현·한계

[list-plan.ts](../../../hardened/list-plan.ts)를 저장소 루트에서 `node --import tsx bench/hardened/list-plan.ts <9f19c2e의 src 사본> <출력 폴더>`로 실행한다. 기본 사본 위치는 프로젝트의 .local/hardened-list-before/src이며 git archive로 src만 별도 폴더에 펼치면 된다. 기존 읽기 전용 fixture·파생본·pg_trgm을 사용하고, 자신의 전용 스키마가 이미 있으면 거부한다. 메모리·OS 캐시와 C 로캘이 결과에 영향을 준다. 한글 평문 LIKE의 pg_trgm 한계를 포함하므로 평문 대비 배율로 제품 속도를 주장하지 않는다. 이 데이터는 합성 fixture이고 여러 workload·운영 분포를 대표하지 않는다.

이번 변경은 판정 SQL의 계획 경로만 바꾸며 키·저장 구조·proof 함수·쓰기·공개 API를 바꾸지 않는다. migration·extraMigrationSql·reindex가 추가로 필요하지 않는다. 원래 토큰 없는 검색의 범위 비례 비용·관찰 누출은 남는다. 로컬 합성 fixture 결과이며 운영 성능 보장·보안 인증이 아니다.
