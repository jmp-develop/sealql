# 검색 보호 후보 실험: 판정 (2026-09-24)

## 판단

**독립 locator와 암호화 posting page는 계속 연구할 가치가 있다.** 합성 고객 10만 행에서 사용자가 우선한 회사명 완전 일치와 메모 중간 문자열 검색은 기본 암호화와 거의 같은 총 지연을 보였고, 검색 방법 자체의 차이도 작았다. 단일 조각 anchor가 빈 결과에 수천 후보를 내는 반례는 실패했으나, 별도 실험의 암호화 목록 교집합이 이를 19.235ms와 인증 개봉 0건으로 줄였다. **두 경로를 결합한 완전한 검색 모드, 관리되는 쓰기, 키 없는 유출 방어는 아직 검증되지 않았다.** 고객에게 완전한 레코드의 대량 복원이 어렵다고 약속하거나 지금 강화 모드로 연결할 근거는 없다.

성능 판정은 두 층으로 한다. A는 검색어 준비, 색인·posting 조회, posting page의 인증 개봉·집합 연산, 후보 고객 암호문 조회까지의 **검색 방법 비용**이다. C는 반환 또는 거짓 후보에 대한 보호 필드 인증 복호화다. A를 우선 비교하되, 전체 호출 D가 같은 실행의 기본 암호화보다 2배를 넘으면 실패로 본다. 색인이 수천 거짓 후보를 내어 C가 커지면 그것도 색인 정확도 문제다. 데이터가 없는 질의나 실행 계획이 우연히 느린 기본 경로만으로 후보를 통과시키지 않는다.

## 실제 비교: 사용자가 우선한 두 질의

동일한 고객 10만 행, UUID 순서 첫 20행, 이름·전화·주소·메모·이메일·회사 **6개 보호 필드**를 반환했다. 두 암호화 경로는 같은 기본 암호문을 같은 `decryptRows`로 인증했고 결과 ID·순서·여섯 값이 일치했다. 준비 1회 뒤 교차 순서 3회 중앙값이며 단위는 **밀리초(ms)**다. A는 중앙 총시간을 낸 바로 그 호출의 구간이다. 아래 **SQL 대기**는 애플리케이션에서 잰 DB 요청~응답의 클라이언트 대기이며, 서버 실행시간만의 값은 아니다. **A는 순수 SQL 대기가 아니라** 검색어·locator 준비, 후보 SQL, 후보 방식의 page 인증과 UUID 집합 처리를 합한 검색 방법 비용이다. **총 D**에는 A 외에 정책 조회, 반환 필드 인증 복호화, 검증과 애플리케이션 시간이 포함된다.

| 질의 | 평문 SQL 대기 | 기본 SQL 대기 | 후보 SQL 대기 | 기본 A / 총 D | 후보 A / 총 D | 후보/기본 총 | 실제 복호화 |
|---|---:|---:|---:|---:|---:|---:|---|
| 회사 `서울서비스 담당` 완전 일치 | 0.864 | 1.046 | 1.299 | 1.565 / 25.425 | 1.928 / 26.890 | 1.058배 | 20행 × 6필드 + 정책 확인 1회 = 121회 |
| 메모 `푸른달` 중간 포함 | 85.572 | 1.595 | 1.497 | 2.259 / 23.699 | 1.929 / 23.547 | 0.994배 | 20행 × 6필드 + 정책 확인 1회 = 121회 |

두 질의 모두 기본과 후보가 검색 중 **실제로 고객 암호문 20행**을 읽었다. 전체 일치 건수는 회사 28,331건, 메모 101건이며, 메모의 반환 20건 전부 앞뒤에 다른 문자가 있는 중간 포함이다. 후보 A의 구성은 회사 준비 0.264 + posting/고객 DB 대기 1.299 + page 인증 0.309 + 집합 처리 0.056, 메모 0.206 + 1.497 + 0.195 + 0.031ms다. 기본 A는 각각 준비/후보 DB 0.519/1.046, 0.664/1.595ms다. 이 차이는 작은 3회 표본의 관찰값이며 보편적 우위가 아니다. 평문 `memo_norm`에는 `pg_trgm` GIN 인덱스가 **존재한다**. 그러나 이 DB의 `C` locale에서 `show_trgm('푸른달')`는 빈 배열이며, 해당 평문 질의의 `EXPLAIN ANALYZE`는 10만 행 순차 스캔·정렬, 서버 실행 82.913ms였다. 반면 기본 암호화의 companion GIN 후보 조회는 별도 계획에서 서버 실행 0.526ms였다. 같은 행·기계의 측정이지만 이 한국어 질의의 **실효 인덱스 조건은 다르다**. 평문 85.572ms를 암호화 방식 자체의 보편적인 우위로 홍보하면 안 된다.

별도 대표 조건에서 후보의 총시간은 흔한 회사 2글자 24.143ms(기본 22.730), 네 필드 OR 28.221ms(기본 77.008), 메모 101건 전체 136.891ms(기본 144.840), 존재하지 않는 조각 0.576ms(기본 1.915)였다. OR 기본 경로에는 알려진 실행 계획 손실이 있으므로 0.366배라는 숫자를 일반적인 색인 우위로 해석하지 않는다. 메모 101건은 101행 × 6필드 = 606개 값과 정책 확인 6회를 인증한 별도 부하 사례다. 이 네 조건의 상세 단계는 [v2 연구 보고서](posting-pages-v2-research-ko.md)와 [원시 JSON](posting-pages-v2-query.json)에 있다.

## 빈 결과 반례와 적응형 탐색

`company CONTAINS 지사담`은 `지사` 5,883건과 `사담` 9,472건이 각각 존재하나 둘을 모두 포함하는 행은 0건이다. v2 **단일 anchor**는 5,883개 고객 행의 여섯 필드를 인증한 뒤 모두 버려 6,185.773ms였다. 같은 실행의 기본은 142.089ms였다. 43.534배이며 절대 지연도 부적합하다. 초기 전체 page 읽기 v1도 흔한 2글자와 OR에서 각각 2.170배, 7.927배로 실패했다. 따라서 무조건 anchor 또는 무조건 전체 목록 읽기 중 하나를 고정하는 설계는 채택할 수 없다.

별도 읽기 전용 [적응형 교집합 실험](posting-pages-v2-adaptive-probe.json)은 같은 `지사담`의 두 암호화 manifest와 **120개 page, 602,431B**를 SQL 2회로 일괄 읽고 UUID 목록을 교차했다. 후보 0건, 보호 필드 개봉 0회가 평문 기준과 일치했다. 준비 1회 + 교차 3회 중앙 총시간은 **19.235ms**, 같은 실행의 기본 45.309ms(0.425배)였다. 이 기본 SQL도 `ORDER BY/LIMIT`와 projection에 따라 크게 흔들렸다. 별도의 무제한 ID 조회가 약 2.2ms였으므로 19ms를 본질적인 암호화 검색 우위라고 주장하지 않는다. 검색 방법 비용과 602KB 전송은 실측이다. **적응형 선택 로직은 주 v2 검색 경로에 아직 합쳐져 있지 않다.**

실용적인 다음 선택은 한 조각짜리 흔한 질의와 첫 page에서 원하는 결과를 얻는 질의에 UUID 순서 page 스트리밍을 쓰고, 여러 조각의 후보가 드물게 교차하는 경우 일괄 암호화 목록 교집합을 쓰는 것이다. 그 선택 기준과 실패 상한은 미정이다. 짧은 표본 후보를 인증해 교집합 전환을 결정하는 방법은 가능한 설계안이지만 아직 측정하지 않았다. 양쪽 목록이 모두 매우 큰 경우에는 전송량을 제한하거나 더 긴 조각 색인이 필요할 수 있고, 긴 조각을 모두 색인하면 저장·쓰기 비용이 늘어난다. 임의의 2글자 이상 문자열에 대해 보편적인 2배 보장은 입증하지 못했다.

## 유출 저항성과 운영 비용

기본 방식은 같은 scope의 같은 조각에 16비트 fingerprint를 붙여 행별 token 배열에 저장한다. 이전 N4 경량 강화도 행별 token 배열을 유지하면서 조각마다 네 가지 keyed bucket 중 하나를 행별로 선택했고, token을 64비트로 늘렸다. 따라서 분할로 동일 조각의 연결이 줄어드는 동시에 16비트 충돌에 따른 흐림도 사라져, N4가 기본보다 얼마나 안전한지 분리해 입증하지 못했다. **v2는 token 폭을 다시 조절한 방식이 아니다.** 연구용 테이블은 각 `(scope, field, 2글자 조각, page 번호)`마다 **서로 다른 256비트 HMAC locator**를 만들고 page 수·건수를 암호화 manifest에 둔다. page에는 정렬된 UUID만 AES-GCM으로 넣고, 공개 테이블에는 locator와 blob만 둔다. 삽입 순서를 섞었다. 이 논리 구조에서 키가 없는 단일 정적 스냅샷은 기본/N4의 공개 행별 검색 토큰처럼 `행 ↔ 조각` 관계를 직접 읽을 수 없다. 이는 N4와 질적으로 다른 누출 구조라는 설계 판단이지 복원 저항성의 실증 결과는 아니다. 서버가 받은 질의와 접근 기록, WAL, 서로 다른 시점의 snapshot, blob 길이·총 page 수, 고객 테이블의 공개 열과 암호문 길이는 별도의 누출이다. page를 제자리 갱신하면 WAL/다중 스냅샷이 변경된 page 묶음을 새 고객 행에 연결할 수 있다. 동적 검색의 업데이트 누출과 검색 패턴은 [Bost의 forward privacy 연구](https://eprint.iacr.org/2016/728) 및 [대규모 encrypted multimap 연구](https://www.ndss-symposium.org/ndss2014/ndss-2014-programme/dynamic-searchable-encryption-very-large-databases-data-structures-and-implementation/)가 다루는 범위지만, 그 논문의 보안 결과가 이 프로토타입에 자동 적용되지는 않는다.

**실험 DB 자체는 기밀성 증거가 아니다.** 키가 소스의 공개 합성 seed로부터 나오며, 비교 대상 고객 테이블에 평문과 기본 검색 토큰도 함께 남아 있다. 실제 키를 숨긴 ciphertext-only DB 스냅샷을 외부 자료와 대조해 완전 레코드 복원률을 잰 적은 없다. 기존 필드 암호문은 정확한 원문 길이에 33B를 더한 길이를 드러낸다. 짧은 전화·회사·주소의 길이와 공개 열은 색인과 무관하게 재식별 단서가 되므로 길이 구간 패딩은 별도 검토 대상이다.

v2 구축은 미리 저장된 **평문 정규화 열** 10만 행 × 네 필드에서 11.571초, 조각 등장 5,472,494개, page 44,451개 + manifest 3,301개, 테이블·색인 합계 **259,022,848B**였다. 6필드를 인증 조회했지만 posting 색인은 네 필드만 만들었다. 이 시간은 기존 암호문 복호화, 관리 쓰기, 동시성, 재구축·키 회전을 포함하지 않는다. 레코드 ID가 실제 UUIDv4라면 정렬 page의 임의 위치 삽입·분할이 필요하고, 합성 fixture의 순차 UUID보다 불리하다. 별도 검토에서 제안된 불변 page + 소규모 상태 저장 delta + 주기적 재구축은 [동적 SSE 연구](https://eprint.iacr.org/2013/832)와 방향이 맞지만 **미구현 추정**이다. 기존 stateful PRF·probe 방식 그대로면 delta 1천 행도 흔한 조각에서 검색에 약 11~14ms가 더해질 것으로 추정되고, 1만 행은 약 75ms로 2배 기준을 넘는다. 11.571초를 운영 재구축 시간이라고 쓸 수 없으며, 보호 필드 복호화와 atomic generation swap, 삭제·갱신 정합성, 다중 스냅샷 누출을 검증해야 한다.

## C/네이티브 최적화 판단

사용자 우선 두 질의의 기본·후보 A는 약 1.6~2.3ms이며 page 인증은 약 0.2~0.3ms다. 이 **검색 단계**를 C로 다시 작성해도 절감 상한이 작다. 20행 × 6필드의 일반 필드 인증은 약 14~18ms로 총시간의 큰 부분이므로 별도 최적화 여지는 있다. 별도 검토에서 Node 24로 실시한 짧은 **메모리 내** 비교는 120개 HKDF+AES-GCM에 WebCrypto 순차 약 15.2ms, 동시 4개 약 8.5ms, `node:crypto` 동기 HKDF 약 2.5ms + AES-GCM 약 3.6ms를 보였다. 현재 제품 호출의 나머지 프레이밍·복사·코덱 처리와 결합한 개선폭은 측정되지 않았다. Node의 [WebCrypto](https://nodejs.org/api/webcrypto.html) 및 [crypto](https://nodejs.org/api/crypto.html)는 이미 네이티브 암호 함수를 제공한다. C/N-API는 Node 전용 배포 부담이 있고, Cloudflare 환경에는 그대로 들어가지 않는다. WebAssembly는 이식 경로지만 암호 구현 검증 부담이 있다([Node-API](https://nodejs.org/api/n-api.html), [Cloudflare WebAssembly](https://developers.cloudflare.com/workers/runtime-apis/webassembly/)). 이 단계에서 C 이식을 검색 색인의 선행 조건으로 삼지 않는다. CPU profile과 동일 데이터의 호출 비교를 먼저 하고, field-open 비용이 실제 병목으로 남을 때만 검토한다.

역사적 stateful의 한 건씩 HMAC 태그 열거는 별개다. 28,331개 태그 준비가 약 614ms였으며 배치 PRF는 줄일 **가능성**이 있다. 그러나 그 방식의 후보 SQL이 다른 사례에서 577~840ms였고 4~5회 의존 probe도 남는다. 메모리 내 AES-CTR 대량 생성 속도를 기존 stateful 검색의 완성된 지연 감소로 바꿔 말할 수 없다.

## 다음 결정 기준

1. 연구 코드의 스트리밍과 일괄 교집합을 하나의 **상한 있는** 검색 경로로 결합하고, 우선 두 질의·빈 결과·OR·101건을 같은 실행에서 다시 비교한다. 검색 A, 실제 인증 행·필드, 총 D, page/전송량을 모두 기록한다.
2. 쓰기·갱신·삭제·동시성·무작위 UUID·generation 교체를 구현한 작은 관리형 수직 경로에서 후보 누락 0과 작업 지연을 확인한다. 10만 행 구축을 운영 쓰기 성능으로 오해하지 않는다.
3. 실제 키를 분리하고 평문/기본 토큰이 없는 스냅샷에서 길이·공개 열·보조 자료·물리 page 순서·여러 시점의 누출을 따로 평가한다. 그 전에는 완전 레코드 대량 복원 방지라는 고객 문구를 사용하지 않는다.

현재 판정은 **연구 계속**, **제품 강화 모드 채택 보류**다. 이 결론은 기초 검색 성능이 나빠서가 아니라, 읽기 전략 결합·운영 쓰기·실제 위협 모델의 증거가 빠져 있기 때문이다. 사용자가 허용한 성능 범위 안에 있는 핵심 검색 결과는 보존할 가치가 있다.
