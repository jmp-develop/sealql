# C 재검토: 개선 가능한 비용과 구조적 비용

새 실측은 하지 않았다. 아래 시간은 [과거 통합 count](../../2026-09-28-unified/m2-fable-measure.json)·[목록](../../2026-09-28-unified/m2-fable-lists.json)의 C-port 중앙값 재계산이다. 실제 MongoDB나 현재 제품의 성능이 아니다. 과거 코드의 첫 3회 제외·후속 7회 교차 중앙값이며, 현재 규칙의 예열 2회와 동일한 실행 계약으로 다시 잰 값은 아니다.

## 설계 판단

| 제안 | 줄일 수 있는 비용 | 남는 비용·보안 조건 | 다음 실험에서 분리할 지표 |
|---|---|---|---|
| 검색 표 단독 count | 긴 검색어의 앱 왕복·불필요한 필드 복호화는 개선 여지 | 보통 C count는 이미 단독 검색 표. 부모 JOIN 제거를 새 개선으로 중복 계산할 수 없음. 10글자 초과·LIKE를 정확 판정할 추가 구조는 별도 설계 | 일반 count와 앱 검증 경로 각각 SQL/전체·복호화 필드 수 |
| 선택도 낮은 후보 먼저 | AND 4/6에서 큰 집합의 중간 행·정렬·교집합 비용 | 현재 형식에는 후보 행에서 다른 평문 조각을 직접 판정할 도구가 없음. 모든 등장 태그를 생성하는 비용이 자동으로 사라지지 않음 | 생성 태그 수, 태그 생성 시간, index 탐색 수, 교집합 입력·출력 |
| SQL 태그 생성·집합 결합 개선 | 배열 materialization, ANY 추정 오류, repeated index probe, sort/hash spill | C는 이미 서버 digest와 (tag,id) covering B-tree 사용. UNNEST JOIN·temporary materialization·계획별 cardinality 비교는 가능하지만 이득은 미측정 | EXPLAIN 실제/추정 행, buffers, temp I/O, 메모리 |
| ID 순서 조기 LIMIT | 반환행에 대한 본문 읽기·복호화 | 무작위 등장 태그 순서와 ID 순서는 다름. n개 태그를 생성·탐색한 뒤 정렬하는 구조는 LIMIT 20으로 n이 20이 되지 않음 | 첫 반환까지 시간, 태그 생성 수, 정렬 입력행 |
| 독립 분기 병렬 처리 | 여러 AND/OR 분기 또는 contention bucket의 지연 중첩 | CPU/I/O 총량은 감소하지 않음. 서버 플래너가 함수·서브계획을 실제 병렬화하는지 확인 필요. 쓰기 병렬은 카운터 충돌·트랜잭션을 따로 검증 | 단일 질의 latency와 처리량, worker 수, wait, 재시도 |
| compact·저장 포맷 조정 | 장부·문서 overhead, 가짜 조각 저장 표현 | SQL 튜닝만으로 90배 용량은 감소하지 않음. 암호화 장부와 패딩은 보호 목적이 있어 평문 counter/전역 deterministic 후보를 추가하면 누출이 바뀜 | 테이블/색인/TOAST/WAL 분리 용량, 업데이트·삭제 후 누적 |

안전한 최적화 후보는 **이미 허용한 조회의 토큰 열거와 집합 연산을 효율화**하는 것이다. 현재 제품의 결정적 16비트 후보를 C에 다시 붙이면 이번에 재검토하는 A/B/C 연결 누출도 다시 도입한다. 이 변경은 단순 속도 개선으로 취급할 수 없다. 더 적은 n-gram만 저장하는 변경도 후보 오탐·긴 검색어의 정확 판정·새 관찰 누출을 함께 시험해야 한다.

## 용량 산술 검산

[원본 용량](../../2026-09-28-unified/m2-fable-sizes.json)에서 고객 10만·티켓 10만의 관련 표와 색인만 합산했다. 고객은 6필드, 티켓은 메모 1필드다. 평문 **94,543,872B**, C-port **8,503,689,216B**, 비율 **89.94배**. 고객 태그 499.4개/행, 티켓 태그 84.1개/행, 서로 다른 장부 키 13,998,743개다. 쓰기 임시 표·D/B 표는 제외했다. 원본 조회가 pg_relation_size 중심이므로 별도 TOAST·WAL까지 포괄하는 완전한 디스크 비용으로 부르지 않는다.

과거 C-port는 본문 AES-GCM에 AAD 행 결속이 없고, SHA256(key∥label) 연구 대체식·64비트 태그·평문 카운터이며 MongoDB SDK 구현이 아니다. 현재 수준의 관리형 쓰기·행 결속·장부 암호화·복구·동시성을 추가한 비용은 측정되지 않았다. 따라서 과거 C를 최적화하면 현재 제품의 약 2배 이내에 들어온다는 결론은 아직 낼 수 없다.
