# count 연구 결론: DB 완결 판정과 오차 지점만 검증

2026-09-28. 기준 제품 커밋 `fc561ac`(R8 제한 해제 후). 일회용 PostgreSQL `127.0.0.1:56439`, 원본 `bench_realistic_100k` 10만 행과 그 파생. 연구용 스키마(`research_count_*`)는 측정 뒤 모두 삭제했다. 제품 코드는 바꾸지 않았다. **로컬 합성 fixture 결과이며 운영 보장·보안 인증이 아니다.** 스크립트는 `bench/research-count/`, 원자료는 이 폴더의 `r2-*`, `x1-*`~`x5-*` JSON이다.

## 1. 질문과 답

| 질문 | 답 | 근거 |
|---|---|---|
| DB가 필터를 끝내고 신뢰할 수 있는 정확한 count를 줄 수 있나 (추가 누출 없이, 상태 없이, 신뢰 하드웨어 없이, 임의 길이 부분 문자열) | **불가**(문헌·제품 전수에서 사례 없음, 추정) | 정확한 부분 문자열 SSE(Chase–Shen PoPETs'15, Faber 외 ESORICS'15)는 질의 때 일치 위치를 드러낸다. 그 누출로 10% 사전 지식이 부분 문자열 74.42%를 복원한 공격이 있다(arXiv 2511.00930). 정확 count를 주는 제품은 전체 폭 결정적 토큰(값 동치류 공개) 또는 서버 안 복호화(TEE)를 쓴다 |
| 부분적으로라도 DB가 끝낼 수 있나 | **정확 일치·짧은 필드는 가능하나 대가가 있다** | 행마다 무작위 전체 폭 판정 태그(Goh "Secure Indexes" 계열). 정적 누출은 늘지 않지만(추정) 질의한 값의 정확한 빈도가 드러나고, **라이브러리가 재확인하지 않으므로 적대적 DB가 count를 부풀려도 알 수 없다**(무결성 후퇴) |
| 오차 날 곳만 검사할 수 있나 | **토큰만으로 참을 증명할 방법은 없다** | 16비트 조각 하나에 같은 토큰을 쓰는 한글 2글자 조각이 약 1,900개. 실제 문장(NSMC)에서 2글자 검색도 질의 100%에 충돌 오탐이 있었다(×1.01–1.04), endsWith 3글자는 ×1.4–4.0 |
| 그럼 비용은 어디서 오나 | **참인 후보가 참임을 증명하는 인증 복호화 호출** | 기준 질의 1–4는 후보 수 = 일치 수(오탐 0)인데도 느리다. 필드마다 WebCrypto를 한 번씩 부르는 비용이 지배한다(GCM 원시 호출 약 19 µs/필드, Node) |

## 2. 측정 결과 (10만 행, count, ms, 예열 2·교차 7 중앙값, 매 실행 평문과 일치)

조건 전문: ① 회사명 = "서울서비스 담당" AND 메모 포함 "서비스"(21,176) ② 회사명 = "서울서비스 담당" OR 메모 포함 "푸른달"(28,400).

| 방식 | 저장 형식 | 누출 변화 | ① 합계 | ② 합계 | 평문 대비(①/②) | 출처 |
|---|---|---|---:|---:|---:|---|
| 평문 COUNT | — | — | 91.7 | 80.3 | 1× | x4 |
| 현재 제품(AES-GCM, 필드별) | 현재 | 기준 | 1,595 | 2,011 | 17× / 25× | x4 |
| X1: 형식 유지 개선(필요한 칸만·단락 평가, 호출 부가비용 축소, 빠른 재확인, 스트리밍) | 현재 | 없음 | 1,101 | 809 | 12× / 10× | x1 |
| X2: AES-CBC + HMAC-SHA-256(암호화 후 인증) | **교체** | 없음(길이 16 B 단위로 감소) | 525 | 546 | 5.7× / 6.8× | x2 |
| **X4: CBC+HMAC + X1 기법 결합** | **교체** | 없음 | **222** | **230** | **2.4× / 2.9×** | x4 |
| R1-A 서버 판정 태그(정확 일치 잎만) | 추가 | 질의 시점: 정확 빈도, 영구 판정 오라클. 무결성 후퇴 | ①은 불가 | — | — | x2 |

- 현재 형식의 실측 하한: ① 약 800 ms(최소 복호화 42,352회 × 원시 호출). 형식을 두고는 이보다 싸질 수 없다(x1).
- 결합안의 남은 시간(① 배치 318 ms): DB 전송 153(48%), MAC 82(26%), 기타 변환·재확인·디코드. **암호 비용을 0으로 만들어도 DB 전송만으로 평문의 1.56배**(x4). 평문 대비 약 2배 목표는 후보 행 전송이 벽이다.
- findMany: 200건 ① 46.3 → 6.9 ms, 전부 ① 4,204 → 603 ms(결합안, x4).
- Cloudflare Workers(로컬 workerd): 현재 GCM 8.2 µs/필드(Node의 절반 이하), 결합안 2.5 µs/필드 → 이득 약 3.2배(Node 약 8배). 실제 배포는 재지 않았다(x4).
- 쓰기: 암호화만 GCM 160 → 120 µs/행, 암호문 행당 +165 B(+54%). 관리형 쓰기는 토큰 계산(약 4.2 ms/행)이 지배(x2, x4).

## 3. 다중 테넌트에서 DB가 느려지는 원인 (x5, 보편 전제에 해당)

- 1억 속 회사 B의 저일치 다조건 질의(예: 회사명 = "서울서비스 담당" AND 주소 포함 "서울" AND 메모 포함 "상담" AND 이메일 포함 "service")의 DB 구간이 10만 단독보다 약 30배 느렸다(167 대 5.3 ms, EXPLAIN 서버 시간).
- **원인(확인):** PostgreSQL이 보조 테이블의 `scope_id = $`와 scope 접두가 들어 있는 토큰 조건을 독립으로 보고 선택도를 곱해 행 수를 약 690배 과소 추정한다 → GIN 대신 정확 토큰 B-tree로 28,331행을 읽고 버린다(21,591페이지). 같은 계획을 10만 단독에 강제하면 똑같이 느리다. 테넌트가 많을수록 오차가 커진다.
- **해결 후보(측정, 보안 변화 없음):** 보조 테이블 서브쿼리에서 `scope_id` 조건을 뺀다(토큰이 이미 scope별이고, 부모 `scope_id = $`와 AAD 결속은 유지). 167 → 5.5, 181 → 9.6, findMany 200 168 → 5.4 ms, 다른 질의 회귀 없음. 정확 일치만 있는 질의를 위해 B-tree 칸 순서 조정 검토 필요(측정 안 함).

## 4b. 후보 전송 구간 (x6)

DB 구간의 벽은 전송량이 아니라 **후보마다 부모 행을 PK로 찾는 비용**이었다. 전송량을 1–8 MB로 바꿔도 DB 시간 차이는 약 10 ms 이내였다(실측). ① 기준 count, ms, 같은 실행 안 비교(평문 COUNT 84–96 ms 변동, 합계 ±5–10%).

| 방식 | 저장 | DB ①/② | 합계 ①/② | 평문 대비 ①/② |
|---|---|---:|---:|---:|
| 결합안 배치(base64) | 그대로 | 133 / 114 | 295 / 250 | 3.29× / 2.65× |
| hex·바이너리 형식·행당 bytea 1개로 묶기 | 그대로 | 139–150 / 108–133 | 298–324 / 234–288 | 이득 없음 |
| 보조 서브쿼리 scope 조건 제거(3절) | 그대로 | 116–119 / 118 | 262–270 / 227–234 | 2.73–3.01× / 2.49–2.70× |
| 서버 커서로 1,024행씩 받으며 검증과 겹침 | 그대로 | (겹침) | 211–218 / 200–201 | **2.20–2.43× / 2.13–2.39×** |
| 보조 행에 조건 칸 암호문 사본 + 커서 | **사본 추가** | 67–82 / 134–171 | 198–204 / 174–183 | **2.07–2.27× / 1.95–2.10×** |

- 사본은 같은 암호문 바이트·같은 결속이라 누출·인증은 같다. 대신 부모만 바뀌고 사본이 안 바뀌면 옛 사본도 인증을 통과해 count가 틀어질 수 있으므로 관리형 쓰기가 같은 트랜잭션에서 둘 다 써야 한다(쓰기 비용·다중 테넌트 미측정).
- node-pg 8.23의 바이너리 결과 형식은 bytea·uuid를 깨뜨려(50/50) 쓸 수 없다.
- 이제 남은 벽은 JS 단일 스레드의 암호 연산(MAC 약 80 ms + 기타 약 40 ms)이다. Node에서 MAC을 워커 스레드로 겹치면 약 1.4–1.5배로 추정(미측정). Workers 요청은 단일 스레드라 해당하지 않는다.

## 5. 결론

1. **보안(누출·무결성)을 그대로 두고 도달할 수 있는 최선**은 암호 형식을 표준 부품 조합(AES-256-CBC + HMAC-SHA-256, 암호화 후 인증, 행·필드·scope 결속 유지)으로 바꾸고 형식 무관 개선·서버 커서 겹침을 더한 것: 큰 count 평문 대비 약 **2.1–2.4배**(현재 17–25배), 보조 행에 암호문 사본을 두면 약 **1.95–2.3배**(4b절). 남은 벽은 JS 단일 스레드의 암호 연산이며, 라이브러리가 후보를 받아 증명하는 구조를 유지하는 한 이 이상 크게 줄지 않는다.
2. 형식을 바꾸지 않으면 약 800 ms(① 기준)가 하한이다.
3. 그보다 빠른 길은 DB가 스스로 판정하는 것뿐이고, 질의 시점 누출 증가와 **적대적 DB의 count 부풀리기 탐지 불가**가 따른다.
4. 다중 테넌트 계획 오류(3절)는 보안과 무관한 별도 개선 후보다.

## 6. 사용자 판단이 필요한 것

| 항목 | 내용 | 되돌리기 |
|---|---|---|
| 암호 형식 교체(CBC+HMAC) | 전체 재암호화 필요, 외부 암호 검토 권장, 암호문 +54% | 어려움 |
| 형식 무관 개선의 "필요한 칸만 인증" | 판정에 쓰지 않은 칸의 변조를 그 count 호출에서 발견하지 못함(반환 숫자는 정확) | 쉬움 |
| 서버 판정 태그 | 질의한 값의 정확 빈도 공개, 영구 판정 오라클, count 부풀리기 탐지 불가 | 중간 |
| 보조 서브쿼리 scope 조건 제거 | 보안 변화 없음, 성능 개선 | 쉬움 |
| 보조 행에 조건 칸 암호문 사본 | 누출·인증 같음, 저장 중복, 부모·사본 동시 쓰기 필수(어긋나면 count 오류) | 쉬움 |
| 서버 커서 스트리밍 | 드라이버별 경로 필요(drizzle은 행 스트림 미노출) | 쉬움 |

## 한계

- 합성 fixture는 오탐을 과소 대표한다(후보 = 일치가 많음). 실제 문장 결과는 메모리 시뮬레이션(NSMC)만 있다.
- 결합안의 스트리밍 경로는 pg 드라이버 전용 시제품이다. 스트리밍 없이 배치로 ① 318, ② 230 ms.
- 순수 JS HMAC의 상수 시간은 JIT가 보증하지 않는다(코드에 비밀 의존 분기·표 없음, 시간 차 관측 없음).
- 측정 동안 1억 보조 테이블 autovacuum이 돌고 있었다(모든 경로 같은 조건).
