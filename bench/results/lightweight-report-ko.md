# 키 기반 버킷 검색 실험 (프로토타입)

## 범위와 재현

- 기존 합성 `bench_realistic_100k.customers` 100,000행을 읽고, 별도 `bench_lightweight_100k.bucket_n1`, `bucket_n4`, `bucket_n8`에 각각 100,000행을 만들었다. 원본 테이블과 기존 벤치마크 결과는 수정하지 않았다. 연결은 `127.0.0.1:56439`이고 쓰기 전 `assertDisposable`과 포트를 확인한다.
- 실행: `npx tsx bench/lightweight-setup.ts` 다음 `npx tsx bench/lightweight-query.ts`. 고정 시드, 배치 200행, 원시 결과와 체크포인트는 [적재 JSON](lightweight-setup.json) 및 [검색 JSON](lightweight-query.json)에 있다. 적재는 제품 CRUD 처리량이 아니라 실험용 색인 구축이다. 1,000행 파일럿 뒤 나머지 99,000행 적재에 122.66초가 걸렸다.
- `memo`, `company` 두 정규화 필드만 실험했다. 각 행/필드/2글자 조각에 대해 비밀키가 있다고 가정한 HMAC으로 버킷 하나를 정하고, 별도 HMAC의 64비트 토큰 하나만 저장한다. 질의는 조각마다 N개 버킷 토큰을 모두 만들고, 조각 간 AND로 후보를 찾은 뒤 원문 정규화 문자열 포함 여부를 확인한다. N=1도 **이 실험의 64비트 대조군**이다. 제품의 40비트 스코프 접두부와 16비트 지문 토큰 형식 또는 공개 `findMany` 경로가 아니다.
- 정규화는 NFC, 전각 숫자 변환, 정의된 공백 제거, ASCII 소문자화이다. 쿼리 오라클에도 이미 적재된 `memo_norm`/`company_norm`을 사용했다. 정규화 후 2글자 이상의 임의 부분문자열은 모든 인접 2글자 조각을 포함하므로 버킷 할당과 무관하게 진짜 결과가 후보에 들어간다. 최종 포함 검사가 조각 순서와 경계에서 생기는 거짓 양성을 제거한다. 단, 여기서 실제로 실행한 질의는 아래 두 개뿐이며 여섯 필드 제품 적용을 검증한 결과는 아니다.

## 정확성과 같은 호출의 시간

페이지는 `ORDER BY id`, 20행, 동일한 여섯 원문 필드이다. 후보 SQL은 한 번에 최대 100행을 읽고 검증한다. 각 N에서 예열 1회 후 N 순서를 바꾸며 3회 실행했다. 표의 네 단계는 **중앙 총시간을 기록한 바로 그 호출**의 상호 배타적 구간이다. 토큰 캐시는 각 호출 직전에 비워 HMAC 생성 비용을 포함했다. `SQL`은 클라이언트 대기이고, `검증`은 **평문 문자열 확인**이며 복호화/인증이 아니다. 모든 수치 ms.

| 질의 / N | 실제 결과 = 전체 후보 | 질의 토큰 | 총 3회 (최소 / 중앙 / 최대) | 중앙 호출: 토큰 / SQL / 검증 / 기타 |
|---|---:|---:|---:|---:|
| 메모 `푸른달` / 1 | 101 = 101 | 2 | 1.347 / 1.391 / 1.407 | 0.106 / 1.268 / 0.008 / 0.009 |
| 메모 `푸른달` / 4 | 101 = 101 | 8 | 1.553 / 1.562 / 1.846 | 0.263 / 1.277 / 0.008 / 0.013 |
| 메모 `푸른달` / 8 | 101 = 101 | 16 | 1.802 / 2.094 / 2.198 | 0.422 / 1.642 / 0.008 / 0.022 |
| 회사 `서비` / 1 | 30,101 = 30,101 | 1 | 0.889 / 1.076 / 1.182 | 0.057 / 1.004 / 0.008 / 0.007 |
| 회사 `서비` / 4 | 30,101 = 30,101 | 4 | 0.999 / 1.134 / 1.558 | 0.108 / 1.006 / 0.011 / 0.010 |
| 회사 `서비` / 8 | 30,101 = 30,101 | 8 | 1.063 / 1.125 / 1.145 | 0.175 / 0.935 / 0.008 / 0.007 |

여섯 경로 모두 전체 후보에서 누락/거짓 양성 0건이고, 최종 첫 20개 ID 및 여섯 값이 평문 오라클과 같다. 표의 `전체 후보`는 20행 페이지에 앞서 별도로 확인했으며, 시간 측정 호출은 실제 후보 100행을 읽어 첫 20행을 반환했다. 이 두 선택된 검색어에서 후보/실제 결과 비는 모두 1이다. 다른 검색어의 거짓 양성률을 뜻하지 않는다.

같은 10만 고객 데이터와 `푸른달` 조건의 [기존 공개 API 반복 측정](realistic-100000-companion-repeat-report-ko.md)은 표준 암호화 경로 20행·여섯 필드에서 중앙값 28.201ms(7회), 결과 101건을 기록했다. 해당 측정에는 제품 토큰 형식, 정책/DB 호출, 암호문 개봉이 들어간다. **다른 실행 시점과 다른 토큰 폭·검증 경로**이므로 위 프로토타입 1–2ms와 속도 비율을 계산하거나 표준보다 빠르다고 주장하지 않는다. 회사 `서비`의 동일 공개 API 20행 기준 비교는 수행하지 않았다.

## 색인, 실행 계획과 비용

각 버킷 테이블은 `(scope_id,id)` 기본키와 `memo_tokens`, `company_tokens` 각각의 GIN 색인을 갖는다. 메모 질의의 실제 100행 후보 페이지 계획은 GIN Bitmap Index/Heap Scan, 원본 고객 행 PK 조인, 정렬이다. N=1/4/8 서버 `EXPLAIN ANALYZE BUFFERS` 실행 시간은 각각 0.349/0.397/0.565ms, 공유 버퍼 hit는 510/522/554, read는 모두 0이다. 회사 질의는 GIN 대신 기본키 순서 Merge Join을 택했다. 첫 100개를 얻기 위해 고객 331행을 읽고 버킷 조건에서 231행을 제거했으며, 서버 시간은 0.245/0.275/0.285ms다. 이 서버 시간은 표의 클라이언트 SQL 대기에서 빼지 않았다.

N=1/4/8의 테이블 크기는 39.27/41.64/41.23 MB, 두 GIN 색인 합계는 5.85/8.21/7.81 MB이다. 색인 생성 시간 합계는 약 311/367/413ms이며 적재 뒤 별도로 측정했다. 세 테이블은 모든 행에 거의 같은 개수의 조각 토큰을 저장한다. N을 늘려도 **질의 토큰 수는 과거 출현 횟수와 무관하게 `N × 고유 조각 수`로 고정**되지만, SQL이 읽는 행과 버퍼 수, 정렬/조인 일은 결과 분포와 계획에 따라 달라진다. 이 두 사례에서 시간 개선은 보이지 않았고 드문 검색은 N 증가에 따라 느려졌다.

같은 회사명 `서울서비스중앙지사`를 가진 20행의 190쌍 중 토큰 하나라도 공유하는 쌍은 N=1에서 190, N=4에서 166, N=8에서 108이다. 흔한 조각 `서비`의 버킷별 행 수는 N=4에서 7,467/7,602/7,556/7,476, N=8에서 3,745/3,842/3,752/3,857/3,722/3,760/3,804/3,619이다. 이는 **일부 토큰 등가집합 분산**의 관측치일 뿐 보안 배수나 전체 문자열 연결 차단을 뜻하지 않는다. 긴 문자열은 여러 조각을 공유하여 두 행의 어느 한 토큰이 같을 확률이 다시 커진다.

## 해석과 제품 적용 조건

실험 시드는 재현을 위해 파일에 공개되어 있으므로 **이 파일 자체에는 비밀성이 없다**. 별도 비밀키를 쓰더라도 DB 스냅샷 공격자는 버킷 토큰의 동등성/빈도/공동 출현을 본다. 같은 값을 선택해 여러 행을 삽입할 수 있으면 버킷 변형을 수집할 수 있고, 질의 로그를 보면 모든 N개 변형이 노출된다. 행 ID 재사용, 스코프·필드별 도메인, 키 회전 시 재색인, 부분 수정의 원자성도 제품 프로토콜에서 따로 해결해야 한다.

본 프로토타입은 **암호문 개봉, 인증, 제품 정책/상태 조회, 키 공급자 비용을 포함하지 않는다**. 기존 표준 구현의 16비트 지문·충돌률·전송량과 달라 공개 API의 속도 또는 보안 우위를 주장할 수 없다. 저장 토큰과 질의 토큰 형식이 맞는 N=1/4/8끼리만 직접 비교해야 한다. 제품 채택 전에 실제 암호문으로 후보를 인증 검증하고, 선택/흔한 질의 및 갱신·회전·동시성에서 같은 공개 API 결과와 실패 정책을 다시 검증해야 한다.
