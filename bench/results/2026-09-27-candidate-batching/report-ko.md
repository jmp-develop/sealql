# 오탐이 많은 페이지의 후보 배치 확대

2026-09-27. 소유를 확인한 일회용 PostgreSQL `127.0.0.1:56439` (`.local/pg-test`)의 기존 `bench_standard_next_100k`와 원본 `bench_realistic_100k`를 읽기만 했다. 새 데이터 적재, fixture 수정, 마이그레이션은 하지 않았다. 평문·기본·건너뜀은 같은 ID, 질의, 6필드 투영을 사용했다. 각 경로를 2회 예열하고 순서를 교차해 7회 측정한 중앙값이다. 스윕 9개와 matrix 21개 모두 초기 실행과 측정 7회에서 반환 ID 순서와 각 필드 값이 평문과 일치함을 단언했다.

표의 `전→후`는 변경 전후의 **기본 구성**이다. SQL ms는 페이지 호출의 SQL 요청~응답 합계, 전체 ms는 API 호출 전체 시간이다. 후보는 DB에서 받은 행, 인증 필드는 `Sealer.open` 호출 수다. 각 지표의 중앙값은 독립적으로 계산해 서로 합산되지 않을 수 있다. 평문과 건너뜀의 모든 실행별 수치는 `before/`와 `after/`의 JSON에 있다.

`대로6고`는 인증 결과 10행을 얻기까지 같은 170후보를 읽었지만 SQL 횟수가 7→2, SQL 시간이 16.60→5.73ms, 전체 시간이 27.95→15.91ms였다. 건너뜀 구성은 전후 모두 후보 10행·SQL 1회·인증 60필드였다. 나머지 일반 페이지는 전후 SQL 1회였다. 이들의 작은 시간 차이는 이 로컬 측정의 변동이며 새 배치 규칙이 실행되지 않은 경로다.

별도로 `budgets.batch=500`을 사용해 확대 묶음이 200행을 넘어 직접 경로로 전환되는 조건도 같은 9개 검색으로 측정했다(`after-batch500/sweep.json`). `대로6고`는 SQL 2회·5.71ms, 전체 16.32ms, 후보 170행이었다. 기본 상한 200의 2회·5.73ms, 전체 15.91ms와 이 로컬 조건에서 비슷했다. 단위 fixture는 첫 SQL이 prefix, 확대 후 SQL이 직접 경로인 것도 확인했다. 다른 분포에서의 직접 경로 성능은 이 측정으로 보장할 수 없다.

## 구현·검증·한계

첫 배치는 기존 `limit + ceil(limit/4) + 2`다. 페이지가 모자라고 후보 묶음이 가득 찼을 때만 이 호출에서 누적한 인증 통과율로 다음 크기를 추정하고, 통과가 0이면 2배로 키운다. `budgets.batch`, 남은 `maxCandidates`, 기존 실제 수신 바이트 검사를 유지한다. 200행을 초과한 요청은 기존 직접 색인 경로를 사용한다. 통과율은 호출이 끝나면 버린다. 공개 API와 저장 구조는 바뀌지 않았다.

고의로 토큰 오탐을 만든 220행 일회용 테스트 fixture에서는 첫 페이지가 4회 이하 SQL로 정확한 8행을 반환하고, 후속 커서 페이지가 남은 2행을 중복·누락 없이 반환했다. 첫 요청의 prefix SQL과 확대된 요청의 직접 SQL을 모두 확인했다. `build`, `check`, `test`, `docs:check`를 실행했다. 원시 파일은 `before/sweep.json`, `after/sweep.json`, `after-batch500/sweep.json`, `before/matrix.json`, `after/matrix.json`이다. 결과는 로컬 합성 fixture에 한정하며 운영 성능 보장 또는 보안 인증이 아니다.
