# WAL 원본 실측: 검색 키는 보이지 않았고, 과거·롤백 자료는 남았다

2026-09-29. 제품 기준 `e3eb11585276db1201217938235b9aecb4bc5794`. **제품 변경 없음.** 기존 고객 fixture64행을 읽어32행을 파생 적재했다. 일회용 DB의 자기 스키마만 만들었으며 종료 후 삭제를 확인했다. 다른 작업자의 적재는 중단하지 않았다. 성능/시간 비교는 하지 않았고 측정 락을 잡지 않았다.

**미검증:** `wal_level=minimal/logical`은 서버 재시작이 필요해 공유 클러스터에서 전환하지 않았다. 전체 PITR 복구·임의 WAL 조각의 완전한 행 복원·외부 TOAST 조각 연결·LZ4/zstd 압축·장기간 통계 공격·운영 로그 수집은 이번 범위가 아니다. 아래 `발견`은 실제 SQL로 읽은 저장값과 WAL 바이트의 일치이며, 본문 복호화 성공률이 아니다.

## 실행과 판정 방법

PostgreSQL/pg_waldump18.4, `wal_level=replica`, `full_page_writes=on`, `wal_compression=off`, `data_checksums=on`, `wal_log_hints=off`, `synchronous_commit=on`이었다. SQL 로그는 `log_statement=none`, `log_min_duration_statement=-1`이었다. **WAL과 SQL/파라미터 로그는 다른 기록**이다.

현재 소스의 공개 `createSealed`·`sealed.insert/update/count/findMany`를 사용했다. 공개 API에 `sealed.delete`는 없으므로 일반 Drizzle `delete`와 companion의 FK cascade를 사용했다. 원문 새 생성 없이 기존 fixture 값을 재사용했다. 제품 키는 기존 연구용 고정 키다.

| 순서 | 수행 | 최종 구간의 자기 relation WAL 레코드 |
|---|---|---:|
| 1 | 고객32행,6개 암호화 칸 insert | 448 |
| 2 | 자기 부모·companion만 `VACUUM FULL`; 값이 전후 완전히 같은지 단언 | 14 |
| 3 | 기존8행의 memo를 다른 fixture 행의 memo로 변경 | 128 |
| 4 | 기존8행 delete; 부모/companion 각각24행인지 단언 | 18 |
| 5 | 다른 fixture4행 insert 후 의도적 rollback; 전후 저장값 동일성 단언 | 55 |
| 6 | 메모 contains count/list, 주소 LIKE count | 0 |
| 7 | 별도 평문 대조 표에 기존 fixture 메모1개 insert | 1 |

전체 수집 구간에서 relation으로 걸러낸 레코드는665건이다. 표의 합계664건 외1건은 평문 대조 표 준비 구간의 FPI다. 관계 재작성 전후 relfilenode와 TOAST/index를 모두 추적했고 다른 작업자 표는 필터에서 제외했다. 메모 count8, 목록8행의6칸48개 값, 주소 LIKE count4를 평문 oracle와 대조했다.

전역 checkpoint·서버 재시작·WAL 전환은 하지 않았다. FPI는 자기 표 재작성으로 확보했다. 마지막에 자기 표의 커밋을 통해 수집 끝 LSN 이전까지 flush되었음을 확인하고, 해당 구간이 포함된 세그먼트를 임시 복사했다. **실행 중 파일을 무제한 따라 읽은 것이 아니라, 복사본의 명시한 시작/끝 LSN만** PostgreSQL18 `pg_waldump -R … -s … -e … -b --save-fullpage=…`로 검사했다. 도구는 전체 호출에서 성공했다. 원시 세그먼트/FPI 복사본은 분석 후 지웠고, relation별 텍스트 덤프·FPI 해시·집계만 보존했다. [도구 설명](https://www.postgresql.org/docs/18/pgwaldump.html).

### 단순 문자열 검색으로 끝내면 틀리는 두 지점

1. **압축.** `wal_compression=off`여도 테이블의 가변 길이 값은 pglz로 압축될 수 있다. 초기 후보 배열384개 중 raw 연속 바이트 탐색은192개만 찾았다. pglz varlena를 해제하자 **384/384**가 나왔다. 위치 배열도173/192에서192/192로 늘었다. FPI 압축 설정과 TOAST/값 압축은 다르며, 압축은 암호화가 아니다. 이번 검사는 완전히 해제 가능한 범위 제한 pglz 후보를 찾은 뒤 실제 DB 값 전체와 대조했다. [TOAST](https://www.postgresql.org/docs/18/storage-toast.html), [pglz 형식 원문](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/common/pg_lzcompress.c).
2. **UPDATE의 공통 앞·뒤 부분 생략.** 최종 실행에서 새 메모 암호문 전체는4/8개, 헤더·nonce를 제외한 본문+태그는7/8개가 연속 바이트로 발견됐다. 새 후보 배열16/16, salt16/16, exact 도장8/8, 위치 도장 배열8/8은 모두 있었다. 일부 레코드의 `flags:0x60`은 과거 tuple의 공통 prefix/suffix를 재사용한다. 따라서 문자열을 통째로 못 찾은 것을 데이터가 사라진 근거로 삼지 않는다. 이번 도구는 과거 tuple을 이용한 전체 redo를 구현하지 않았으므로 빠진 새 암호문·offset 복원은 **미검증**이다. [heap WAL 형식의 PREFIX/SUFFIX 정의](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/include/access/heapam_xlog.h).

바이트 검사는 WAL 페이지 경계의24/40B 헤더를 건너뛰어 레코드를 연결했다. 헤더 삽입 때문에 바이트 패턴이 끊기는 문제도 피했다. 최종 원자료의 `phaseOnlyEvidence`는 해당 작업 구간만, `snapshots.*.evidence`는 수집된 과거 전체를 대상으로 한다. 초기 실패는 연구 스크립트의 API 반환형/도구 출력 디렉터리 가정 문제였고 매번 자기 스키마를 정리했다. 최종 실행은 모든 단언을 통과했다. 초기 status의 새 암호문5/8·본문8/8은 앞선 실행 값이며, 이 보고서는 nonce가 새로 생성된 최종 실행의4/8·7/8로 갱신했다.

## ‘삭제 레코드’와 ‘삭제된 자료가 남은 WAL’을 구분

| 구간을 제한한 검사 | 암호문 | 후보 배열 | 위치 도장 배열 | 의미 |
|---|---:|---:|---:|---|
| 최초 insert 구간, 초기32행×6칸 | 192/192 | 384/384 | 192/192 | 재작성 FPI를 만들기 전에도 값이 WAL에 있었음 |
| delete 구간만, 삭제8행×6칸 | 0/48 | 0/96 | 0/48 | 이번 replica DELETE는 예전 전체 값을 다시 쓰지 않았음 |
| 과거 전체, 동일 삭제8행×6칸 | 48/48 | 96/96 | 48/48 | 과거 INSERT/FPI가 남아 있으므로 삭제해도 회수 가능 |
| rollback 구간만, 취소4행×6칸 | 24/24 | 48/48 | 24/24 | 아직 커밋하지 않은 입력도 물리 WAL에 남음 |

후보 배열은 exact/substring 두 개이므로 칸당2개다. 표는 pglz 해제 후 저장값 일치 수이며 중복 값을 가진 칸도 각각 센다. count를 속이는 능력이나 평문 전체 복원율을 나타내지 않는다. 행·scope 같은 평문 메타데이터와 transaction ID·LSN·old/new tuple 위치는 이력을 연결하는 자료가 된다. 반대로 과거 구간이 잘려 나가고 필요한 페이지 이미지/기본 백업이 없으면 **임의의 DELETE 레코드 하나만으로 과거 행 전체를 되살린다고 보장할 수 없다**.

## SELECT와 full-page image의 주의점

이번 검색 세 번은 LSN 변화0이었다. 그렇다고 모든 SELECT가 WAL0이라고 말하면 부정확하다. 읽기 중 commit 상태의 hint bit를 갱신할 수 있고 checksums 또는 `wal_log_hints` 조건에서는 그 페이지 이미지가 WAL에 기록될 수 있다. 실제 전체 작업 덤프에도 `FPI_FOR_HINT`가 있다. **그것은 저장 페이지의 이미지이지, SELECT의 검색어/파라미터를 기록하는 기능이 아니다.** 이번 검색 직전 snapshot 판독으로 이미 읽힌 페이지였다는 점도 남긴다. [PostgreSQL의 hint/FPI 설명](https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-WAL-LOG-HINTS).

FPI는 해당8KiB 페이지에 있던 본문/색인 tuple들을 담을 수 있다. 본 실험에서 초기32행의 암호문·후보·도장·offset이 추출 이미지에 전부 있었다. 이후 만들어진 값은 모든 FPI에 자동으로 들어가는 것이 아니며, 이번 롤백 암호문24개는 FPI에서는0개, 물리 insert 레코드에서는24개가 나왔다. FPI를 삭제 이력 전체의 독립 백업이나 매번의 전체 행 로그라고 부르지 않는다.

## wal_level 차이: 실측과 문헌

| 설정 | 이번 실측 | 의미와 보안상 해석 |
|---|---|---|
| `minimal` | **측정 안 함** | 충돌 복구에 필요한 WAL은 남는다. 새 표/재작성 등 일부 작업에서는 행 WAL을 줄일 수 있으나 기존 표의 일반 변경 이력을 지우는 보안 모드는 아니다. PITR/스트리밍 복제 조건도 달라짐 |
| `replica` | **실측 완료** | 기본 모드. 과거 암호문·검색 자료와 롤백 입력이 위와 같이 남았다 |
| `logical` | **측정 안 함** | replica 정보에 논리 디코딩용 정보가 추가된다. `REPLICA IDENTITY FULL`인 UPDATE/DELETE는 예전 행 정보와 WAL량이 더 늘 수 있다. 본문이 앱에서 암호화되었다면 이를 켠다고 AES 평문으로 변하는 것은 아님 |

`wal_level`은 서버 시작 시 설정이며 이번에 공유 서버를 재시작하지 않았다. 논리 디코딩의 정상 committed-change 출력과 **원본 물리 WAL**을 구분해야 한다. 롤백된 입력이 정상 구독자에게 커밋 행으로 전달되지 않는 것과 공격자가 raw WAL 바이트를 보는 것은 다르다. 각 모드 간 바이트량·복원율 배수는 **측정 안 함**이다. [공식 설정 설명](https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-WAL-LEVEL).

## T1 대비 추가 위험과 운영 권고

기존 [수정 전후 시험](../../2026-09-29-attack-extra/report-ko.md)은 논리 snapshot128행/수정64행을 비교했고 `rawPhysicalWalParsed=false`였다. 이번 결과는 그 차분 공격에 필요한 이전 암호문·토큰·도장이 실제 물리 이력에서도 남을 수 있음을 보였다. 추가로 **삭제·롤백 입력**까지 확인했다. 따라서 최신 상태만 가진 T1보다, 이력·갱신 순서·트랜잭션 경계를 가진 T2에 가깝다. 과거의 알려진 원문/선택 삽입과 이력을 결합할 위험은 있지만 이번에 그 공격의 복원율을 새로 재지는 않았다.

단, **물리 기본 백업 자체도 정리 전 MVCC/dead tuple을 포함할 수 있다**. ‘백업’이라는 파일 이름만으로 최신 논리 상태만 있다고 가정하면 안 된다. 이번 비교의 추가점은 시간순 변경 레코드와 취소된 입력까지 확인한 것이며, 물리 백업에는 과거 자료가 절대 없다는 뜻이 아니다.

WAL에서 조각 키를 새로 얻지 못했다고 해서 T4와 결합할 수 없는 것은 아니다. 별도 로그·앱·실행 중 DB 관찰로 얻은 지속 조각 키가 있으면, 보존된 과거 salt/도장에도 적용할 수 있다. 이는 **WAL 단독**과 **WAL+관찰 키**를 구분해야 한다는 뜻이다.

- WAL·아카이브·물리 백업·복제본을 현재 DB와 같은 민감도로 접근 통제하고, 저장/전송 암호화의 키와 복구 권한도 분리한다. 파일 암호화는 저장소 탈취 경계를 위한 것이며 이미 접근 가능한 DB 관리자에게 질의 키를 숨기는 대체책은 아니다.
- 삭제/롤백을 안전 삭제로 설명하지 않는다. 복구 정책이 허용하는 보관 기간과 모든 복사본의 수명으로 위험을 관리한다. 이번 DROP SCHEMA도 원본 클러스터 WAL의 안전 삭제를 의미하지 않는다.
- `wal_level`, full-page 기록, checksums를 끄는 것을 보안 대책으로 권하지 않는다. 복구 성질을 떨어뜨리면서 현재 색인 누출의 원인을 없애지 못한다.
- SQL/드라이버/프록시/APM의 파라미터 기록은 별도로 확인한다. `log_statement=none`이어도 물리 WAL의 기존 저장물은 사라지지 않고, 반대로 WAL에서 키가 없었다고 오류 로그·메모리에도 없다는 뜻은 아니다.

근거: [최종 집계](result.json), [ABORT 레코드](rollback-transaction.txt), 같은 폴더의 relation별 `wal-*.txt`, [재현 스크립트](../../../followup-wal/run.ts). 재현은 저장소 루트에서 `rtk proxy node --import tsx bench/followup-wal/run.ts`. 별도 설치·제품 변경·전역 DB 설정 변경은 하지 않는다.
