# 독립 locator와 암호화 posting page: 정적 10만 행 연구 결과와 반례

## 판정

합성 고객 100,000행에서 **연구용 단일-anchor v2 adapter는 네 대표 조건을 통과했지만, 추가 반례에서 2배 상한을 43.534배로 크게 넘었다. 이 단일-anchor 방식의 채택 판정은 실패**다. 희귀 메모 1.040배, 흔한 회사 2글자 1.062배, 회사·메모·주소·이메일 OR 0.366배, 희귀 메모 101행 전체 배수 0.945배였지만, 결과가 없는 회사 `지사담`은 표준 142.089ms 대비 v2 **6,185.773ms**였다. 두 조각 `지사`(5,883행)와 `사담`(9,472행)은 각각 존재하지만 공통 행은 0건이다. 표준은 모든 조각의 DB 후보 조건으로 0건을 반환한 반면 v2의 단일 anchor는 5,883행을 인증 개봉한 뒤 모두 버렸다. 이는 임의 2글자 이상 부분문자열 지원에서 가능한 경계다. 먼저 만든 [v1 부정 대조군](posting-pages-research-ko.md)은 조각별 공개 page 그룹을 노출하고 전체 page를 읽어 흔한 검색 2.170배·OR 7.927배로 실패했다. 해당 숫자를 v2의 속도나 보안 성과로 섞지 않는다.

### 사용자 우선 검색: 회사 완전 일치·메모 중간 포함

별도 [우선 조건 원시 JSON](posting-pages-v2-primary.json)에서 같은 100,000행, UUID 정렬 첫 20행, 여섯 복호화 필드를 평문·표준·v2로 대조했다. 회사 `서울서비스 담당`은 정규화된 **완전 일치** 28,331건 중 20건을 반환했다. v2는 **전용 정확 인덱스가 아니라** 전체 값의 2글자 조각 중 드문 조각을 anchor로 사용한 뒤 전체 값 동일성을 인증된 평문에 검사한다. 메모 `푸른달`은 101건 중 20건을 반환했고, **반환 20건 모두** 정규화된 메모의 앞과 뒤에 다른 문자가 있는 중간 포함이었다(전체 101건도 모두 중간 포함). 실제 20개 UUID와 첫 행 여섯 값은 JSON에 있다.

표의 단계는 각 경로의 중앙 총시간과 **동일한 호출**에서 나눴다. 단위는 ms이며 A는 질의 토큰 준비+후보 SQL client wait(색인/posting과 고객 암호문 전송)+posting page AEAD+UUID 집합/정렬을 **포함하는 검색 방법 비용**이다. B는 정책 SQL, C는 여섯 필드의 인증 개봉과 마지막 술어 확인이다. D는 A+B+C+미할당 앱 시간이다. v2의 실제 검색 page는 조건마다 1개였고, 표준과 v2의 반환값·순서는 완전히 같았다. 이 우선 조건의 표준 비교는 회사 정확 Btree 술어와 메모 GIN 술어를 사용한다. 연구 adapter에는 아직 정확 전용 locator나 쓰기 경로가 없다. A의 세부 구성은 회사 표준 준비 .519/후보 DB 1.046, v2 준비 .264/후보 DB 1.299/page AEAD .309/결합 .056; 메모 표준 준비 .664/후보 DB 1.595, v2 준비 .206/후보 DB 1.497/page AEAD .195/결합 .031ms다. page AEAD는 C의 필드 복호화에 포함하지 않았다.

## 방법과 동일 결과

격리된 PostgreSQL `127.0.0.1:56439`에서 매 쓰기 전에 `assertDisposable`과 포트를 확인했다. 기존 `bench_realistic_100k.customers`의 고객 100,000행은 변경하지 않고 새 `bench_posting_pages_v2_100k.pages`에만 색인을 구축했다. 네 검색 필드(메모·회사·주소·이메일)의 **모든 정규화된 2글자 조각**에 독립 `HMAC-SHA256(scope,field,gram,kind,page ordinal)` locator를 사용했다. 암호화된 root manifest에 해당 조각의 page 수와 건수를 넣고, 최대 128 UUID씩 정렬한 page를 서로 다른 locator와 무작위 AES-256-GCM IV로 봉인했다. 테이블의 공개 열은 256비트 locator와 blob뿐이며 field, gram, row ID, page 번호 또는 행별 검색 토큰은 없다. 47,752개 삽입 순서는 섞었다.

검색은 각 조각 manifest를 인증 개봉하고, AND 구문마다 가장 드문 조각을 **필수 anchor**로 택한다. 참인 부분문자열에는 anchor가 반드시 포함되므로 그 posting의 UUID 후보를 가져오고 여섯 암호문 필드의 기존 repository `decryptRows`로 scope/policy 검사·AES 인증·개봉한 뒤 원래 정규화된 전체 술어를 검증한다. OR는 각 가지의 anchor 후보를 합친다. 20행 검색에서는 각 가지에서 불러온 page의 마지막 UUID가 미조회 page의 하한이므로, 더 작은 UUID가 남을 수 없는 범위의 후보만 반환 대상으로 처리한다. 충분한 검증 결과 20건을 얻으면 멈춘다. 101행 전체 배수에서는 끝까지 읽는다. page 손실·순서 오류는 예외로 처리한다.

평문·표준·v2 모두 UUID 순서, 20행(전체 배수는 101행), 같은 여섯 필드 `name, phone, address, memo, email, company`, 같은 scope와 `legacy-text-v1` 정규화다. 평문 기준선은 fixture의 사전 정규화된 열을 사용하고, 두 암호화 경로는 **똑같은 기존 `*_std_ct`**를 동결된 동일 `decryptRows`에 넣는다. 독립 평문 oracle에 대한 **전체 후보 ID 누락**을 검사하고, 준비 1회 뒤 3회 교차 순서 측정마다 최종 ID·정렬·여섯 값을 비교했다. 일곱 고유 조건에서 누락과 최종 불일치 0이다(메모 희귀 조건은 우선 조건에서 한 번 더 측정). OR v2 전체 후보는 42,716건으로 참값 42,472건보다 244건 많았고, 인증 개봉 후 원래 술어가 이 거짓 후보를 제거했다. [대표 조건 JSON](posting-pages-v2-query.json)과 [부재·반례 JSON](posting-pages-v2-adversarial.json)에 실제 결과 ID 20개 또는 101개, 첫 행의 여섯 값, 결과 SHA-256, 각 반복 및 단계가 있다. `지사담`은 [읽기 전용 탐색 코드](../posting-pages-adversarial-probe.ts)로 사전 선정했고, 두 조각의 공통 행과 전체 부분문자열 결과가 0임을 확인한 뒤 측정했다.

## 구축, 자원과 기밀성 한계

[구축 원시 JSON](posting-pages-v2-setup.json): 100,000행, 메모·회사·주소·이메일의 조각 등장 합계 5,472,494, 암호화 posting page **44,451개**와 manifest **3,301개**, 전체 **47,752행**. 정적 구축 총 **11.571초**(그중 shuffled insertion 3.500초, shuffle 0.016초), 저장 table+index **259,022,848 B**. 최초 삽입 종료 시 PK **3,784,704 B**; 별도 **후속 REINDEX 0.030초** 이후 PK **2,850,816 B**다. 최초 PK 생성만의 순수 시간은 분리되지 않았으며 REINDEX는 질의 측정 전에 완료했다. 한 조각의 최대 fanout은 회사 94,117, 주소·이메일 100,000건이다. 구축 시간은 정적 fixture 생성으로서 insert/update 운영 처리량이 아니다.

v2는 v1의 공개 locator 반복과 `page_no` 노출을 없앴다. 그러나 공개 blob 길이가 manifest와 일부 짧은 page를 구별할 수 있고, locator에 대한 반복 query·쓰기 관찰, heap 위치, 변경 전후 snapshot, 애플리케이션 외부 정보가 조각 빈도나 행 관계를 추정하는 단서가 될 수 있다. 단일 DB snapshot만 가진 **키 없는** 공격자는 AEAD page의 UUID를 직접 읽을 수 없지만, 공개 metadata로 행을 절대 추론할 수 없다는 주장도 하지 않는다. 이 benchmark는 합성 키가 소스에 공개되고, 비교용 원본 고객 표 자체에 평문 열과 기존 표준 검색 sidecar가 함께 있으므로 **실제 DB snapshot 기밀성 시험이 아니다**. 해당 전체 snapshot을 훔치면 평문을 바로 읽을 수 있다. 키 관리가 분리된 ciphertext-only 배포에서조차 known/chosen insertion, query log, 다중 snapshot, page 빈도 분석 및 레코드 재구성률은 검증하지 않았다.

append·delete·partial update는 관련 manifest와 여러 page의 재봉인, page split/merge, 경합 제어, DB transaction과 정책·암호문 원자성을 요구한다. 삭제 흔적, 동시 삽입, epoch·키 교체, 여러 scope, page 유실·손상 시 복구, 대규모 스케일은 구현하지 않았다. 특히 지연 page 읽기는 정적 UUID 정렬과 인증된 manifest 완전성에 의존하며, 쓰기 경로 없이 제품에 연결하면 검색 누락 가능성이 생긴다. 현재 단일 anchor는 부재 술어에서 모든 anchor 후보를 복호화해야 할 수 있어 2배 상한을 보장하지 않는다. 적응형 암호화 posting 교집합은 이 보고서에서 측정하지 않았으며 별도 담당자가 평가 중이다. 소스 `src`/`dist`, 기존 인덱스·고객 데이터, 실제 `5432`는 변경하지 않았다.
