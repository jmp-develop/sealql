검토일: 2026-09-29. 기준 HEAD: `906e09cc176a202320f4aea8f1a6fafef2e35ead`의 현재 제품 코드. 코디네이터의 독립 검토 답변이나 다른 검토자의 답변은 읽지 않았다. 기존 결정·실험과 이후 전달된 공통 배경·추가 과제는 읽었다. 제품 코드는 변경하지 않았다. 초기 문헌/코드 분석 뒤 추가 지시에 따라 일회용 DB의 기존 fixture만 읽고 메모리에서 공백 누출을 계산했다(§3.1). DB 쓰기·새 fixture 생성·성능 측정은 없다.

## 1. 기능·보안을 유지한 개선 여지

현재 범위는 compact 2글자 위치 증명, 정확 count, AND/OR/JOIN, 현행 LIKE 의미와 관리형 쓰기다. 이미 제외한 기능을 다시 넣거나 현재 기능을 끄는 안은 개선안으로 세지 않는다. 회사 2비트는 선택한 프로필이며 라이브러리의 모든 exact 기본값이 2비트인 것은 아니다.

### 남길 만한 방향 두 가지

| 방향 | 구체적인 변경 | 예상 이득 | 대가·확신 |
|---|---|---|---|
| **후보 추정/병렬 계획 바로잡기** | 같은 토큰·위치 함수·SQL 결과를 유지하며, 검색 표 전체에 병렬 경로가 검토되도록 하는 관계 정책과 후보 선택도 오차를 검증한다. 키워드별 분기는 넣지 않는다 | 100만 행 이메일/상담은 현재5.52/4.03초. 4 worker와 유효 병렬도3~4 가정이면 약1.48–1.93/1.06–1.39초. **추정**이며1초 이하 보장 없음 | 추가 CPU·worker 자원, 동시 요청 시 경합. 직렬 원인은 **확실한 과소추정**과 높은 확신의 페이지 문턱 재구성; 정책 효과는 미실험 |
| **동일 판정 알고리즘을 한 번의 네이티브 호출로 실행** | C/Rust 등으로 해시·배열 접근·전진 커서를 한 루프 안에서 수행하고 기존 salt/도장/키 전송 형식은 그대로 둔다. LIKE는 이미 있는 공통 위치 탐색 원리를 재사용한다 | PL/pgSQL 변수 대입·표현식 호출·배열 처리 비용을 줄일 가능성. 함수 구간2배 개선은 **검증할 가설**, 전체 SQL 배수는 **모름**. 행당 해시 횟수와 메모리 읽기는 남는다 | 서버 확장 설치·버전별 바이너리·메모리 안전성·취소 처리·배열 검증 부담. SQL 본문은 단순해져도 배포는 복잡해진다. 관리형 PostgreSQL에서 허용 여부를 확인해야 하므로 현재 제품의 무조건적 후속 패치로 권하지 않는다 |

첫 방향은 암호가 아닌 잘못된 비용 모델을 겨냥한다. 이메일 GIN 후보 추정816 대 실제265,980, 상담517 대298,430이다. `@>`가 상관된 조각 확률을 독립으로 곱하면서 과소추정한다. 함수 COST만 올리는 것으로는 예상 heap 크기에 따른 병렬 경로 생성 문턱을 해결하지 못한다. [100만 분석](../2026-09-29-million-parallel-analysis/report-ko.md), [원 EXPLAIN](../2026-09-29-scale-count-million/measure.json).

두 번째 방향은 **같은 알고리즘의 실행 비용을 줄이는 안**이다. 네이티브 확장으로 속도가 얼마나 오를지는 측정하지 않았다. 현재 SQL의 빠른 경로를 또 겹치는 방식은 이미 실패했다. 별도 첫 등장 패스는 반복·45자·NULL에서 퇴행했고, 단일 탐색 식 결합도 일관된 이득이 없었다. 직접 bigint cast는 약3–8% 개선이지만 PostgreSQL 18 이상 요구와 함께 적용 연기로 종결됐다. 이들을 이름만 바꿔 큰 개선이라고 재제안하지 않는다. [첫 등장/직접 cast](../2026-09-29-next-first-astra/report-ko.md), [C 함수 설치 요구](https://www.postgresql.org/docs/17/xfunc-c.html).

**단순화의 한계 — 추정:** 결정022로 일반 LIKE가 이미 고정 길이 구간의 순서 탐색으로 정리됐고, compact만 남겨 중복 스트림도 제거했다. 이제 위치 확인 자체를 없애면 임의 길이 substring/LIKE 정확성이 깨진다. 동일 의미·누출·배포 조건을 모두 유지하는 작은 SQL 변경으로 한 자릿수 배의 범용 개선이 남아 있다고 주장할 근거는 없다. 이는 최적성 증명도, 향후 개선 불가능 주장도 아니다.

여기서 B/C/D는 과거 통합 실험의 이름이다. 최근 첫 등장 실험의 A/B 표기와 다르다.

| 이전 안 | 한계와 이번 방향의 차이 |
|---|---|
| 초기 B: 길이2..K 문자열의 행별 도장 | K=8의 조각 집합 일치는 긴 문자열의 순서/인접성을 증명하지 못했다. 통합45자 조건에서 실제0 대 후보판정2440 반례가 있었다. K를 무한히 키우면 모든 부분 문자열 저장은 값 길이의 제곱까지 커지며 일반 LIKE도 별도 문제다. 현재 위치 알고리즘의 실행 최적화는 그 저장 확대를 하지 않는다 |
| C: 등장별 태그 + 장부 | 행별 태그 열거와 카운터 유지·쓰기 경합이 생긴다. 결정011의 stateful 문제와 같은 계열이며 DB 장부가 사라지지 않는다. 위 두 방향은 태그 장부·등장별 side row를 추가하지 않는다 |
| D: 길이2..K 후보 + 행별 확인값 | 후보 오탐을 줄여도 긴 조건의 완전한 위치/순서 증명이 자동으로 생기지 않는다. 16비트 후보 구성을 바꾸면 누출과 후보 비용도 같이 바뀐다. 제안은 현재의 전체 의미를 보존한 판정과 동일 후보 형식이 출발점이다 |

## 2. T4 위치 누출은 어디까지 불가피한가

### 현재 구조: 피할 수 있음이 아니라, 실제로 복원 가능함 — 확실

현재 [stampKey/positionProof](../../../src/core/search-stamps.ts)는 조각·모델·필드·scope에 결속된 키 k를 만들고 다음 증명을 저장한다.

`stamp(i) = SHA256(k || rowFieldSalt || uint32BE(i))[:8]`

DB가 k를 한 번 관찰하면 접근 가능한 각 행에서 i=1,2,…를 계산해 정렬 도장 배열에서 찾고 대응 offset을 읽을 수 있다. 이는 검색문 전체의 일치 여부와 무관한 **조각의 모든 등장 위치**를 준다. substring에서 사용자가 `%서비스상담%` 한 번만 검색해도 관찰자는 각 전달 조각을 따로 검사할 수 있다. 입력 offset·affix·qlen을 SQL 함수에서 제한하는 것은 키를 가진 DB의 오프라인 연산을 제한하지 않는다.

같은 키는 미래의 새 salt에도 유효하다. 재암호화 시 salt만 교체하거나 bind 값을 지우거나 SQL 함수를 감추는 것은 이미 관찰된 키를 폐기하지 않는다. 루트 키/다른 scope 키가 곧바로 유출된다는 뜻은 아니다. [추가 공격 §2–3](../2026-09-29-attack-extra/report-ko.md)은 관찰 키의 위치 복원과 재쓰기 후 키 재사용을 실제로 확인했다.

### 일반적인 정확 계산: 중간 위치 공개가 필수는 아님 — 확실(원리)

유한한 저장 문자열과 LIKE 조건의 판정은 회로로 표현할 수 있다. 위치별 비교·인접성·구간 순서·행별 일치 bit를 **암호화/비밀분산 상태로 계산하고 최종 합계만 공개**하는 것은 원리적으로 가능하다. 정확 count와 중간 위치 공개는 같은 요구가 아니다.

| 설계 계열 | 유지할 수 있는 기능 / 줄이는 정보 | 대가와 한계 | 확신 |
|---|---|---|---|
| 정확 정수/Boolean 기반 동형 계산 | 서버가 substring/LIKE 회로와 합계를 계산하고 앱은 최종 숫자만 복호화. 조각별 위치 중간값을 서버에 주지 않을 수 있음. 정수 modulus·회로 범위를 맞춰 count overflow를 피해야 함 | 저장 표현과 질의 엔진을 새로 설계해야 함. 목록/JOIN도 원리적으로 계산할 수 있지만 선택·정렬·중간 크기의 비용이 큼. 일반 LIKE의 실용 속도는 **모름**. 근사 CKKS 결과를 정확 count의 대체로 쓰지 않음 | 원리 **확실**, 현재 성능 목표 충족 **모름** |
| MPC/비밀분산 계산 | 서로 결탁하지 않는 실행 주체들이 전체 판정을 수행하고 필요한 결과만 공개 | 추가 서버/통신과 비결탁 전제 또는 앱의 프로토콜 참여. 현재 단일 PostgreSQL 배포와 다름 | 원리 **확실**, 이 제품의 실용 설계 **모름** |
| TEE와 접근 패턴 은닉 실행 | 신뢰 경계 안에서 판정하고 DB 운영자에게는 위치를 숨길 수 있음 | 하드웨어·attestation·부채널·운영 신뢰가 추가됨. enclave만으로 접근 패턴이 사라지지 않으며 기존 신뢰 가정에 대한 무조건적 보안 우위가 아님 | 방향 **확실**, 배포별 보장 **모름** |

Microsoft SEAL은 BFV/BGV 정확 정수 연산을 제공하지만 비교·정렬·정규식 등은 실용성이 어렵다고 명시한다. 따라서 **구현 가능한 빠른 드롭인 대체재가 있다는 근거로 인용하지 않는다**. Opaque는 enclave에 더해 oblivious 연산을 쓰는 실제 연구 사례이며, 그 논문의 다른 워크로드 성능을 SealQL 예상 배수로 옮기지 않는다. [SEAL 공식 설명](https://github.com/microsoft/SEAL#introduction), [일반 안전한 2자 계산](https://iacr.org/archive/crypto2013/80420149/80420149.pdf), [Opaque](https://www.usenix.org/conference/nsdi17/technical-sessions/presentation/zheng).

**현재 관측 입력을 유지한 답 — 확실:** 단일 비신뢰 일반 DB가 현재 k·salt·도장·offset을 모두 볼 수 있는 조건을 그대로 유지하면서 위치 복원을 막는 방법은 없다. 공개 위치에 난수 이동을 더하거나 per-row salt를 늘리는 것은 k로 복원되는 관계를 없애지 않는다. 이 결론은 현재 관측 입력에 대한 것이며 모든 검색 암호 방식의 불가능 정리가 아니다. ORAM/패딩만 추가해도 이미 전달한 k와 offset 해독 능력은 사라지지 않는다. 전체 검색어 도장만 보내는 초기 B 회귀는 임의 길이·일반 LIKE 문제를 다시 만든다.

또한 안전한 계산으로 내부를 숨겨도 **정확한 응답을 관찰하는 주체**가 자기가 고른 많은 질의를 실행하면 결과 자체로 추론할 수 있다. 이것은 중간 위치 누출과 별도다. 서버가 암호화된 count만 받는 구조에서는 서버에게 그 숫자가 자동으로 공개된다고 가정하지 않는다. 정확 기능을 유지하면서 모든 권한 있는 질의 결과의 정보까지 없애는 것은 다른 요구다.

## 3. 백업만 가진 T1–T3는 R9 이전보다 약해졌는가

비교 기준은 R9 이전 HMAC 후보 토큰 + 앱의 인증 복호화 판정과, 현재 compact 위치 도장이다. 질의 키/검색어/앱 토큰 계산 oracle를 가진 공격은 이 표에서 T4/T5로 분리한다.

| 항목 | 이전 → 현재 | 독립 판단 | 확신 |
|---|---|---|---|
| 본문 AES-GCM·행/필드/scope AAD | 동일한 field-cipher 경로·128비트 인증 태그 유지 | 도장 추가 때문에 본문 AES 키 강도가 낮아지거나 행 결속이 제거된 것은 아님 | 코드 범위 **확실** |
| 정규화 길이 | 이전은 주로 암호문 UTF-8 바이트 길이와 토큰 집합 크기. 현재는 compact Unicode 글자 수가 직접 저장됨 | **추가 누출이며 약해진 부분**이다. 공백·다바이트 문자·반복 때문에 byte 길이/고유 토큰 수와 완전히 같지 않다. 이미 형식으로 길이를 아는 필드에서는 추가량이 작을 수 있음 | 채널 **확실**, 실데이터 복원 증가 폭 **모름** |
| offset 배열과 행별 도장 | n−1개 서로 다른 도장과 대응하는 위치의 순열 추가 | 키 없는 도장을 조각 이름으로 바꿀 수 있다는 근거는 없음. PRF/해시 가정 아래 위치에 붙은 무작위 순위에 가깝다. 반복 조각도 ordinal을 섞어 다른 도장을 만들므로 반복 횟수 그룹이 평문으로 저장되는 구조가 아님 | 구조 **확실**, 전체 결합 누출의 형식적 동등성 **모름** |
| T2 여러 시점 | 기존 토큰 차집합에 새 정규화 길이·proof 재생성 시점이 추가 | 변경 내용의 제약을 더 줄 수 있음. salt 교체로 서로 다른 시점의 도장 값 직접 교집합은 차단되지만 행·토큰 연결은 남음 | 논리 전후 실험 **확실**, raw WAL에서 추가 복원량 **모름** |
| 알려진 행(T3) | 기존 deterministic 후보 토큰 라벨 전파가 남고 길이 조건 추가 | 알려진 평문만으로 다른 행의 salt 도장에 같은 라벨을 직접 붙일 수는 없다. HMAC 조각 키를 계산하는 권한과 알려진 평문은 다르다. 기존 후보/길이/공개 자료 결합 추론은 계속 가능 | 구별 **확실**, 최적 공격 강도 **모름** |
| 회사 2비트 | exact 후보 동치류를 크게 섞음 | exact 채널만 보면 의미가 있지만 **substring이 함께 켜진 회사 칸의 전체 누출을 2비트로 제한하지 않는다**. 현재 공격/규모 fixture는 company에도 substring=true. 회사 후보 빈도·길이·조각 연결은 여전히 드러남 | **확실** |

정규화 길이가 중복이라는 주장은 성립하지 않는다. 예를 들어 반복 횟수가 다른 다바이트/ASCII 혼합 문자열은 동일한 UTF-8 길이와 동일한 인접·skip 조각 집합을 가질 수 있지만 compact 글자 수는 다를 수 있다. 반대로 **offset 배열 길이**는 compact2에서 `max(n−1,0)`이므로 이미 공개된 n을 알고 나면 그 자체의 새 정보는 없다. 기존 기계적 공격에서도 정규화 길이에 배열 길이를 추가했을 때 예측은 전부 같았다. 이 예시는 정보 차이의 설명이며 새 공격 성공률 측정은 아니다.

**중요한 수치 경계:** [추가 공격](../2026-09-29-attack-extra/report-ko.md)의 후보-only→위치 추가 값 복원 전화0→87.48%, 주소3.96→35.32%는 **질의1000회·그 원문·참조 사전까지 아는 T4 비교**다. 이 수치를 백업-only 약화라고 보고하면 틀린다. 같은 보고의 백업 통계는 회사 빈도+길이 약70.62% 등의 위험을 보여주지만, 동일한 최적 T1–T3 공격으로 이전/현재 전체를 비교한 결과는 아니다. 어휘가 적은 fixture의 수치를 일반 자연어로 확대할 수도 없다.

별도의 무결성 변화는 있다. 예전 앱은 받은 조건 칸을 인증 복호화해 거짓 positive를 제거할 수 있었으나 현재는 DB 판정을 믿고 count 숫자만 받는다. 또한 64비트 도장의 우연한 충돌은0이 아니다. 이것은 **T6/판정 정확성 문제**이며 T1–T3의 AES 복호화 저항이 낮아졌다는 주장과 섞지 않는다. 이전에도 DB의 행 누락을 탐지하지 못했다. [현재 위협 모델](../../../docs/threat-model.md), [결정015](../../../docs/decisions/015-database-search-proofs.md).

### 3.1 추가 검증: 암호문 길이와 compact 길이로 공백 수 계산

**결론 — 확실:** 원문이 NFC 상태의 한글 음절과 ASCII 공백으로만 구성되면 `s = C − 29 − 3n`이다. C는 저장 암호문 바이트, n은 공백 제거 후 글자 수, s는 원문의 ASCII 공백 개수다. 문자열·조각 키가 없어도 백업의 두 길이로 계산된다. words 스트림 제거는 두 정규화 스트림 사이의 직접 차분을 없앴지만 **다른 두 길이의 결합으로 같은 종류의 정보를 복원하는 길은 남았다**. 공백의 **수**가 드러나며 위치·단어 경계까지 이 식만으로 알아내는 것은 아니다. words의 정규화 공백 수와 원문의 공백 문자 수는 연속 공백·다른 whitespace가 있을 때 구분해야 한다.

공백 외 문자가 UTF-8에서 1/2/3/4바이트인 개수를 각각 a₁/a₂/a₃/a₄라고 하면, 정규화가 그 바이트 폭과 글자 수를 바꾸지 않는 범위에서 다음과 같다.

`b = C − 29`, `n = a₁+a₂+a₃+a₄`, `s = b − 3n + 2a₁ + a₂ − a₄`.

따라서 ‘순수 한글’은 충분조건이며 필요조건은 아니다. ASCII 5글자 접미사와 3바이트 본문임을 알면 `s=b−3n+10`으로 똑같이 정확하다. 반대로 혼합 문자 구성을 모르면 보정항을 추측해야 한다. NFC 합성·전각 변환·2/3바이트 whitespace는 별도 보정이 필요하다. 아래 fixture는 30만 칸 모두 공백이 U+0020이고 비공백의 정규화 전후 바이트 폭·글자 수가 같음을 단언했다.

#### 실제 10만 고객, 3개 칸의 계산

원본 `bench_realistic_100k.customers`의 100,000행을 읽었다. 입력을 읽기 전에 일회용 클러스터 확인 및 포트 확인을 수행했고 원본은 읽기만 했다. 원문·ID 목록은 결과에 저장하지 않았다. 기존 pre-R9 토큰 생성기를 재사용해 substring 토큰 개수 t를 계산했으며, 3개 칸 각각20행은 과거 커밋의 실제 WebCrypto 출력과 일치함을 확인했다. t는 고정 연구용 키로 메모리에서 생성한 과거 형식의 값이며 원본 fixture의 다른 암호화 칼럼을 계수한 것은 아니다. b는 실제 원문 UTF-8 길이에서 계산했고 현재 제품의29B envelope 산식을 적용했다. 패딩용 새 암호문은 만들지 않았다.

| 사실/조건 | 메모 100,000행 | 주소 100,000행 | 이름 100,000행 |
|---|---:|---:|---:|
| 순수 한글+공백인 원문 | 0 | 0 | 0 |
| 보정 없는 `b−3n`이 실제 공백 수와 일치 | 0% | 0% | 0% |
| 한글 본문+ASCII 5글자 접미사인 행 | 78,144 (78.144%) | 0 | 68,143 (68.143%) |
| 위 형식을 아는 경우 보정식 정확 일치 | 78,144/78,144 (100%) | 해당 없음 | 68,143/68,143 (100%) |
| 실제 공백 수 분포 | 2개98 / 3개97,462 / 19개3 / 20개2,437 | 3개16,821 / 4개83,179 | 1개76,056 / 2개23,944 |

주소에는 숫자 번지와 외국어, 이름·메모에는 접미사가 있어 순수 한글 식을 무조건 적용하면 모두 틀린다. 이는 한글 칸의 취약성을 반박하지 않는다. 위 형식별 수치는 **평가자가 실제 형식을 확인해 나눈 부분집합**이며, 공격자가 사전지식 없이 그 부분집합을 식별했다고 주장하지 않는다. 한자 본문+ASCII 접미사도 같은 보정식이므로 이름에서 식 `b−3n+10` 자체의 전체 적중은76.056%다.

#### R9 이전 대비: 길이 제약과 참조 자료 공격을 분리

pre-R9의 기본 adjacent+skip+start+end 토큰 수는 n≥2에서 최대 `2n−1`이다. 중복·16비트 충돌로 줄어들 수 있으므로 `L=ceil((t+1)/2)`는 **n의 하한**이고 등식으로 취급하면 안 된다. 문자 구성 사전지식 없이 ASCII 공백과 폭1..4의 비공백만 가정하면 이전 제약은 `0≤s≤b−L`, 현재 제약은 `max(0,b−4n)≤s≤b−n`이다. 이는 토큰 라벨·빈도·사전을 쓰지 않은 보수적 범위다. 모든 범위가 실제 공백 수를 포함함을 30만 칸에서 단언했다.

| 문자 구성 모르는 길이 제약 | 메모 | 주소 | 이름 |
|---|---:|---:|---:|
| 이전 → 현재 단일 공백 수로 확정된 행 비율 | 0% → 0% | 0% → 0% | 0% → 0% |
| 남는 정수 후보 개수 평균, 이전 → 현재 | 17.84337 → 17.21261 | 20.66181 → 20.66037 | 7.04102 → 7.04004 |
| 범위가 엄격히 좁아진 행 비율 | 3.937% | 0.144% | 0.097% |
| 현재 후보 개수 최소 / 중앙 / 최대 | 4 / 18 / 110 | 8 / 25 / 29 | 3 / 8 / 10 |

‘한글 본문+ASCII 5개’만 알고 템플릿 사전은 모르는 경우 이전의 가능한 n은 `L≤n≤floor((b+10)/3)`이고 s는 3씩 변한다. 그 제약만으로 공백 수가 단일 값인 메모는98/78,144행(0.1254%)에서 현재78,144/78,144행(100%)으로, 이름은68,138/68,143행(99.9927%)에서100%로 늘어난다. **이 수치는 제약식의 단일값 비율이며, 이전의 더 강한 토큰 공격이 나머지를 못 푼다는 뜻은 아니다.** 특히 메모의 이전 범위 대부분은 공백0/3처럼2개 후보뿐이다.

참조 자료 공격도 따로 수행했다. 기존과 같은 seed714029로 ID가 겹치지 않는 참조10,000행과 피해10,000행을 나눴다. 참조의 관측값별 공백 수 집합을 만들고, 유일한 값이면 추측했다. 이 공격은 공격자의 참조 분포에 의존하며 논리적 확정/일반 데이터 보장이 아니다.

| 참조 기반 유일값 추측의 **정답 행 / 피해10,000행** | 메모 | 주소 | 이름 |
|---|---:|---:|---:|
| 이전: 암호문 바이트 길이 b만 | 100% | 100% | 7.65% |
| 이전: b와 실제 과거 토큰 개수 t | 99.97% | 100% | 99.94% |
| 현재: b,t,n 모두 | 99.97% | 100% | 99.94% |
| 현재: b,n만 | 100% | 100% | 100% |

b,t 참조에서 빠진 조합은 메모3행·이름6행이며 오답으로 채우지 않았다. b,t,n의 세 조건을 무조건 동시에 요구하면 참조 부족으로 같은 행이 빠진다. 새 정보를 이용하는 공격자는 더 작은 관측 조합도 선택할 수 있으므로 b,n 결과도 제시했다. **이 템플릿 fixture에서는 이전 정보만으로 공백 수 추측이 이미 거의 완성돼 있어 R9 전체 약화량을 대표하지 못한다.** 길이 결합이 정확한 수학적 채널이라는 사실과, 이 fixture의 성공률 증가가 작다는 사실은 양립한다. n 없는 임의 자연어에 대한 전체 증가량은 **모름**이다.

#### 저장 형식 변경 없이 막을 수 있는가

**현재 b와 n을 백업에 그대로 남기는 한 이 산술 채널을 막을 수 없다 — 확실.** SQL·함수·인덱스·로그 설정을 바꿔도 백업의 숫자 두 개로 하는 계산은 남는다. n 열만 지워도 n≥2에서 도장/offset 배열 길이가 n−1이고 offset 집합은0..n−2라 n이 복원된다. salt 증가도 길이를 숨기지 않는다.

가장 작은 별도 검토 후보는 **본문 암호문 내부 패딩**이다. 원문 바이트 길이4B와 원문·패딩을 함께 인증 암호화하고, 암호화 전 payload를 Q바이트 배수 `P=Q·ceil((b+4)/Q)`로 만든다. 공개 길이는 `29+P`다. 원래 공백/대소문자를 그대로 반환하며 compact 검색 표·질의·DB count 의미는 유지할 수 있다. DB 칼럼 타입은 같아도 **암호문 형식 변경과 기존 본문 전체 재암호화**가 필요하다. 평문 길이를 암호문 밖에 두거나 복호화 없이 벗길 수 있는 padding을 쓰면 목적이 사라진다.

| Q=64 가상 패딩, 각100,000행 | 현재 본문 암호문 합계 | 패딩 후 합계 | 증가 / 행 | 현재 본문 대비 |
|---|---:|---:|---:|---:|
| 메모 | 6,000,353B | 9,612,320B | 평균36.12B | 1.602배 |
| 주소 | 6,355,695B | 9,300,000B | 평균29.44B | 1.463배 |
| 이름 | 4,439,472B | 9,300,000B | 평균48.61B | 2.095배 |
| 3개 칸 합계, 고객100,000행 | 16,795,520B | 28,212,320B | 고객당114.17B | 1.680배 |

이는 실제 원문 길이로 계산한 **바이트 산술**이며 새 암호화/DB 용량/속도 실측이 아니다. 검색 표·부모 행 header·index·TOAST 공간은 제외했다. companion-only count의 연산은 그대로일 것으로 **추정**하지만 목록·쓰기의 전송/암호화 바이트는 늘고 실제 시간은 **측정 안 함**이다. 같은 계산의 Q32/Q128 결과도 JSON에 있다. 무조건 큰 Q가 더 안전하고 가치 있다는 결론은 내리지 않는다.

**패딩도 공백 수 전체 은닉 보장은 아니다.** Q64에서 공개 P가 알려주는 원문 b 범위는 `max(0,P−Q−3)..P−4`다. 비공백 바이트 수까지 아는 공격자에게도 이번30만 칸의 산술적 공백 후보는 최소22개 이상(메모32/주소22/이름44)이지만, 템플릿 사전은 그 범위를 다시 좁힌다.

| 같은 분리 참조 공격, Q64의 공개 P와 n만 사용 | 메모 | 주소 | 이름 |
|---|---:|---:|---:|
| 참조에서 유일한 공백 수이며 실제도 맞는 비율 | 50.76% | 65.85% | 100% |
| 애매한 경우에도 참조의 최빈값을 택한 전체 정답률 | **99.88%** | **98.25%** | **100%** |
| 후보 범위가 실제 공백 수를 포함한 비율 | 100% | 100% | 100% |

토큰 개수 t까지 넣으면 주소의 유일 정답은99.72%까지 다시 오른다. Q32는 메모의 유일 정답100%를 그대로 남겼고, Q128도 이 참조 공격에서 Q64보다 더 낮은 정답률을 만들지 못했다. 따라서 ‘패딩 뒤 유일한 값이 줄었다’만 보고 공격 방어에 성공했다고 결론 내리면 안 된다. 위 결과도 한 시드·템플릿 fixture·단순 공격의 하한이며 최적 공격이 아니다.

| 더 강한 변경 | 기능·누출 효과 | 대가/판정 |
|---|---|---|
| n 숨김 + 도장/offset 배열을 함께 패딩 + 끝 경계의 비공개 증명 | 백업에 정확 n을 직접 남기지 않을 여지가 있음. n만 암호화하는 것으로는 부족하며 starts/ends/LIKE의 길이·경계 검증을 바꿔야 함 | 새 증명 구조·더미의 구별 불가능성·우연 일치·후보 토큰 개수·장기 갱신 누출까지 재검증 필요. 모든 companion 재구축, 용량·순회 비용 증가. **미설계/미측정**, 즉시 채택안 아님 |
| 본문·검색 배열·후보 개수를 모두 길이 은닉 | 남은 길이 채널도 줄이는 별도 연구 | 함수/조회/쓰기까지 넓은 변경. 무제한 입력에 유한한 단일 고정 크기를 강제할 수 없고, 구간 패딩은 구간을 남김. **성능·충분한 보안 이득 모름** |

이번 권고는 **공백 채널을 명시적으로 수용할지 먼저 결정하고**, 수용할 수 없다면 본문 내부 패딩을 최소 후보로 평가하되 n/토큰/사전의 잔여 복원을 함께 보는 것이다. 공백 삭제 후 암호화해 원문을 잃거나 검색 기능을 제한하는 대안은 제안하지 않는다. 결정019의 제거는 유효하지만 ‘공백 개수 정확 노출이 사라졌다’로 확대 해석하면 안 된다.

## 4. 미시험 공격 중 실제 위험이 큰 것

이미 한 시험을 미시험이라고 부르지 않는다. 현재는 키 관찰/검색어 라벨 관찰, 단순 빈도 추측, 논리적 전후 스냅샷128행, 제한된 사전 결합, 과거 시간 표의 kNN 분석까지 있다. 남은 것은 아래다.

| 우선 | 공격과 필요한 권한 | 위험 이유·기존 시험과 차이 | 다음에 해야 할 기계적 검증 | 확신 |
|---|---|---|---|---|
| 1 | **적응적 선택 평문 삽입 + 검색 관찰**. 피해자와 같은 모델/필드/scope에 값이 들어가게 할 능력과 결과/키 관찰 | 공격자가 구별되는 조각 조합을 넣어 익명 키/토큰의 문자 라벨을 얻을 수 있다. 기존 공격은 수동 참조 사전·고정 질의 모형이며, 능동적으로 다음 입력을 고르지 않았다. 무작위 키-only 결과가 낮다는 점을 방어로 볼 수 없음 | 쓰기 수·입력 바이트 제한을 고정하고 관측 질의 라벨/위치 복원율을 수동 공격과 비교. 다른 scope에만 쓸 수 있을 때는 실패하는 경계도 확인 | 문헌의 공격 계열 **확실**, 현 제품 효율/성공률 **모름** |
| 2 | **조각 그래프·IKK류 전역 최적화 + 필드/FK/시간 결합**. 백업과 공개/일부 알려진 행 | 현재 사전 방식은 참조에 없는 전화·이메일·메모를 조립하지 못한다. 인접/skip 토큰, 고정 형식, 연계된 필드, 조각의 겹치는 위치를 함께 풀면 제한이 달라진다. 단일 단순 추측기의0%는 특히 약한 증거 | 참조·피해를 분리한 공개 말뭉치 및 형식 필드, 여러 시드에서 사전 밖 값/6필드 레코드 복원. 후보-only/현재를 같은 최적화기로 비교 | 실제 중요성 **추정**, 증가 폭 **모름** |
| 3 | **물리 WAL/dead tuple/백업 + 장기 관찰 키 결합**. 보관 파일/복제본 또는 과거 bind 기록 접근 | 논리 전후64건은 raw 파일 회수·삭제된 값·장기간 부분 수정·트랜잭션 롤백 잔존물을 시험하지 않았다. 이전 관찰 키가 미래 salt에서도 유효한 것은 이미 확인됨 | 삭제·수정·롤백·재색인 전후의 복구 가능한 역사, 키 누적에 따른 시점별 값 복원. 키 없는 T2와 키가 섞인 T2+T4를 별도 표시 | 키 지속성 **확실**, 실제 추가 복원량 **모름** |
| 4 | **적대적 DB의 거짓 proof/count 및 선택적 응답**. DB 실행/쓰기 권한 | 인증되는 것은 반환 암호문이지 WHERE나 count가 아니다. 정상 암호문을 그대로 두고 companion/함수 결과를 바꿔 앱의 후속 행동을 유도할 수 있다. 조건을 권한 판단에 쓰면 영향이 큼. 단순 누락은 이미 알려졌지만 거짓 positive·업무 효과·선택적 실패의 체계적 시험은 없음 | 정상 암호문+다른 proof, 거짓 scalar, 재생·누락, JOIN 조건 바꿔치기를 통해 허용되는 잘못된 결과와 정보 피드백 측정 | 판정 비인증 **확실**, 특정 서비스에서의 피해 **모름** |
| 5 | **실제 동시 부하의 비용·취소 공격**. 허용된 검색 API 호출권 | 긴 반복 LIKE/광범위 count, 병렬 worker 점유, 취소 뒤 남은 작업을 조합할 수 있다. 긴 값 회귀와 일부 취소 시험은 있지만 다중 사용자 가용성 공격은 별개 | 데이터/질의 길이를 늘려 CPU·메모리·취소 지연과 다른 사용자의 p95를 측정. 의미 변경 없이 호출자 deadline·접근 통제의 효과 확인 | 가용성 위험 **추정**, 규모별 임계 **모름** |

1번은 [Zhang·Katz·Papamanthou의 file-injection 공격](https://www.usenix.org/conference/usenixsecurity16/technical-sessions/presentation/zhang), 2번은 [Cash 등의 leakage-abuse 연구](https://eprint.iacr.org/2016/718)에 근거한 우선순위다. 이 논문의 성공률을 우리 제품 수치로 가져오지 않는다. 실제 서비스에서 입력 권한·scope 격리가 이 공격을 제한할 수 있으며, 공격자에게 피해 scope의 입력권이 있다고 몰래 가정하지 않는다.

**운영에서 먼저 확인할 경계 — 확실한 설계 노출, 배포 실태는 모름:** DB·드라이버·프록시·APM의 오류/trace/크래시 수집에 bind 키가 남으면 단순 백업 탈취가 더 이상 T1-only가 아니다. 정상 로그를 끈 것과 실행 중 DB 관리자에게서 인자를 암호학적으로 숨기는 것은 다르다. TLS는 수동 전송 관찰을 줄이지만 DB 종단 자체의 관찰을 막지 않는다. 키 탈취·권한 오용·GCM nonce 관리도 중요하지만 R9에 새로 생긴 취약점이라고 분류하지 않는다.

## 최종 권고

1. 이번 저장 형식 확정 전에는 **b+n 공백 채널의 수용 여부**를 먼저 결정한다. n 열만 지워서는 안 된다. 본문 내부 패딩은 원문·검색 기능을 보존하는 작은 후보지만, fixture의 사전 추측을 크게 줄이지 못해 곧바로 채택할 근거는 부족하다. 이후 성능 과제는 **planner의 후보 오차/병렬 경로**, **동일 판정의 실행 비용** 순이며 저장 형식 결정과 분리해 진행할 수 있다. 100만 행 병렬 추정은 보편적 최대 scope10만 행의 개선 보장이 아니다.
2. **T4 위치 누출을 제품의 수용한 누출로 명시**하되 수학적으로 불가피하다고 포장하지 않는다. 이를 줄이려면 안전한 계산이나 새로운 암호 프로토콜과 그 배포 대가를 별도 연구해야 한다.
3. T1–T3에 대해서도 “이전과 완전히 같다”거나 “현재 안전하다”는 판정은 보류한다. 추가 길이 채널을 인정하고 **능동 삽입·강한 결합 복원·물리 역사 공격**을 같은 조건에서 실행하는 것이 다음 보안 근거다.

본 문서는 독립 설계 검토와 제한된 길이 채널 메모리 검증이다. 능동 삽입·전역 복원·물리 역사 공격의 새 실험을 대신하지 않는다. 기능 통과·복원0건·단순 통계 공격 실패를 안전성 증명으로 사용하지 않았다.
