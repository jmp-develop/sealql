# 제품 다중 컬럼 GIN DDL 검증

2026-09-27 · 일회용 PostgreSQL `127.0.0.1:56439` (`.local/pg-test`). `assertDisposable`로 데이터 디렉터리·소유자·포트를 확인했다. 기존 `bench_standard_next_100k.customers_skip` 부모와 companion에서 같은 암호문·토큰 100,000행을 새 제품 DDL의 `customers_skip_product_multi` 부모·companion으로 복사했다. 원본과 `bench_realistic_100k`는 읽기만 했다. 새 companion은 여섯 부분 검색 열을 덮는 GIN 하나, 정확 토큰 B-tree 여섯 개와 PK를 가진다([`fixture.json`](fixture.json)). 토큰 열·값은 바꾸지 않았다.

제품 공개 API `findMany`를 기본 구성(건너뛴 조각 켬)으로 실행했다. `matrix.ts`의 21개 케이스와 주소 빈도 스윕 9개에서 평문과 반환 ID 순서·여섯 필드 값의 일치를 최초 실행 및 교차 7회 모두 단언했다. 2회 예열 뒤 7회 중앙값을 냈다. 아래는 **SQL 요청~응답 합계 / 전체 호출 ms**이며 모든 원시 실행, SQL 횟수, 후보 수, 반환 행 수, 인증 복호화 필드 수는 [`matrix.json`](matrix.json), [`sweep.json`](sweep.json)에 있다.

직접 후보 SQL의 `EXPLAIN (ANALYZE, BUFFERS)` 한 번씩에서 AND 4와 AND 6은 모두 새 다중 컬럼 GIN `seal_de9d32fbbc6ee7e5_gin`을 사용했다. 서버 실행 시간은 각각 8.93 ms, 12.36 ms였다. 원시 노드와 BUFFERS는 [`explain.json`](explain.json)에 있다. 이는 위 공개 API 중앙값과 다른 측정이다.

새 DDL의 읽기 정합성과 계획을 확인한 로컬 합성 fixture 결과다. 운영 쓰기 부하, 동시 마이그레이션, 다른 데이터 분포와 PostgreSQL 환경에서의 성능을 보장하지 않는다. 색인 구조만 바꾸었고 토큰 저장값은 같지만 이 실행에서 별도 공격 시뮬레이션은 하지 않았다.
