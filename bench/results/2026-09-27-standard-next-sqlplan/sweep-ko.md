# 256행 prefix 후속 검증: 적중 빈도와 AND 비용

2026-09-27 · 일회용 PostgreSQL `127.0.0.1:56439` (`.local/pg-test`). 기존 `bench_standard_next_100k`와 원본 `bench_realistic_100k`를 읽기만 했다. `sqlplan-and.ts`는 소유·포트 검증 후 그 일회용 DB에 `CREATE EXTENSION IF NOT EXISTS pgstattuple`을 실행해 GIN pending list를 측정했다. 원본 행, companion 행, 색인, 토큰은 수정하지 않았고 VACUUM·REINDEX도 실행하지 않았다.

## 부분검색 적중 빈도 스윕

원본 고객 주소 10만 행에서 실제로 등장하는 2~4글자 부분 문자열을 수집해 목표 적중 수에 가까운 검색어를 골랐다. `hits`는 원본 평문 `address_norm LIKE`의 전체 행 수로 다시 확인한 값이다. 마지막 `세종대로`는 기존 병적 계획을 재현하기 위한 기준점이다. 같은 검색어와 데이터, ID 오름차순 20행, 6개 필드 투영을 사용했다. 평문, 기본, 건너뜀을 2회 예열하고 각 경로를 교차 7회 측정한 중앙값이며, **모든 경로의 최초 실행과 7회 결과에서 ID 순서와 필드 값이 평문과 일치**했다. 모든 방식은 같은 공개 API 엔진을 거쳤고, 벤치 래퍼가 내부 후보 SQL만 이전 직접 경로 또는 prefix 크기별로 치환했다.

전체 호출 시간의 9개 최악값은 기본 직접/256/1024/2048/4096 순서로 **43.14/29.06/32.80/39.22/51.51ms**, 건너뜀은 **98.59/9.56/10.28/10.10/12.07ms**였다. 10행 적중 검색은 기본 토큰 오탐 때문에 170 후보를 7번의 SQL로 읽고 220개 필드를 인증한 뒤 10행을 반환했다. 이 사례에서는 prefix 크기가 커질수록 매번 불필요한 앞 구간을 다시 읽어 손해가 커진다. 건너뜀 경로는 같은 검색에서 후보 10행·SQL 1회·인증 필드 60개였다. 나머지 스윕 사례의 20행 페이지는 SQL 1회, 후보 27행, 인증 필드 127개였다. 희귀 검색의 다중 배치 동작은 기존 엔진의 페이지 채움 동작이며 이번 변경에서 생긴 것은 아니다.

**판단:** 이번 10만 행 분포와 실제 계획에서는 256행이 측정한 prefix 크기 중 최악값이 가장 작았다. 중간 적중(418~1,956행)에서도 기본 SQL의 최댓값은 2.77ms, 건너뜀은 3.88ms였다. 적중 빈도만으로 직접 경로의 비용을 예측할 수 없다. 적중 수가 비슷한 `ch`와 `세종대로`는 기본 직접 SQL이 각각 0.74ms와 37.46ms였다. 제시된 `sqrt(L×N)` 분기점은 근사 가설이며 이 fixture에서 약 1,414~1,643행으로 추정되지만, 1024/2048행 prefix의 실측 최악값은 256보다 컸다. 테이블 크기에 따라 prefix를 조정할 실측 근거는 현재 10만 행 한 규모뿐이라 없다. 따라서 제품의 256행을 유지하고 행 수 조회나 빈도 저장을 추가하지 않았다. 이는 다른 분포·크기에서의 최적값을 보장하지 않는다.

## AND 4/6: GIN pending list와 실행 계획

`pgstatginindex`가 기본·건너뜀 companion의 **12개 GIN 색인 모두에서 `pending_pages=0`, `pending_tuples=0`**을 보고했다. 모든 색인의 `reloptions`가 null이어서 `fastupdate` 별도 설정도 없다. companion 통계는 두 테이블 모두 10만 live tuple을 기록하고 있었고 적재 후 `ANALYZE` 이력이 있었다. 그러므로 이번 AND 비용을 pending list나 적재 후 VACUUM 부재로 돌릴 근거는 없다.

`EXPLAIN (ANALYZE, BUFFERS)` 원시 결과는 `and-diagnostics.json`이다. 기본 AND 4의 bitmap index는 이메일 `service` 약 26,759행(약 5~6ms)과 주소 `서울` 16,574행(약 2ms)을 읽고 bitmap AND를 만들었다. bitmap heap은 예상 1행/실제 62행이고, 약 4천 shared block을 읽으며 약 25ms를 썼다. 건너뜀 AND 4는 planner가 bitmap index 한 개에서 실제 26,759행을 읽어 약 18천 heap block에서 토큰을 재검사했으며 약 55ms였다. 기본 AND 6은 주소 16,574·메모 40,097·전화 18,998·이름 28,023행의 posting을 bitmap AND로 결합해 624행을 얻었다. bitmap index 네 개와 결합에 약 13ms, 624행 부모 조회에 약 10ms가 들었다. 건너뜀 AND 6도 같은 종류의 비용이 남았다. 이 시간은 각각 한 번의 EXPLAIN이며 7회 중앙값이 아니다.

긴 posting과 bitmap 결합·heap 재검사가 관측 원인이다. pending list가 0이므로 이 fixture에서 VACUUM·REINDEX를 해결책으로 제시하지 않는다. 새 저장 구조나 토큰 구성 변경 없이 이 비용을 제거할 근거가 없으므로 제품 SQL은 추가 수정하지 않았다. 실제 업데이트가 축적된 다른 DB의 pending list 상태는 이 측정으로 판단할 수 없다.

## 재검증과 한계

`matrix.ts`, `explain.ts`, `count.ts`를 같은 fixture에서 다시 실행하고 결과를 `matrix-followup.json`, `explain-followup.json`, `count-followup.json`에 별도로 보존했다. `matrix.ts`와 스윕은 반환 ID 순서와 필드 값의 평문 일치를 단언했다. `count` 1,770건은 여전히 SQL 1회이며 정확한 `number`를 반환했다. `rtk npm run build`, `rtk npm run check`, `rtk npm test`, `rtk npm run docs:check` 결과를 작업 종료 전 확인했다. 이 측정은 로컬 합성 fixture의 실행 결과이며 운영 성능 보장 또는 보안 인증이 아니다.
