# standard SQL 계획 이상치 후속 검증

2026-09-27 · 일회용 PostgreSQL `127.0.0.1:56439` (`.local/pg-test`) · 기존 `bench_standard_next_100k`만 읽음. 같은 10만 고객 데이터와 질의, 평문/기본/건너뛴 조각 경로를 각각 2회 예열하고 교차 7회 측정한 중앙값이다. 모든 측정 실행에서 반환 ID 순서와 선택한 6개 필드가 평문과 일치했다. 이 수치는 로컬 fixture의 결과이며 운영 성능 보장이 아니다.

## 원인과 선택

`EXPLAIN (ANALYZE, BUFFERS)`에서 companion 배열 조건의 행 수 과소추정과 bitmap 후보 전체 읽기·정렬을 확인했다. `세종대로` 기본은 예상 455행/실제 16,574행, 건너뜀은 예상 13행/실제 16,574행이다. `endsWith` 건너뜀은 예상 82행/실제 26,598행, 단어 경계는 기본 예상 181행/실제 29,843행이었다. AND 4는 기본 bitmap heap 예상 1행/실제 62행, AND 6은 예상 40행/실제 624행이다. 긴 메모 구절은 예상 1행/실제 2,440행이었다. 독립 선택도 가정이 원인이라는 것은 이 실행 계획과 부합하지만 PostgreSQL 내부 추정식 자체를 증명한 것은 아니다.

ID 오름차순의 일반 부분검색 페이지는 companion 기본키 순서로 최대 256행의 **토큰 열만** 먼저 읽고, 그 안에서 요청 후보 수를 채우면 즉시 멈춘다. 모자라면 같은 SQL 안에서 기존 GIN 후보 경로를 실행한다. 이 구조는 한 쪽 계획을 고정하지 않고 각 질의의 실제 첫 구간 결과로 분기한다. 정확 일치는 기존 B-tree 경로를 유지한다. 공개 필터·다른 정렬·고급 질의와 큰 count 배치도 기존 직접 경로를 유지한다. DB 스키마, 토큰, 빈도 저장, 공개 API는 바꾸지 않았다.

## 검색 전후 (ms, 중앙값)

각 칸은 `전체 / SQL 요청~응답`이다. 전 수치는 기존 [10만 행 결과](../2026-09-27-standard-next/report-ko.md), 후 수치는 이 폴더의 `matrix.json`이다. 후보/반환/인증 필드 수는 아래 설명과 원시 JSON에 있다.

| 케이스 | 평문 전→후 | 기본 전→후 | 건너뜀 전→후 |
|---|---:|---:|---:|
| 주소 `세종대로` | 0.92/0.91 → 0.87/0.86 | 39.08/33.29 → 7.58/1.37 | 92.18/85.84 → 7.99/1.51 |
| 이메일 접미 | 0.67/0.66 → 0.68/0.65 | 6.64/1.00 → 7.67/1.27 | 113.81/108.02 → 7.50/1.46 |
| AND 4 | 60.03/60.00 → 63.08/63.05 | 28.10/21.47 → 30.58/23.75 | 60.38/53.86 → 63.44/56.50 |
| AND 6 | 2.67/2.64 → 2.73/2.70 | 22.76/14.79 → 22.27/14.26 | 25.84/17.57 → 24.73/17.00 |
| 긴 메모 구절 | 82.36/82.33 → 77.96/77.93 | 16.76/10.46 → 10.91/4.29 | 17.36/11.01 → 11.67/4.86 |
| 띄어쓰기 구분 | 291.80/226.54 → 295.94/234.06 | 130.26/124.02 → 7.55/1.45 | 142.96/136.97 → 7.53/1.48 |
| 희귀 부분 | 74.30/74.28 → 77.92/77.90 | 6.90/1.33 → 7.97/1.74 | 6.97/1.31 → 7.52/1.79 |
| 부분 0건 | 88.24/88.22 → 79.30/79.29 | 1.28/0.61 → 2.00/1.25 | 1.08/0.49 → 2.11/1.25 |
| 정확 일치 1건 | 0.36/0.35 → 0.45/0.44 | 1.14/0.42 → 1.44/0.55 | 1.19/0.45 → 1.44/0.57 |

위 20행 페이지는 모두 암호 경로에서 SQL 1회, 후보 27행, 반환 20행이었다. 단건은 후보/반환 1행, 부분 0건은 후보/반환 0행이며, 정확 일치 1건은 인증 필드 6개였다. 20행 부분검색의 인증 필드는 대개 127개이고, AND 4/6은 각각 148/162개다. 각 지표는 개별 7회 중앙값이어서 행 안의 중앙값끼리 합산하지 않는다.

독립 `explain-compare.json`은 기본/건너뜀 각각 기존 SQL과 새 후보 SQL의 서버 실행 계획을 보존한다. 주소 기본의 서버 실행 시간은 39.90→0.51ms였고 새 계획의 GIN fallback은 실행되지 않았다. 긴 구절은 32.92→3.51ms였지만 256행 안에서 후보를 채우지 못해 GIN fallback이 실행됐다. AND 4/6 역시 fallback이 필요해 SQL 비용이 남는다. 부분 0건은 prefix 탐색 비용 때문에 SQL 0.61→1.25ms로 늘었다. 희귀·0건 경로의 절대 시간은 여전히 수 ms 이하지만 그 회귀를 감추지 않는다. `C` 로캘에서 한글 평문 `LIKE`가 전체 스캔되는 비교 한계도 이전과 같다.

## count

공개 반환 타입 `number`와 후보 상한 초과 오류를 유지하면서 내부 후보 배치를 최대 2,000행으로 키웠다. `count.json`은 같은 2회 예열·교차 7회 중앙값이다. 중간 정확 일치 1,770건의 기본 경로는 SQL **9→1회**, 전체 108.52→113.30ms, SQL 합계 22.58→24.34ms였다. 건너뜀은 전체 114.36→114.70ms였다. SQL 왕복은 줄었으나 1,770개 필드의 인증 복호화가 남아 전체 시간은 개선되지 않았다. 희귀 101건과 0건은 여전히 각 SQL 1회이고 평문 count와 값이 같았다.

## 검증과 한계

`matrix.ts`, `explain.ts`, `count.ts`, 추가 `sqlplan-probe.ts`를 실행했다. 제품 `build`, `check`, `test`(12/12), `docs:check`가 통과했다. 관리형 쓰기·부분 수정·삭제·커서 검증은 기존 통합 테스트가 통과했고, 저장 구조는 그대로다. 이 후속은 토큰 형식이나 누출 경계를 변경하지 않는다. AND 4/6의 큰 bitmap 작업, 희귀·0건의 작은 SQL 회귀, 악의적 DB의 검색 누락 가능성은 남는다.
