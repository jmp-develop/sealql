# G0: 부모 테이블 토큰 배치 측정

2026-09-27. 일회용 PostgreSQL `127.0.0.1:56439`에서 `assertDisposable`과 포트를 확인한 뒤 측정했다. 기존 `bench_standard_next_100k.customers_skip_product_multi`의 암호문 10만 행과 companion의 토큰 배열을 같은 행 식별값으로 결합해 `g0_parent_tokens`를 만들었다. 원본과 `bench_realistic_100k` 평문은 읽기만 했다. 파생 테이블 네 개는 측정 뒤 모두 삭제했다. [원시 측정값](measurements.json)과 [재현 스크립트](../../standard-next/g0-token-placement.ts)에 각 실행값과 SQL이 있다.

모든 시간은 Node `pg`의 SQL 요청 시작부터 응답까지의 클라이언트 경과 시간(ms)이다. 각 경로를 2회 예열하고 순서를 교차한 7회 측정의 중앙값이다. 같은 로컬 데이터와 scope를 썼고, 21개 검색 모두 두 저장 구조의 후보 ID 순서가 일치했다. 후보에 포함되어야 할 평문 첫 20개 적중 ID도 확인했다. 이는 재확인 후 전체 페이지 실행의 성능이나 운영 성능 보장이 아니다.

## 게이트 판정: 초과

| 20행 일반 조회 | 현재 부모+companion | 부모 토큰 | 차이 | G0 기준 |
|---|---:|---:|---:|---|
| `select *` | 0.5122 | 3.6671 | +3.1549 ms, +616.0% | **초과** |
| 토큰 칸 제외 선택 | 0.4165 | 0.4108 | −0.0057 ms, −1.4% | 이 측정에서는 이내 |

판정식은 `부모 토큰 − 현재 > 0.3ms` **또는** `부모 토큰 / 현재 − 1 > 20%`이다. `select *`는 두 기준 모두 넘는다. 토큰 배열 열을 전송·역직렬화하는 비용이 포함된 SQL 요청~응답 시간이다. 이 측정만으로 서버 실행 시간과 전송 비용을 따로 나누지는 못한다. 설계 계획의 G0 기준에 따라 보고했으며, 저장 구조는 별도 설계 재검증에서 결정했다([결정 008](../../../docs/decisions/008-drizzle-integration.md)).

## 쓰기 SQL: 각 연산 1,000건

| 1,000행 합계 | 현재 부모+companion | 부모 토큰 |
|---|---:|---:|
| insert | 629.55 | 445.16 |
| 메모 부분 update | 578.66 | 358.45 |
| delete | 445.06 | 235.20 |

같은 기존 1,000행의 암호문과 토큰을 별도 빈 파생 테이블에 삽입하고, 메모의 암호문·정확/부분 토큰 두 열만 부분 update한 뒤 삭제했다. update에는 각 행의 기존 값을 다시 썼으므로 **변경된 평문을 다시 암호화하는 관리형 쓰기 검증은 아니다**. 현재 구조는 부모와 companion에 각각 SQL 문을 보냈고, 부모 토큰 구조는 한 문장을 보냈다. 합계에는 해당 SQL 요청~응답을 모두 더했으며 암호화와 토큰 생성, 애플리케이션 트랜잭션 비용은 포함하지 않았다. 따라서 제품 쓰기 처리량으로 해석할 수 없다.

## 저장 공간

| 구성 | 테이블 MB | 색인 MB | 합계 MB |
|---|---:|---:|---:|
| 현재 부모 | 37.63 | 4.77 | 42.45 |
| 현재 companion | 195.31 | 95.23 | 290.63 |
| **현재 합계** | **232.94** | **100.00** | **333.08** |
| 부모 토큰 | 195.50 | 95.28 | 290.84 |

MB는 `pg_relation_size`, `pg_indexes_size`, `pg_total_relation_size`의 byte를 1,048,576으로 나눈 값이다. 부모 토큰 파생 테이블에는 부분 검색 열 전체를 묶은 GIN 하나, 각 정확 일치 열의 `(scope_id, (tokens)[1], id)` B-tree, 기본키를 만들고 `ANALYZE`했다. 현재 구조는 fixture의 제품 다중 컬럼 GIN과 정확 일치 B-tree를 그대로 사용했다. 숫자는 현재 일회용 DB의 물리적 크기이며 VACUUM 상태 등 다른 환경에 일반화할 수 없다.
