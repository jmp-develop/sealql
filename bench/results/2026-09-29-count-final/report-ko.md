# count를 DB 안에서 정확히: 최종 증거 보고 (2026-09-28/29)

목적: "암호화 필드의 count를 앱 복호화 없이 DB 안에서 정확히 낸다"는 연구의 결과를 남겨, 같은 시도를 되풀이하지 않게 한다. 이 문서는 새 측정을 하지 않고 이미 나온 보고를 한곳에 정리한 것이다. 비교 기준은 언제나 **평문 = 1배**다. 측정하지 않은 값은 "미측정", 계산·외삽한 값은 "추정"으로 적는다. 제품 코드는 바뀌지 않았다.

이름(이 문서에서만 이 뜻으로 쓴다).

| 이름 | 뜻 |
|---|---|
| 평문 | 정규화 평문 칸 + 칸별 B-tree + trigram GIN (같은 데이터·같은 질의의 기준) |
| A 지금 방식 | 현재 제품: 16비트 조각 토큰으로 후보를 고르고, 앱이 후보를 복호화해 재확인 |
| B 행별 도장 | A의 후보 토큰 + 행마다 무작위 salt로 만든 8바이트 판정 도장(부분 문자열 2–8글자·접두·접미 전부) |
| 개선 B | 위치 도장: 2글자 창마다 (등장 순번을 넣은 도장 + 평문 위치). 창 2글자, 긴 질의는 창을 이어 붙여 판정 |
| 최종안 | 개선 B + 값 종류가 적은 정확 일치 칸의 거친 번호 2비트(실험은 회사명 1칸만 2비트, 나머지 5칸은 16비트 유지) |
| C MongoDB 방식 | MongoDB QE를 PostgreSQL로 옮긴 것: 등장별 꼬리표 + 등장 수 장부 |
| 실제 MongoDB | MongoDB 8.2 Community Queryable Encryption(substringPreview) 실물 |
| D 결합안 | 16비트 후보 토큰 + 행 nonce + 8바이트 검증값(조각 2..10글자) |
| 꼬리표안 | 개선 B + 회사명만 등장별 꼬리표·장부 |
| 꼬리표안-개선 | 꼬리표안과 저장물이 같고 질의 방식만 바꾼 것(장부 등장 수를 먼저 읽고 경로 선택) |

주의: 2026-09-28 초기 보고(`../2026-09-28-count-test/summary-ko.md`)는 "A = 행별 검증, B = 결합안"이라는 다른 이름을 썼다. 그 문서의 A는 이 문서의 B에 해당하고, 그 문서의 B는 이 문서의 D에 해당한다. 통합 비교 보고(`../2026-09-28-unified/m1-astra-report-ko.md`)도 같은 점을 적어 두었다.

## 2. 테스트 환경과 한계

| 항목 | 내용 |
|---|---|
| DB | 일회용 PostgreSQL 18.4 (`127.0.0.1:56439`, work_mem 4MB, max_parallel_workers_per_gather 2, lc_collate C). 운영 DB·5432 미접속. 모든 스크립트가 일회용 확인(`assertDisposable`)과 포트 확인 후 실행 |
| 데이터 | 원본 `bench_realistic_100k`는 읽기만 하고, `research_u` 스키마에 파생: 고객 100,000행(name·phone·address·memo·email·company 6칸) + 티켓 100,000행(memo). 값은 원본의 정규화 값(`*_norm`). scope 1개, 대상 = 전체 100,000행. 새 데이터 생성 없음 |
| 최종안 측정 범위 | 고객 10만 행 6칸만(티켓 미적재). 통합 비교의 B는 고객 10만 행만 적재, 티켓 B·JOIN은 미측정 |
| 평문 색인 | 6칸 각 정규화 필드 B-tree + trigram GIN. **로캘이 C라 한글 trigram이 비어 한글 부분 일치 평문은 전체 스캔**이다 |
| 암호 경로 색인 | A: 정확 일치 B-tree(scope, 토큰[1], row_id) 칸마다 + 부분 검색 다중 컬럼 GIN 1개. B·개선 B·최종안: 칸별 정확 일치 B-tree(scope, ce[1], id) + 6칸 후보 GIN(`cs_*`) + PK. 색인 정의 원문은 `.local/research/task4-m1-astra.md`의 pg_indexes 목록, `../2026-09-29-task4/metadata.json` |
| 반복 규칙 | 첫 실행 별도, 예열 2회 + 경로 순서를 돌린 교차 7회, 지표별 중앙값. 매 실행 count·정렬 ID·6칸 값을 평문과 단언. OS 캐시는 비우지 않았으므로 첫 실행을 cold라 부르지 않는다 |
| A의 반복 축소 | 최종안 52조건 측정에서 A는 뒤쪽 79개 조건·연산이 첫1회 + 예열1 + 교차3(표본 3), 앞쪽 25개 count는 예열2 + 교차7(표본 7). 평문·B·개선 B·최종안은 전부 예열2 + 교차7. 꼬리표안 측정(과제 7)은 A를 뺐다 |
| 지표 | SQL 요청~응답(서버 실행만이 아님)과 전체 시간(토큰 준비, 복호화 포함)을 따로 적는다. 두 중앙값은 합산되지 않을 수 있다 |
| C 로캘 주의 | 한글 부분 일치 평문의 배수(1 미만 포함)는 성능 주장에 쓰지 않는다. 아래 표의 해당 배수는 참고이며 "암호화 검색이 평문보다 빠르다"는 결론에 쓰지 않는다 |
| 세션 분할 | 52조건 측정은 물리 세션 3개(PID 63704 → 48748 → 42632)로 나뉘었다. 각 조건의 경로들은 같은 연결에서 교차했다. 유휴 만료로 연결이 바뀐 조건은 보정 후 재측정했다(보정 전 자료는 `../2026-09-29-task4/before-session-repair.json`) |
| 세션마다 다른 평문 기준 | 같은 fixture라도 세션마다 평문 시간이 다르다(예: 회사명 count 평문 2.8–3.0 ms 대 7.7–8.2 ms). 배수는 **같은 표 안에서만** 비교한다 |
| 외부 부하 겹침 | 500·1,000자 긴 값 측정과 MongoDB 적재는 시간이 겹쳤다. MongoDB 적재 시간도 PostgreSQL 측정과 겹친 구간이 있어 참고값이다 |
| 규모 한계 | 고객 10만 행·scope 1개. 다중 scope·1억 행 규모의 최종안, 운영 로캘의 평문 성능은 미측정 |

## 3. 저장 구조 비교 (한 값 예: 메모 "서비스 상담 요청")

정규화(NFC, 전각→반각, 소문자, 공백 제거) 후 "서비스상담요청"(7글자). 해시는 `h(...)`로 표기. 출처: `.local/research/fact-m1-fable.md`(A, B), `fact-m2-fable.md`(C, D, 실제 MongoDB), `task1b-m1-astra.md`(개선 B), `task7-m1-astra.md`, `task8-m1-astra.md`(꼬리표안). 구현마다 salt 길이(8 B 또는 16 B) 등이 다르다.

| 방식 | 본문 | 검색용 저장 | 예 "서비스상담요청"에서 생기는 것 | 검색 시 DB가 하는 일 | 상태(장부) |
|---|---|---|---|---|---|
| 평문 | 평문 그대로 | B-tree + trigram GIN | (한글은 C 로캘이라 GIN이 비어 전체 스캔) | 비교 | 없음 |
| A 지금 방식 | AES-256-GCM 암호문(평문+29 B, 행·칸·scope 결속) | 16비트 절단 조각 토큰 bigint[] (`scope32 ‖ h16(조각)`) | 인접 2글자 6 + 시작·끝 2 + 건너뜀 5 + 단어 경계 ≤6 = 약 19개, 정확 일치 토큰 1개 | GIN으로 후보만 고름. **앱이 후보를 복호화해 재확인** | 없음 |
| B 행별 도장 | 같음 | A의 후보 토큰 + 칸별 salt + 판정 도장 bigint[] | 2..8글자 모든 부분 문자열 21 + 접두 6 + 접미 6 = 33개 도장 `h(k_조각 ‖ salt)[0:8]` + 정확 일치 도장 1 | 후보마다 `sha256(k_조각 ‖ salt)`를 계산해 도장 배열에 있는지 확인 후 `count(*)`. 8글자 초과는 DB 판정 불가 | 없음 |
| 개선 B | 같음 | A의 후보 토큰 + salt 16 B + (도장, 평문 위치) 배열 | 2글자 창 6개: 도장 `h(k_조각 ‖ salt ‖ 등장 순번 i)[0:8]` 6개 + 위치 0..5(평문). 같은 조각이 반복되면 i=1,2,…로 도장이 다름 | 질의를 2글자 창들로 덮고 같은 시작 위치에서 창들의 상대 위치가 맞는지 확인. 도장이 없으면 멈춤(후보당 해시 약 2×창 수) | 없음 |
| 최종안 | 같음 | 개선 B 그대로, 단 **회사명 정확 일치 후보 번호만 16비트 → 상위 2비트** | 회사 "서울서비스 담당" → 2비트 번호(4개 중 하나). 다른 5칸 정확 일치는 16비트 유지 | 개선 B와 같고, 회사명은 2비트 후보를 정확 일치 도장으로 걸러 확정 | 없음 |
| C MongoDB 방식 | 같음 | 꼬리표 표 `(tag8, id)` B-tree + 장부 `esc(h(값토큰,'esc'), n)` | 조각(2..10글자) 21개마다 꼬리표 `h(값토큰(조각), 등장 순번)` 1행 + 장부 21행 upsert | DB가 장부에서 등장 수 n을 읽고 꼬리표 n개를 만들어 색인에서 찾음. AND는 집합 교집합 | 있음(쓰기마다 갱신, 삭제해도 줄지 않음) |
| 실제 MongoDB | 값 봉투(안쪽 AEAD + 조각마다 96 B 검증 블록) | `__safeContent__` 꼬리표 배열 + 보조 컬렉션 ESC·ECOC | 메모는 길이 2..10 모든 부분 문자열마다 꼬리표·ESC·ECOC 1건씩(6필드 문서당 평균 518.7건) | 서버가 ESC에서 등장 수를 찾아 꼬리표를 만들고 `$in`으로 찾음 | 있음 |
| D 결합안 | 같음 | `cand int[]`(16비트 후보) + 행 nonce 16 B + `chks bigint[]`(`h64(값토큰(조각), nonce)`) | 조각 2..10글자 21개 → 후보 21개 + 검증값 21개(통합 비교에서는 6칸을 한 배열에 넣은 구성) | GIN 후보 → 후보 행마다 `hmac(nonce, 값토큰)` 계산·비교. 10자 초과·공백 포함 질의는 앱 복호화 확정 | 없음 |
| 꼬리표안 | 같음 | 개선 B(회사명 정확 후보·도장 제외) + 회사명 꼬리표 `(tag8, id)` + 장부 `(tok, n)` | 회사명만 등장별 꼬리표 1행 + 장부 1행. 다른 칸은 개선 B | 회사명은 C처럼 장부 n → 꼬리표 n개 생성 | 있음(회사명 칸) |
| 꼬리표안-개선 | 같음 | **저장물 동일**(전후 스키마 동일 확인) | 같음 | 장부 n을 먼저 읽는다. n=0이면 회사명 분기 거짓, n>2048이고 AND·목록이면 꼬리표 전개를 생략하고 위치 도장으로 확인, 그 밖은 집합 조인 | 있음 |
