# Standard 코어 10만 행 전수 검증

2026-09-27 · 일회용 PostgreSQL `127.0.0.1:56439` (`.local/pg-test`) · 고정 키 제품 코드 기준. **정확성 검사 통과.** 이 결과는 로컬 합성 fixture의 측정이며 운영 성능 보장이나 보안 인증이 아니다.

## 적재와 정확성

| 항목 | 고객 | 티켓 |
|---|---:|---:|
| 원본 평문 행 / 새 기본 행 / 건너뛴 조각 행 | 100,000 / 100,000 / 100,000 | 100,000 / 100,000 / 100,000 |
| 인증 복호화 후 평문과 대조한 필드 | 600,000 | 600,000 |
| 불일치 / 건너뛴 조각 변형의 암호문 차이 | 0 / 0 | 0 / 0 |

| 배치 적재 처리량 | 128.4행/초 | 133.0행/초 |

기존 `bench_realistic_100k`의 고객·티켓과 정책·색인 테이블은 읽기만 했다. 새 `bench_standard_next_100k` 스키마의 두 변형에 공개 DDL을 적용했다. 기본 변형은 제품 `Sealer.seal`, `searchPieces`, `searchTokens`를 사용해 모든 원본 `*_plain` 필드를 재암호화하고 100행씩 부모·companion에 넣었다. 건너뛴 조각 변형은 동일 모델·코덱의 인증 암호문을 복사하고 별도 프로필의 토큰을 계산했다. 두 변형의 고객·티켓 각 10만 행을 확인했으며, 기본 변형 120만 필드를 전수 인증 복호화해 평문과 대조했다. 적재 처리량은 두 변형의 토큰 계산·쓰기와 배치 SQL을 포함하지만 사후 색인 생성 시간은 포함하지 않는다. 관리형 단건 쓰기 처리량으로 해석할 수 없다.

## 같은 데이터·질의의 검색 측정

평문, 이전 제품 알고리즘(코드 삭제로 재현 불가, 결과만 보존), 새 기본, 건너뛴 조각 켬을 같은 원본 ID·scope, 정렬(`id` 오름차순), LIMIT, 6개 필드 투영으로 비교했다. 이전 코드는 별도 복사본에서 빌드했고 소유 검사를 현재 일회용 클러스터 경로에 맞춘 뒤 같은 세션에서 실행했다. 각 경로를 2회 예열하고 순서를 번갈아 7회 측정한 중앙값이다. **모든 암호 경로의 최초 실행과 7회 측정에서 반환 ID 순서와 6개 필드 전체가 평문과 같았다.** 표의 괄호는 새 기본의 SQL 요청~응답 시간이며, 전체 시간의 일부다.

기본의 대표 20행 페이지는 약 6–7ms, OR 3개는 2.23ms였다. 주소 중간·AND 4/6과 띄어쓰기 구분 검색에는 SQL 비용이 크게 남았다. 이전 제품은 단건·0건에도 정책 SQL을 포함한 3–5회 SQL을 썼고, 새 기본은 표의 모든 케이스에서 페이지당 1회였다. 후보 수는 DB에서 받은 행, 인증 필드는 실제 `Sealer.open` 호출 수다. 각 지표는 각각 7회 중앙값이므로 한 행의 중앙값끼리 반드시 합산되지는 않는다.

이 DB의 로캘은 `C`다. 한글 `LIKE`는 `pg_trgm` 인덱스가 없어 전체 스캔이 된다. 띄어쓰기 구분 평문 경로는 원본의 공백 제거 정규화 열로 후보를 읽고 JavaScript에서 단어 공백을 다시 확인했으므로 SQL 시간 외의 필터 비용도 포함한다. 희귀·긴 메모, 0건 부분 검색, 띄어쓰기 구분 행에서 평문보다 빠른 수치를 일반적인 성능 배율로 주장하지 않는다.

### 단계 분해와 실행 계획

| 케이스 | 준비 ms | 토큰 ms | 후보 SQL ms | 조건 인증·재확인 ms | 선택 필드 인증 ms |
|---|---:|---:|---:|---:|---:|
| 흔한 정확 일치 | 0.015 | 0.192 | 1.226 | 0.970 | 2.784 |
| 주소 중간 | 0.014 | 0.229 | 14.669 | 0.954 | 2.490 |
| OR 3 | 0.011 | 0.313 | 0.904 | 0.218 | 0.231 |

이 분해는 제품 컴파일러·SQL 어댑터·인증 복호화기·재확인 함수를 단일 후보 배치로 순차 실행한 별도 7회 중앙값이다. 실제 엔진 호출의 정확한 내부 trace가 아니므로 위 검색 표의 SQL/전체 시간과 직접 합산하거나 대응시키지 않는다. 실제 호출의 누적 `open` 시간은 병렬 호출의 합계라 wall time보다 클 수 있으며 원시 결과에 별도 기록했다.

건너뛴 조각을 켠 경우 GIN 배열이 커지고 PostgreSQL 계획이 바뀌었다. 동일한 27행 LIMIT의 `EXPLAIN ANALYZE`에서 주소 중간 검색은 기본 38.3ms(merge join) 대 건너뜀 87.9ms(16,574 후보 bitmap + sort), 이메일 접미는 기본 0.4ms(nested loop) 대 건너뜀 123.6ms(26,598 후보 bitmap + sort)였다. 이 fixture에서 건너뛴 조각은 검색 후보 정확성 이득보다 SQL 계획 비용이 컸다. **기본 꺼짐을 유지할 근거**이며, 다른 분포나 통계 상태에서의 판단은 별도 측정이 필요하다.

## 카운트·JOIN·혼합 필터·쓰기

카운트는 세 케이스 모두 평문 `COUNT`와 정확히 같고 반환 타입은 `number`였다. 후보 상한 110,000으로 호출했다.

| 카운트 | 값 | 평문 ms | 새 기본 ms (SQL 횟수·시간·후보) | 건너뜀 ms |
|---|---:|---:|---:|---:|
| 중간 정확 일치 | 1,770 | 0.91 | 108.52 (9회·22.58ms·1,770) | 114.36 |
| 희귀 부분 | 101 | 19.32 | 7.19 (1회·1.33ms·101) | 6.93 |
| 0건 | 0 | 21.47 | 1.28 (1회·0.65ms·0) | 1.28 |

| JOIN/혼합 | 행 | 평문 ms | 이전 제품 ms | 새 기본 ms (SQL) | 건너뜀 ms |
|---|---:|---:|---:|---:|---:|
| 티켓⋈고객, 희귀 메모 양쪽 | 20 | 66.23 | 154.3 | 29.00 (3.18) | 27.86 |
| 티켓 메모+고객 회사 | 20 | 1.47 | 147.9 | 26.43 (2.25) | 26.18 |
| 티켓 0건 | 0 | 67.48 | 2.5 | 2.96 (1.54) | 2.65 |
| 평문 필터 24 + 암호 필터 6 | 20 | 130.66 | — | 43.62 (29.95) | 47.26 |

JOIN과 혼합 경로는 원본과 같은 조인 키·평문 필터를 사용하고 제품 토큰 함수와 `decryptRows`로 후보 전 필드를 인증 복호화한 뒤 재확인했다. JOIN은 SQL 1회·후보 40행·인증 필드 480개, 혼합은 SQL 1회·후보 40행·인증 필드 240개였다. ID 순서와 양쪽 6개 필드, 혼합의 6개 필드 값이 모두 평문과 같았다. JOIN의 이전 수치는 같은 세션에서 실행한 옛 `join-mixed.ts`의 `current` 경로다. 혼합의 옛 스크립트는 이전 제품 `current` 경로를 측정하지 않고 실험적 `fast-v2`만 측정하므로 비교 칸을 비웠다(참고: 그 경로 72.6ms). 새 JOIN/혼합 스크립트는 `searchWithQuery` 자체의 성능을 대변하지 않는 raw SQL + 제품 복호화 경로다.

| 단건 공개 API (각 1,000건) | 중앙값 ms | 총 시간 ms | 정합성 |
|---|---:|---:|---|
| insert | 4.82 | 4,942.67 | 새 토큰 생성 |
| memo 부분 update | 1.26 | 1,321.64 | 새 값 검색 1,000건, 옛 값에서 해당 ID 0건 |
| delete | 0.39 | 426.76 | 새 값 검색 0건 |

이는 별도 새 `crud_probe` 테이블의 순차 단건 로컬 측정이다. 동시 쓰기·WAL 비용·운영 환경 처리량은 측정하지 않았다. Companion 크기(부모 제외, 고객 10만 행)는 이전 163.9MiB, 새 기본 201.4MiB, 건너뜀 290.5MiB였다. 이전 부모는 평문·다른 실험 암호문을 함께 보유하므로 부모 크기는 직접 비교하지 않는다.

## 기계적 공격 시뮬레이션

실제 이전/새 companion의 메모 토큰 배열에서 동일한 피해 20,000행, 참고 20,000행, 알려진 원문 5%(1,000행), 시드 99를 사용했다. 빈도 순위와 알려진 행의 토큰·조각 행집합 일치(count attack)를 키 없이 계산했고, 별도 평가기에 키를 써 정답만 채점했다. 이전 프로필의 토큰 열은 알려진 한 행의 22개 조각·토큰이 22개 모두 일치함을 기계적으로 확인했다.

| 실제 DB 토큰 | 빈도 공격 조각 등장 해독 | 5% 원문 공격 조각 등장 해독 | 모르는 행의 80%+ 해독 |
|---|---:|---:|---:|
| 이전 인접 조각 | 12.13% | 59.75% | 19.20% |
| 새 인접+경계 | 7.80% | 45.75% | 19.20% |
| 새 인접+경계+건너뜀 | 4.81% | 42.88% | 18.67% |

독립된 공개 리뷰 말뭉치 20,000/20,000행에서는 새 기본의 빈도/5% 원문 공격 해독률이 8.50%/54.84%, 건너뜀은 6.08%/35.04%였다. 건너뜀 조각 중 20.29%가 알려진 행 공격으로 해독됐고, 그 해독 조각의 32.26%는 이미 해독한 인접 조각의 `ab·bc → a_c` 경로와 일치했다. 이는 조각 간 일관성을 이용할 수 있음을 확인한 기계적 하한이며, 미해독 토큰까지 확장한 복원 공격은 수행하지 않았다. 합성 fixture는 템플릿 반복이 많고 공격자 참고자료도 같은 원천의 다른 행이므로 자연어 누출률로 일반화하지 않는다. 쿼리 관찰·다중 스냅샷·형식 추론·앱 키 탈취 공격은 이번 검증 범위 밖이다.

## 원시 증거와 한계

이 폴더의 `load.json`, `verify-customers.json`, `verify-tickets.json`, `old-matrix.json`, `matrix.json`, `stages.json`, `count.json`, `join.json`, `old-join-mixed.ndjson`, `mixed.json`, `crud.json`, `storage.json`, `explain.json`, `db-attack.json`, `token-attack.json`이 원시 결과다. 재현 스크립트와 순서는 [`bench/standard-next/README.md`](../../standard-next/README.md)에 있다.

검색 결과 누락은 이 fixture와 실행한 케이스에서 0건이었다. 임의 데이터 전체에 대한 완전성 증명은 아니며, 악의적인 DB가 결과를 누락하는 위협은 남는다. 필드 범위 검색·암호화 필드 집계는 지원되지 않는다. 건너뛴 조각을 켠 대규모 쓰기, 병행 갱신, 운영 PostgreSQL에서의 성능은 측정하지 않았다.
