# v2 불투명 locator·암호화 posting page의 블라인드 관찰 평가

## 범위와 절차

대상은 로컬 합성 데이터의 단일 정적 관찰자 뷰다. 애플리케이션 키, 보호 필드 평문·정규화 열, 합성 seed, oracle label은 추론 전에 사용하지 않았다. 평가자가 만든 `bench/results/metadata-observer-v2.json`에서 공개 행 10,000개와 locator/blob 표본 1,000개를 `observer-v2-frozen.json`으로 복사했다. 복사본 SHA-256은 `1cdac2bbaf766ef6e61803e3873c226578a2389341606c1075fc67cf8e2ed520`이다. 원본이 작업 중 1,000행에서 10,000행으로 바뀌었으므로 모든 아래 분석과 예측은 이 고정 복사본만 사용한다. 별도 oracle 채점은 예측 고정 후 수행한다.

## 공개 형식에서 확인한 누출

연구용 v2는 `(scope, field, bigram, kind, ordinal)`별 HMAC-SHA256 locator를 만들며, 암호화 manifest에 page 수와 posting 수를, AES-GCM page에 정렬된 UUID 목록을 담는다. 테이블의 공개 열은 `locator bytea`와 `blob bytea`뿐이고 삽입 순서는 섞였다. 따라서 키 없는 정적 뷰에서 locator와 고객 행·검색 조각을 직접 결합하는 공개 키가 없다. Blob 길이로 page의 항목 수 등 전역 분포는 새며, 고객 필드 암호문의 길이와 공개 열은 별도의 행별 단서다. 이는 정적 단일 스냅샷의 구조 판단이며 질의 로그·WAL·여러 시점의 갱신 추적까지 포함하지 않는다.

## 관찰·예측·채점

관찰자 파일의 고객 열은 `id`, `scope_id`, `revision`과 여섯 보호 필드별 기존/신규 암호문 byte 길이다. 이 표본의 두 길이는 각 행·필드에서 전부 같았고, scope/revision도 전부 같았다. 길이에서 33B의 암호문 부가분을 빼면 평문 UTF-8 byte 길이가 나온다. 행별 길이 조합은 2,269종이며, 그중 1,111행은 이 10,000행 표본 안에서 유일하다. 가장 큰 조합은 500행, 행 기준 중앙 조합 크기는 11행이다. 전화 길이는 전부 12B였고, 필드별 길이 종류는 이름 3·전화 1·주소 15·메모 12·이메일 7·회사 10개였다. 길이 조합의 표본 엔트로피는 9.581비트다. 이 수치는 **구별 가능성**이지 정확한 값 복원률이 아니다. 고유 `id`는 이미 공개되어 있으므로 이를 길이 조합의 익명성 수치에 끼워 넣지 않았다.

1,000개 locator/blob 표본은 locator 순서의 앞부분이며 임의 표본이 아니다. 공개 형식상 UUID 문자열 배열 page의 blob 길이는 `29 + 39n` byte다(12B nonce + 16B tag + JSON 배열의 `39n+1`B). 이 식과 길이로 926개를 page형으로 분류해 그중 859개는 128건짜리 가득 찬 page, 67개는 일부만 찬 page로 읽힌다. 나머지 74개의 길이는 51~56B로 manifest형이다. page형에서 계산되는 UUID 항목은 합계 113,765개지만, UUID 자체와 대응 필드·검색 조각은 암호화되어 보이지 않는다. 이 표본만으로 전체 색인 빈도를 대표시킬 수 없다.

`freeze-v2-guesses.py`는 고정 관찰자의 공개 ID와 필드 길이만으로 범용 한국어/전화/이메일 템플릿에 숫자를 채운 **정확한 문자열 추측**을 모든 행의 여섯 필드에 기록했다. 보호 데이터·합성 seed·검색어 목록에서 어휘를 추출하지 않았다. `v2-predictions-frozen.jsonl`에는 `{id,name,phone,address,memo,email,company}` 10,000개가 있으며 SHA-256은 `d892b4404663f1a0adaed60563cd0d8f17c063e62a58b515751cdec4820a52d2`다. 생성 시간은 약 205ms였다. 이 추측은 길이만으로 맞출 수 있는지가 아니라 **공개 정보만 가진 공격자의 구체적인 정확값 추측**을 시험한다. 템플릿 선택의 근거가 약하므로 낮은 적중률이 강한 공격의 부재를 증명하지는 않는다.

독립 seed `blind-independent-seed-20260925`로 별도 일반 문구를 생성한 두 번째 정확값 추측도 `v2-independent-prior-predictions-frozen.jsonl`에 10,000행 고정했다(SHA-256 `43add34f0570b1d8b123c5a5bcecc0ba74d46d48ffe37c562eccbf8e2563f8c2`, 생성 약 276ms). 이것은 타깃 합성 generator를 재현하거나 타깃 어휘를 가져온 것이 아니다. 전화·이메일의 공개 ID 및 길이 기반 숫자 규칙에 대한 민감도 확인이고, 두 추측 파일 모두 oracle 접근 전에 완성했다.

추가로 `page-order-probe.py`에서 정렬된 locator 1,000개의 순위와 공개 고객 첫 1,000행의 순위를 임의로 맞춰 blob 길이와 여섯 필드 길이의 상관을 검사했다. 최대 절대 상관은 회사 길이의 0.04278이었으며 3,000회 순열의 여섯 필드 최대값 보정 p값은 0.625, 실행 약 196ms였다. 이 순위 맞춤은 알려진 join이 아니고, 관찰된 상관으로 행↔page 연결을 추정할 근거가 없었다. 가능한 모든 물리적·시간적 부채널을 배제하는 검사는 아니다.

길이·공개 열만 쓰는 대조군과 v2 관찰군은 동일한 행별 예측 파일을 사용한다. v2의 추가 page metadata에서 공개 행과 이어지는 식별자가 발견되지 않았기 때문이다. 그러므로 두 군의 행별 정확값 적중률 차이는 이 정적 뷰·이 공격 규칙에서는 0이다. 이 비교는 길이로 인한 잔여 추론과 v2 posting의 추가 누출을 분리한다. **별도 평가자가 첫 번째 고정 파일을 채점해 전달한 결과는 보호 필드 정확값 0/60,000개, 여섯 필드 완전 레코드 0/10,000개였다.** 이 작업자는 oracle label 또는 보호 평문 파일을 열지 않았다. 이 값은 약한 일반 템플릿 prior의 결과이며 v2의 복원 저항성을 입증하지 않는다. 두 번째 독립 seed 추측 파일은 고정했지만 채점 결과를 받지 않았다.

## 규모 해석과 제한

위의 고객 관찰은 **1만 행**이고 blob은 전체 10만 행 색인에서 뽑은 앞 1,000 locator뿐이다. 앞선 v2 구축 보고의 10만 행 전체 posting 등장 5,472,494개, page 44,451개·manifest 3,301개와 혼동하지 않는다. 10만 행, 1억·10억 행의 복원률이나 실행 시간을 여기서 선형 외삽하지 않는다. 행별 공개 길이와 공개 열의 고유성은 모집단 및 데이터 생성 분포에 따라 바뀐다. 같은 필드·평균 조각 수라는 **조건부 산술**로 10만→1억→10억은 행과 posting 항목이 각각 1,000배·10,000배라서 약 54.7억·547억 posting 항목이다. 128건/page로 거의 찬다고 가정한 하한 규모는 대략 4,275만·4억 2,754만 page이며, 조각별 마지막 page와 manifest·메타데이터는 추가된다. 이것은 용량 차수 점검일 뿐 실제 저장량·구축/검색 지연 예측이 아니다. 외부 길이 자료를 행별로 처리하는 공격도 최소 O(N) 일이어서, 대규모가 그 자체로 방어를 보증하지 않는다. Locator가 독립적이고 목록이 인증 암호화되어 있는 한 단일 정적 뷰에서 공개 행-조각 join은 생기지 않는다. 대규모 운영에서는 갱신·삭제·WAL·접근 기록과 외부 보조 자료가 별도 위협이 된다.
