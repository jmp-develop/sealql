# V2. 최종 토큰 구성의 기계적 공격 검증

2026-09-27 · 검증 전용. 실행: `node --import tsx bench/verify-core/v2-attack.ts .local/ratings.txt`. 원시 수치와 색인 정의: [results.json](results.json). 공격 스크립트: `bench/verify-core/v2-attack.ts`. DB는 `assertDisposable`과 포트 확인 뒤 `127.0.0.1:56439`의 기존 fixture를 읽기만 했다. 공개 리뷰는 메모리에서만 처리했고 DB에 적재하지 않았다.

## 공격자와 측정 조건

키 없는 DB 스냅샷 공격자가 행 ID, companion 토큰 배열, 암호문 바이트 길이, 일부 행의 원문을 가진다고 가정했다. 공격에는 키와 토큰 계산 함수를 주지 않았다. 검증 도구만 제품 키로 조각의 정답 토큰을 재계산해 공격 결과를 채점했다. 공개 리뷰 `.local/ratings.txt`의 처음 20,000행을 피해자로, 다음 20,000행을 겹치지 않는 참고 자료로 썼다. DB는 `bench_realistic_100k.customers`의 처음 20,000행에 대응하는 `bench_standard_next_100k.customers_skip_product_multi_seal_index`의 **실제 메모 토큰 배열**을 피해 덤프로, 다음 20,000행의 원문을 빈도 참고 자료로 썼다. 시드 99 Fisher–Yates 순서의 중첩된 1/5/10% 알려진 행을 사용했다.

메모리 프로필은 현재 기본 `substring:true`의 인접·필드 시작·끝·건너뜀 조각이다. DB fixture는 이 구성에 **옵션인 단어 경계 조각을 추가**한 기존 프로필이다. 두 코퍼스와 프로필이 달라 해독률을 서로 직접 비교하지 않는다. 각 행 안의 중복 조각과 토큰은 한 번 센다. 빈도 공격은 피해 토큰과 별도 참고 조각의 행 빈도 순위를 맞췄다. 원문 대조는 알려진 행의 토큰·조각 출현 행집합이 같고 조각 후보가 하나일 때만 채택했다. 일관성 전파는 `ab·bc → a_c`와 역방향을 최대 6회 반복하고, 같은 행의 후보가 2표 이상이며 차점보다 2표 이상 앞설 때 채택했다. 위치 없는 조각 집합이므로 오답도 가능하며 표는 정답만 채점했다.

공개 리뷰의 172,978개 고유 조각은 60,896개 고유 16비트 토큰으로 압축되었다. DB 메모의 3,676개 고유 조각은 3,579개 토큰으로 저장되었다. DB 피해 20,000행에서 제품 함수로 재계산한 토큰 대비 누락 0건, 추가 0건이었다. 이 일치 검사는 검증 도구가 키를 가진 채점 단계이며 공격자에게 토큰 계산 권한을 준 결과가 아니다. 공개 리뷰·DB의 검색 오탐과 속도는 이번 검증에서 **측정 안 함**이며, 같은 공개 리뷰의 구성별 오탐은 `bench/results/2026-09-27-layout-attack/report-ko.md`의 별도 실험이다.

## 짧고 형식이 있는 필드

출처: 기존 제품 fixture의 전화·이메일·이름 각 20,000행, 실제 16비트 정확 토큰의 첫 원소와 암호문 `octet_length`, 대응 평문을 채점용으로만 사용한 `v2-attack.ts`. 암호문은 모든 표본에서 평문 UTF-8 바이트 길이보다 29바이트 길었다. 이 길이와 정확 토큰은 동일 길이·동일 토큰의 행을 묶는다. 아래 `원문 복원`은 1/5/10% 알려진 행의 `(길이, 토큰)`에 **원문 후보가 하나일 때만** 모르는 행에 전파하고 정답을 확인한 수치다.

| 필드 | 암호문 길이 종류 | 서로 다른 원문 | 서로 다른 정확 토큰 | 토큰 충돌 묶음 | 원문 복원 1/5/10% |
|---|---:|---:|---:|---:|---:|
| 전화 | 1 | 20,000 | 17,220 | 2,490 | 0 / 0 / 0행 |
| 이메일 | 7 | 20,000 | 17,238 | 2,509 | 0 / 0 / 0행 |
| 이름 | 3 | 19,999 | 17,233 | 2,508 | 0 / 0 / 0행 |

형식 후보를 기계적으로 열거했을 때, 관찰된 전화 형식 `[0-9]{2}-[0-9]{4}-[0-9]{4}`의 전 공간은 100억 개이고 모두 동일한 암호문 길이 41바이트를 만든다. 이메일의 제한된 시험 사전 `user[0-9]{4}@<알려진 1% 행에서 관찰한 도메인>`은 4개 도메인 × 10,000개 = 40,000개이며, 길이별로 0/10,000/20,000개의 후보가 남았다. 이름의 알려진 1% 행 어휘는 200개였다. 이들은 **명시한 형식의 후보 공간**이지 전체 이메일·이름 언어의 전수 공간이 아니다. 키 없는 공격자는 임의 후보의 HMAC 정확 토큰을 계산할 수 없으므로 이 후보들을 토큰에 직접 대입해 판별할 수 없다. 따라서 0행 복원은 해당 알려진 행 전파 공격의 결과일 뿐, 형식이나 길이가 안전하다는 증명이 아니다. `results.json`의 `lengthAndTokenOracleSingletonRows`는 모든 원문을 아는 채점자의 동치류 크기이며 공격자 복원 수치가 아니다.

## 다중 컬럼 GIN 이후 DB 노출

출처: `bench_standard_next_100k.customers_skip_seal_index`와 `customers_skip_product_multi_seal_index`의 10만 행, 12개 토큰 열 전체, `pg_indexes` 정의. 두 companion의 동일 `(scope_id,row_id)`에 있는 토큰 배열은 **차이 0/100,000행**이었다. 이전 색인은 부분 검색 열마다 별도 GIN을, 제품 fixture는 같은 6개 부분 검색 열을 하나의 다중 컬럼 GIN에 넣는다. 각 열의 토큰 값과 행별 결합은 그대로 노출되며, 색인 정의에도 6개 열의 정체와 순서가 드러난다. 따라서 이 덤프 공격에 필요한 논리적 토큰·행 관계는 동일하다. 물리적 GIN 페이지의 바이트나 posting 구조는 읽지 않았으므로 물리 구조 동일성은 주장하지 않는다.

## 판정과 한계

| 영역 | 판정 | 근거·한계 |
|---|---|---|
| 최종 기본 조각의 빈도·원문·일관성 공격 | 한계(설계상) | 두 덤프에서 위 해독률 확인. 키 없는 DB 스냅샷의 조각 빈도·공출현 누출이다. |
| 제품 companion 토큰의 재계산 일치 | 통과 | 메모 피해 20,000행, 누락·추가 0건. |
| 짧은 필드의 길이·정확 토큰 | 한계(설계상) | 길이와 동치류 노출 확인. 시험한 알려진 원문 전파 복원은 0행. 후보 토큰 직접 대입은 키 없는 조건에서 불가. |
| 다중 컬럼 GIN의 논리적 노출 | 통과 | 10만 행 토큰 열 차이 0건. 물리 posting 바이트는 측정 안 함. |

**사용한 공격 목록 = 확인한 누출의 하한**이다: 빈도 순위, 알려진 원문 행집합 대조, 제한된 조각 일관성 전파, 알려진 행의 정확 토큰 전파, 지정 형식의 후보 길이 열거. 쓰지 않은 공격: 더 강한 동시출현·문자열 전체 복원, 쿼리 관찰, 다중 스냅샷·WAL 변경 추적, 키 또는 토큰 계산 기능 탈취, 물리 GIN 페이지 분석. 이 결과는 보안 인증이나 운영 성능 수치가 아니다.
