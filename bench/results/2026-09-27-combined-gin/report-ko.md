# 필드 통합 GIN 실험

2026-09-27 · 일회용 PostgreSQL `127.0.0.1:56439` (`.local/pg-test`) · `bench_standard_next_100k` 고객 100,000행. `assertDisposable`로 데이터 디렉터리와 소유자를 확인한 뒤 실행했다. 원본 companion의 기존 토큰을 복사해 기본·건너뜀 각각 통합 배열 열과 GIN 하나를 가진 실험 companion을 만들었다. 정확 일치 토큰 열은 별도 B-tree로 유지했다. 제품 `src/`와 원본 행은 수정하지 않았다.

동일 데이터·검색식·ID 오름차순 20행·6필드 투영으로 평문, 기존 기본/건너뜀, 통합 기본/건너뜀을 비교했다. 같은 공개 API 엔진을 사용하고, 통합 경로에서만 후보 SQL을 벤치 래퍼로 치환했다. AND에 속한 부분검색 토큰은 한 `combined_tokens @> bigint[]`로 합쳤고 OR은 각 분기 조건의 OR로 실행했다. 256행 prefix 경로에도 동일한 조건을 적용했다. 2회 예열, 경로 순서 교차 7회 중앙값이며 **최초 실행과 각 7회 모두 반환 ID 순서 및 6필드 값이 평문과 일치했다**. 수치는 `SQL 요청~응답 ms / 전체 ms`; SQL 횟수, 후보 수, 반환 행 수, 인증 복호화 필드 수와 7회 원시 값은 `matrix.json`에 있다.

AND 4/6의 SQL 비용은 통합 경로에서 낮았다. `EXPLAIN (ANALYZE, BUFFERS)` 한 번씩의 직접 후보 경로에서 기본 AND 4는 기존 두 필드 GIN의 `BitmapAnd`(서버 실행 23.94 ms)에서 통합 GIN 한 번의 `Bitmap Index Scan`(7.37 ms)으로 바뀌었다. 기본 AND 6은 네 GIN의 `BitmapAnd`(21.67 ms)에서 통합 GIN과 정확 토큰 B-tree의 `BitmapAnd`(11.42 ms)로 바뀌었다. 건너뜀 AND 4는 기존 한 GIN과 많은 heap 재검사(63.94 ms)에서 통합 GIN(9.18 ms)으로 바뀌었다. 원시 계획 및 BUFFERS는 `explain.json`에 있다. 이는 내부 GIN의 특정 fast scan 알고리즘이 사용됐다는 증명은 아니다. 단일 필드와 OR은 통합으로 일관된 개선이 없었다. `대로6고` 기본은 두 구조 모두 SQL 2회, 후보 170개, 인증 필드 220개였고 건너뜀은 SQL 1회, 후보 10개, 인증 필드 60개였다.

## 저장·쓰기·토큰 경계

| 구성 | 기존 companion 총 크기 | 통합 companion 총 크기 | 기존/통합 insert ms | 기존/통합 memo 부분 수정 ms |
|---|---:|---:|---:|---:|
| 기본 | 211,255,296 B | 181,239,808 B | 1.005/0.636 | 0.853/0.585 |
| 건너뜀 | 304,619,520 B | 275,398,656 B | 1.910/0.806 | 0.673/0.415 |

크기는 `pg_total_relation_size`로 테이블·색인을 포함한다(`storage.json`). 쓰기는 기존 한 행의 토큰을 복사해 새 sentinel 행에 한 SQL씩 insert하고, `memo` 토큰을 새 문자열에서 계산한 뒤 한 SQL씩 update한 **각 1회 표본**이다(`cost.json`). 같은 트랜잭션에서 수행하고 rollback했다. 통합 부분 수정은 한 필드만 바뀌어도 통합 배열 전체를 재작성한다. 이 표본은 암호화·관리형 쓰기, 동시성, WAL 누적 비용, 반복 분포를 포함하지 않으므로 운영 쓰기 성능으로 해석할 수 없다. 통합 companion은 별도 실험 테이블로 남는다.

기존 기본·건너뜀 companion의 모든 행에서 필드별 부분검색 토큰의 상위 32비트 prefix를 추출했다(`collisions.json`). 각 구성의 여섯 필드는 각각 하나의 서로 다른 prefix를 가졌고, **관측된 필드 간 prefix 중복은 0건**이었다. 따라서 이 fixture에서는 통합 배열의 필드 간 토큰 충돌이 없었다. 동시에 DB 스냅샷을 보는 공격자는 통합 배열에서도 상위 비트로 필드별 토큰을 분류할 수 있다. 통합 전후 토큰·행 동시출현 정보의 누출이 같다는 완전한 보안 증명은 아니다. 빈도 공격, 원문 대조, 다중 스냅샷 공격은 이번 구조 실험에서 새로 실행하지 않았다.

이 결과는 로컬 합성 fixture의 관찰이며 제품 반영안이나 보안 인증이 아니다. `explain.json`은 직접 후보 SQL의 한 번 실행, 검색 표는 공개 API의 256행 prefix 포함 7회 중앙값이므로 서로 같은 시간 측정이 아니다. 저장 구조 변경에 따른 관리형 쓰기·삭제·동시성의 전체 영향은 측정하지 않았다.
