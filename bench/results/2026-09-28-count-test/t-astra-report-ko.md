DB 후보 전체는 LIMIT 없는 후보 조건의 별도 COUNT로 잰 논리적 후보 집합이며 실제 plan이 읽은 tuple 수와 다르다. 앱 수신 행은 SQL 결과 행 합계이며 count(*)는 1행이다. count/SUM 결과 수 1은 스칼라 결과 행이며 일치 행 수와 구분했다. JOIN은 티켓 100,000과 고객 100,000을 customer_id로 연결하고 티켓을 반환 단위로 삼는다. 제품 JOIN count는 search로 검증된 ID를 모두 받아 길이를 계산한 조합이며 단일-table count API와 구분한다. SUM은 ticket.memo_plain의 char_length를 미리 저장한 평문 amount를 더한다; 제품은 암호 조건 검증 후 ID로 SUM하여 두 단계이며 A는 DB 한 번에 SUM한다.

동시 쓰기 8개, 서로 다른 행 갱신 80회 및 공통 행 갱신 8회; 3회의 repeatable-read 스냅샷에서 A와 평문 count가 같았다. 코디네이터의 명시적 락 예외 지시로 다른 적재와 병행한 정확성 검사이므로 시간 수치를 제외했다.
삭제는 동일 트랜잭션 안에서 count와 태그/인덱스 FK cascade를 확인한 뒤 롤백했다. 부분 수정·동시 갱신은 커밋 후 검사하고 원본 fixture 값으로 복구했다. 앱 편의 API에 A를 통합한 제품 구현은 아니다.

EXPLAIN은 코디네이터 지시에 따라 ANALYZE 없는 계획 구조만 수집했다. JOIN 20 계획은 `Limit → Sort → Nested Loop/Gather → Hash Join`이며 tickets와 customers_tags의 Seq Scan 및 태그 판정이 Sort 아래에 있다. 따라서 ORDER BY와 LIMIT이 판정·JOIN 뒤에 놓이는 구조가 확인된다; 별도 측정에서 일치한 21,182행은 EXPLAIN의 실제 처리 행 수가 아니다. 20건만 필요해도 Sort 입력을 먼저 구성하는 계획이 큰 퇴행의 원인으로 판단된다.

정확 일치 count도 customers_tags Seq Scan 후 customers_seal_index 조회였고, 희귀/보통 contains count는 GIN Bitmap Scan 후 태그 Index Scan이었다. 현재 SQL은 모든 경로에서 GIN 후보 선별을 먼저 실행하도록 강제하지 않는다. 따라서 이 수치는 해당 시제품 SQL·배치의 결과이며, A 개념의 최적 성능 하한이 아니다. find200은 tags Index Scan과 Gather Merge를 선택해 find20과 계획이 달랐다. 개선된 SQL의 성능은 측정하지 않았다.
