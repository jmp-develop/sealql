# count를 DB 안에서 정확히 — 실용 테스트 교차 정리

2026-09-28. 연구자 4명(미션 1: Claude Fable·Codex astra, 미션 2: Claude Fable·Codex astra)의 결과를 코디네이터가 한 표로 정리했다. 일회용 PostgreSQL `127.0.0.1:56439`. 기존 테이블(`native_scale_100m` 1억, `native_verify_main`, `bench_realistic_100k`)은 읽기만 했고, 실험용 새 테이블만 만들었다(측정 뒤 삭제, `research_t_fable.b_tags`만 확인용으로 남음). 제품 코드는 바꾸지 않았다. 예열 2·교차 7 중앙값, 매 실행 평문과 결과 일치 단언. **로컬 합성 fixture 결과이며 운영 보장·보안 인증이 아니다.**

원자료: 이 폴더의 `t-fable-*.json`(1억 속 회사 B), `t-astra-*.json`·`t-astra-report-ko.md`(10만 단독), `bench/results/2026-09-28-mission/`(미션 2 재현), 보고 원문은 각 연구자 노트.

## 후보 설계 (쉬운 말)

| 이름 | 무엇을 하나 |
|---|---|
| 지금 제품 | DB가 16비트 조각 토큰으로 후보를 고르고, 앱이 후보를 받아 복호화·대조해 센다 |
| **A = 행별 검증** | 후보 고르기는 지금과 같다. 행·칸마다 무작위 값과 검증값을 미리 저장해 두고, DB가 후보마다 계산해 맞는지 확정한 뒤 `count(*)` 숫자만 돌려준다. 행 전송·복호화·상태 없음 |
| **B = 결합안** (미션 2) | A와 같은 원리에 MongoDB의 요소(충돌 없는 긴 검증값, 부분 문자열 자체를 검증 단위로)를 온전히 결합. PostgreSQL 안 `hmac` 계산 |
| MongoDB 온전 이식 | 등장마다 다른 태그 + 카운터 표(상태 필요) |

## 5. 결론

1. **행별 검증(A·B)은 count를 DB 안에서 정확히 끝낸다.** 행을 가져오지 않고 숫자만 받으며, 대량 count가 지금보다 5–30배 빠르다. 저장만 보고 드러나는 정보는 늘지 않고, 자연스러운 사용(수정·삭제·동시 쓰기·롤백)에서 모순이 없었다.
2. **제품에 넣기 전 풀어야 할 것:** 8글자보다 긴 검색어의 앱 확인 경로, 목록·JOIN에서 필요한 만큼만 확인하고 멈추는 처리, 가장 빠른 구현(검증값 위치·계산 함수) 선택, 다중 회사 실제 배치 확인.
3. **평문 대비 약 2배 목표는 아직 미달**이다(후보 수에 비례하는 DB 안 계산). 가장 좋은 구현(B 86–133 ms)도 평문 9–29 ms의 수 배다.
