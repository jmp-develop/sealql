## 대상과 검증 방법

고객 원문 100,000행의 공백·대소문자를 보존해 공개 `sealed.insert`로 새 `test_r9_verify_main`에 적재했다. 원문 600,000필드를 독립 정규화한 결과와 `research_u.customers_plain`의 차이는 0개다. 적재 100000행, 1459269.917ms; 원문 복호화 표본 100행이 모든 6칸에서 그대로 일치했다. 회사명 exact bits=2, 나머지 exact 기본16, 여섯 칸 substring wordBoundary=true, skipGrams 기본값이다. 스키마는 공개 Drizzle 정의에서 drizzle-kit으로 생성했고 extraMigrationSql을 설치했다.

원문 SHA-256: `1cf0a7590198cd9650ebbce302c0ee75eb8830fbadec3cef9f56ee00e199502b`. 초기 적재 기준 a15f85a; 최종 조회 빌드/함수 설치 정보: 04994b2097a215a47dfb8ac07809bd9bb89f489c, 2026-09-29T02:46:57.645Z. 적재 2026-09-29T01:57:51.933Z ~ 2026-09-29T02:23:04.382Z, 조회 2026-09-29T02:47:13.560Z ~ 2026-09-29T02:52:04.049Z. 물리 행 정렬·인덱스 통계는 catalog 원자료로 확인한다.

각 조건은 첫 실행 1회 별도, 예열 2회, 두 경로 순서를 번갈아 7회 실행해 지표별 중앙값을 기록했다. 매 실행 count 또는 ID 순서와 정규화 6칸을 **원문에서 계산한 oracle**과 대조했다. count는 1 SQL·0 복호화, 목록은 반환 1행당 6필드 인증 복호화를 단언했다. 전체 목록은 exact_common / sub_rare / exact_one 3개이며 limit를 생략했다. SQL은 클라이언트 요청~응답 누적 시간이다. 비교용 출력 정규화와 assert는 계측 밖이다.

like 3개는 실제 첫 고객 email에서 만들었고, respectWords는 원문 공백을 유지한 "서비스 상담"이다. respectWords 평문 시간은 해당 fixture에서만 compact 조건과 원문 words oracle의 **전체 ID가 동일함을 먼저 단언**한 뒤 지정된 평문 표를 사용했다(29843행); 일반적으로 두 의미가 같다는 주장이 아니다. 기존 52조건 파일의 case 수준 respectWords 메타데이터도 제품 API 옵션으로 반영했다. 과제4 참조 실행은 해당 옵션을 반영하지 않았으므로 그 두 조건의 역사 수치는 특히 직접 비교하지 않는다. 추가 respectWords 조건까지 세 조건 모두 원문 words oracle과 평문 기준의 전체 ID 동등성을 단언했다.

C 로캘 한글 LIKE가 포함된 조건은 †이며 평문 대비 성능 판정에서 제외한다. OS 캐시는 비우지 않았고 첫 실행을 콜드 캐시라고 부르지 않는다. 후보 검토 행 수는 DB 내부에서 측정하지 않았으며, 앱 수신 행은 SQL 응답 행 수다. 과제4 A·최종안은 **참고(다른 세션)**로만 제시한다.

## 구간별 원자료와 한계

전처리/SQL/SQL 사이/후처리/전체, SQL 호출·앱 수신 행·인증 복호화 필드 수는 metrics.csv와 measure.json에 전 조건·경로별로 보존했다. 지표별 중앙값은 서로 합산되지 않을 수 있다. writes.json에는 7회×각 행의 세부 지표, capacity.json에는 카탈로그·함수·색인과 용량 원자료, join.json에는 JOIN 반복을 보존했다. 원문을 보고 추측한 보안 판단은 수행하지 않았으며 이 작업은 보안 검증을 대체하지 않는다.

기록된 오류 0개. 미완료 항목은 첫 상태 문장에 표시한다. 로컬 합성 fixture 결과이며 운영 보장·보안 인증이 아니다.

재현 스크립트: bench/verify-r9/{load,measure,writes,capacity,load-tickets,join}.ts 및 report.mjs. 새 스키마를 생성하는 load/writes/load-tickets는 기존 스키마가 있으면 중단하며 보호 표를 지우거나 재설정하지 않는다. 조회는 코디네이터의 수정 완료 통지 후 최신 빌드+extraMigrationSql 설치가 선행되어야 한다. 모든 DB 실행은 assertDisposable·포트 확인과 measure.lock 소유하에 수행한다.

재현·검수: install.ts --fix-announced → measure.ts → writes.ts → capacity.ts → load-tickets.ts → join.ts → report.mjs → verify-results.mjs. install.ts의 최신 빌드와 extraMigrationSql 재설치는 데이터와 기존 형식을 유지한다. capacity.ts는 설치 함수 본문 4개와 MAIN 카탈로그 설정을 최종 공개 API 출력에 대조했다. 최초 적재의 extraMigrationSql에도 MAIN 설정이 포함되어 있었다.

최종 검수: 조회 2,300회(첫 실행·예열 포함)와 쓰기·JOIN의 실행 중 oracle 단언을 통과했다. verification.json은 반복 횟수·계측 값·물리 용량 합계·보고서 동일성·락 해제를 재검수한다. 최종 빌드, 측정 스크립트 TypeScript 검사, docs:check도 통과했다. 데이터 유지 지시에 따라 측정 스키마를 보존했으며 보호 표는 읽기만 했다.
