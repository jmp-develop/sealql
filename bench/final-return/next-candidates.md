# 미채택 후보 A/B — 준비와 검증 결과

A는 지정 9조건의 비교를 마쳤으나 반복 값·45자·NULL 입력에서 퇴행하여 연기했다. [결과 표](../results/2026-09-29-final-impl/next-candidates-report-ko.md)를 참고한다. B는 제품 검색 표 TOAST 0MiB 확인으로 불필요하여 DB 실험을 실행하지 않았다. 아래는 당시 후보의 재현 방법이며 추가 실행 계획이 아니다.

근거: 로컬 함수 비용 분해 보고서. 흔한 세 조건의 19–25% 감소는 병행 부하 중 연구 배열에서 얻은 후보 근거이며 제품 이득으로 확정하지 않는다. 현재 제품과 dist는 바꾸지 않는다.

## A: 첫 등장 충분조건

`firstOccurrenceVariant(query)`에 현재 제품에서 포착한 `{text, params}`를 전달한다. 컴파일러의 offset 배열 길이 N으로 모든 창의 ordinal 1 도장 위치와 N개 위치 비교 항을 생성한다. 창 수·연산자별 전용 구현이나 상한 분기는 없다. 첫 위치, 길이, affix가 모두 맞는 경우만 참이며, 불일치·없는 도장·NULL은 `CASE WHEN sufficient THEN true ELSE 원래 함수 END`의 ELSE로 간다. 일반 LIKE 프로그램은 변경하지 않는다. 단일 literal LIKE가 위치 판정으로 정규화되면 그 위치 호출에는 A가 적용된다.

위치 배열은 `SELECT array[...] OFFSET 0` 하위 식에서 한 번 계산한다. 첫 창 해시를 N개 비교 항에 반복하지 않으므로 SQL 크기와 해시 수가 N에 비례한다. 대신 행별 SubPlan 비용과 큰 배열의 선형 `array_position` 비용, 실패 후 기존 함수의 중복 작업이 생길 수 있다. 23창(45자) SQL 바이트 수를 준비 시험에서 출력하며 실행·계획 시간과 함께 채택 여부를 판단한다. 성능상 불리하면 후보를 기각하며 임의의 창 수 특례를 추가하지 않는다.

## B: 검색 표 TOAST 목표 크기

자기 소유의 **새 복사본**에서 전체 인라인 행 크기의 백분위와 최대값을 확인하고, 모든 행을 담는 목표(상한 8160)를 `toastTargetVariant(seal, target)`으로 명시한다. 근거 없는 기본 목표값은 두지 않는다. MAIN·도장 codec·색인·파생 키는 유지하고 테이블의 `toast_tuple_target`만 바꾼다. ALTER만으로 기존 행은 재작성되지 않으므로 복제 → 저장 파라미터 설정 → VACUUM FULL로 비교한다. 기존 보호 스키마와 독립 측정 중인 표에는 적용하지 않는다.

큰 목표 값이 모든 배열의 인라인 보존을 보장하지 않는다. 넓은 행이 페이지에 들어가지 않으면 외부 TOAST가 남을 수 있다. 같은 데이터·ID/물리 순서의 새 대조군과 후보를 적재하고 배열별 `pg_column_toast_chunk_id`, 압축 여부, 행 크기, heap/index/TOAST 용량을 기록한다. insert·부분 update·reindex 행당 비용과 검색 시 heap/TOAST 버퍼를 함께 비교해야 한다. 논리 저장 값·질의 키·인증/AAD·도장 확률은 그대로이고 물리 배치만 바뀌지만, 보안 증명으로 표현하지 않는다.

## 측정 락 해제 후 확인

현재 제품, A, B를 같은 연결에서 예열 2회·교차 7회로 비교한다. 주소 세종대로·메모 서비스상담·이메일 biz.test 끝, 희귀 푸른달·0건 조각·반복 값·45자·LIKE 1개·NULL의 count와 목록300만 실행하고 평문과 대조한다. A는 기존 bind 배열 객체까지 그대로 사용하며 새 파생 키를 보내지 않는다. B는 재암호화 없이 행을 복제하므로 salt·도장까지 동일하다. A의 EXPLAIN을 먼저 확인하고 행별 SubPlan 비용을 평가한다. 흔한 조건은 개선되어야 하고, 나머지는 절대 1ms 이내 차이만 무시한다.

SQL 왕복·전체 시간·계획 시간·SQL 바이트 수·반환 수·함수 호출 수·버퍼·쓰기 시간·용량을 분리한다. A의 CASE 성공률과 fallback 횟수를 함께 기록한다. 새 스키마/포트 검사, assertDisposable, 측정 락은 실행 harness가 책임진다. 이 준비 모듈과 메모리 시험은 DB 연결·빌드·설치를 실행하지 않는다. 실제 A의 결과는 위 보고서에 기록했다. B의 저장·쓰기·용량 변화는 측정하지 않았다.
