# 위협 모델

현재 제품(`standard`: AES-256-GCM 필드 암호화 + HMAC 후보 토큰 + DB 도장 판정)의 공격자와 누출을 정리한다. [015](decisions/015-database-search-proofs.md)가 앱 조건 재확인을 대체한다. 과거 토큰 공격의 수치 근거는 [010](decisions/010-security-claim-limits.md), 새 스트림 시험은 [R9 보고](../bench/results/2026-09-29-r9/report-ko.md), 측정 방법은 [attack-simulation.md](attack-simulation.md)에 있다.

## 1. 전제

- 루트·암호화 키는 앱의 비밀 저장소에만 있다. 토큰 계산과 복호화는 앱에서 한다. **검색 때 값/조각별 파생 키는 DB로 보낸다.** 이 키는 관찰된 값·조각의 도장 확인에 재사용될 수 있다.
- 검색 토큰은 키 있는 HMAC(SHA-384) 절단값이다. 키 없는 해시 경로는 제공하지 않는다.
- DB는 토큰 후보에 64비트 도장을 대조한다. 앱은 반환된 암호화 선택 칸을 인증 복호화하지만 조건 칸을 재확인하지 않는다. count는 복호화하지 않는다. 우연한 도장 충돌 가능성은 0이 아니고, 적대적 DB의 조건 판정을 증명하지 않는다.
- scope(테넌트) 권한 확인은 앱의 책임이다. 라이브러리는 받은 scope를 SQL 격리 조건과 AAD에 쓴다.

## 2. 공격자 유형

| 유형 | 가진 것 | 예 |
|---|---|---|
| T1 정적 스냅샷 (키 없음) | 덤프·백업 1회: 암호문, 토큰 배열, 행 수, 암호문 길이, 평문 컬럼, FK | 백업 유출, 덤프 탈취 |
| T2 물리 파일·WAL·다중 스냅샷 | T1 + 쓰기 시점, 갱신 전후 비교, MVCC dead tuple | 복제본·WAL 보관소 유출, 시점이 다른 백업 두 개 |
| T3 알려진 평문·공개 부가 정보 | 일부 행의 원문, 같은 종류의 공개 자료(언어 빈도, 이름·주소 분포, 형식) | 공격자가 직접 입력한 행, 다른 경로로 샌 기록 |
| T4 질의 관찰 | 검색 토큰·값/조각 키, 결과 행 집합·수·순서, 반복 질의 | DB 내부자, bind 파라미터 로그, 드라이버·프록시 추적 |
| T5 앱·키 탈취 | 루트 키 또는 토큰 계산 기능 | 비밀 유출, 앱 서버 침해 |
| T6 적대적 DB | 결과를 누락·재생하거나 행을 바꿔치기 | 악의적 DB 운영자 |

## 3. 누출 매트릭스

| 유형 | 드러나는 것 | 막는 것 |
|---|---|---|
| T1 | 결정적 토큰의 동일성·빈도·동시출현, 토큰 수, 암호문 길이(평문 UTF-8 + 29 B), coarse exact 동치류, 색인 정의. 추가로 정규화 길이와 compact 위치의 순열 | 암호문 직접 복호화. 질의 키 없는 새 도장은 행·스트림 salt로 분리됨 |
| T2 | T1 + 어떤 행이 언제 바뀌었는지, 갱신된 행과 토큰의 연결 | 같음. **이 채널은 측정하지 않았다** |
| T3 | 일부 원문으로 토큰·조각 대응을 추정하고 같은 조각을 가진 행을 연결한다. 과거의 5% 원문 → 모르는 행 80%+ 해독 0.03–3.64%(제품 토큰 10만 행·구성별), 합성 메모 19.33%는 **약한 공격의 하한**이다. 최신 충돌 인지 전화 조립과 주소 사전 공격은 아래 실측처럼 훨씬 높은 값 복원을 보였다. 길이 + 고유값 사전만으로 16종 회사명 69.875% | 과거 측정의 완전 레코드 복원 0건은 **방어의 증거가 아니다** |
| T4 | 질의 토큰, 값/조각 파생 키, 결과 집합·수·반복. 관찰된 조각 키와 DB salt로 해당 조각의 모든 등장순번 도장을 계산해 위치 복원 가능. | 이 채널은 암호로 막지 못한다. 파라미터 로그 금지·접근 최소화·감사 |
| T5 | 전부 | 어떤 제품도 막지 못한다. 비밀 관리와 탐지 |
| T6 | 토큰/도장 삭제로 조용한 누락, 도장·위치·실행 결과 조작으로 거짓 조건/count 반환 가능. 커서는 스냅샷이 아님 | 선택된 변조·이동 암호문은 인증 실패. **완전성·SQL 판정 무결성은 보장하지 않는다** |

- **T3 추가 실측:** 부분 검색을 켠 제품의 피해·참조 각 1만 행 fixture에서 충돌 인지 조립 공격은 전화의 알려진 원문 1%·5% 조건에서 나머지 9,900·9,500행의 정규화 값 전체를 각각 **99.79%·99.80%** 복원했다. 주소는 알려진 원문 5%에서 사전 공격으로 **73.41%** 복원했다([A/B 근거](../bench/results/2026-09-30-competitor-sim/m1-astra/report-ko.md)). 같은 scope에 정상 값 100·1,000행을 선택 삽입한 전화 공격은 피해 1만 행의 값을 **99.74%·99.80%** 복원했다([C 근거](../bench/results/2026-09-30-competitor-sim/r9-impl/report-ko.md), [통합·독립 검산](../bench/results/2026-09-30-competitor-sim/v-astra/report-ko.md)). 이는 특정 fixture·키·공격의 전수 실측이며, 과거의 80%+ 조각 해독 지표와 다른 값 전체 일치 지표다. 과거의 낮은 비율을 현재 누출의 상한이나 안전 근거로 사용하지 않는다.
- **T4 추가 실측:** 피해·참조 각 1만 행에서 1000회 질의와 검색어 원문·참조 사전을 아는 조건의 정규화 값 복원율은 동일 사전 공격에 위치 정보를 더했을 때(후보-only→위치 추가) 전화 0→87.5%, 주소 4→35%, 회사 100→100%, 나머지 필드 ≤1.2%였다([근거·공격 한계](../bench/results/2026-09-29-attack-extra/report-ko.md)).
- **T4 키-only:** 검색어 원문 없이 관찰 키와 참조 빈도로 추정한 글자 정답률은 약 9.7–34%였다. 연구 최종안과 같은 관찰 채널이며, 백업만으로 질의 키를 얻는 것은 아니므로 백업 단독으로 이 관찰 조건이 성립하지 않는다.

- 16비트 조각 토큰의 충돌은 scope당 수천 조각 규모에서 사실상 흐림을 주지 않는다. 비트를 늘리면 누출만 커진다([004](decisions/004-token-layout-16bit.md)).
- 다중 컬럼 GIN은 필드별 GIN과 논리적 토큰·행 관계가 같다(10만 행 차이 0건). 물리 GIN 페이지는 분석하지 않았다.
- 제거 전 스트림의 역사적 기계적 시험에서 fixture·공개 리뷰 각 250행의 도장 중복과 위치 순열 오류는 0건이었다. 관찰한 조각 키로는 각각 797·906개 위치를 복원했다. words 길이 차이는 각각 868·1,640개 정규화 공백을 드러냈다. 중복 0건은 안전 증명이 아니며 기존 토큰 공격의 방어를 뜻하지 않는다.
- 질의에서 관찰한 값/조각 키는 고정 키 아래에서 만료되지 않는다. 이후에 저장·수정된 행의 새 salt에도 같은 값·조각을 대조할 수 있다.
- [019](decisions/019-compact-only-search.md)는 singleton·words 스트림과 단어 경계 후보를 제거한다. 따라서 words/compact 길이 차이의 공백 수 채널과 singleton 질의 키 채널은 현재 스키마에 없다. 기존 토큰·길이·compact 조각 관찰 누출은 그대로다.
- AI는 대입 공격을 바꾸지 못한다(HMAC-SHA-384). 통계 추론(주소 구조, 성씨 분포, 조각 조립)은 강화한다. 존재하는 누출을 증폭할 뿐 없는 신호를 만들지는 못한다.

## 4. 보안 문장

허용:

> SealQL은 선택한 필드를 AES-256-GCM으로 암호화하고 행·필드·scope에 결속한다. 루트·암호화 키 없는 스냅샷 공격자는 암호문을 직접 복호화할 수 없지만 토큰 빈도·동시출현과 길이로 추론할 수 있다. 질의를 관찰하면 값/조각 키도 얻어 해당 조각의 위치를 복원할 수 있다. 반환 암호문 인증은 DB 조건 판정이나 완전성을 증명하지 않는다. 키 없는 DB 탈취에서 완전한 레코드의 대량 복원이 어렵다는 것은 입증되지 않았다.

불허:

- "DB를 훔쳐도 복원이 어렵다", "안전하다", "N배 안전", 복원률 수치를 안전의 근거로 쓰는 것, 블라인드 복원 0건 인용.
- "평문보다 빠르다".
- "개인정보 보호 법적 의무 준수". 이름·연락처·주소·메모 암호화는 자발적 보호 조치다(「개인정보의 안전성 확보조치 기준」 제7조의 의무 대상은 고유식별정보, 비밀번호, 생체인식정보, 신용카드·계좌번호).
- 로컬 실험 결과를 보안 인증이나 운영 보장으로 표현하는 것.

## 5. 운영 필수 조치 (라이브러리 밖)

- **로그:** DB·드라이버·프록시·APM에서 bind 파라미터와 실패 질의 매개변수를 기록하지 않는다. PostgreSQL의 `log_parameter_max_length`와 `log_parameter_max_length_on_error`를 0으로 설정하고 statement/auto_explain·추적 도구의 실제 출력을 확인한다. 단순 SQL 정규화 통계와 bind 값 기록을 구분한다. 조각 키가 로그에 남으면 T4 위치 복원이 가능하다.
- **WAL·복제본·백업:** 본 DB와 같은 등급으로 접근을 통제하고 암호화해 보관한다. 시점이 다른 백업 여러 개가 함께 새면 T2가 된다.
- **키:** 루트 키는 비밀 저장소(Workers Secret 등)에만 둔다. 코드, CI 로그, 에러 리포팅, 크래시 덤프에 남기지 않는다. 키를 바꾸면 전체를 재암호화·재색인한다.
- **키별 암호화 호출 수:** 한 필드 키(shard 포함)의 암호화 호출은 모든 테넌트를 합쳐 2³² 이하여야 한다(NIST SP 800-38D). 대량 쓰기 서비스는 감시한다([003](decisions/003-field-cipher-key-cache-aad.md)).
- **복호화 접근 감사:** 가능하면 복호화 경로를 분리하고 접근을 기록한다.
- **쓰기 경로:** 관리형 쓰기만 암호문·토큰·도장을 한 트랜잭션에서 맞춘다. 원시 SQL로 암호문 칸을 쓰면 색인이 어긋난다. 새 형식은 스키마·함수 설치와 전체 reindex를 마친 뒤 검색한다.
- **필드 선택:** 전화번호·계좌번호·주민등록번호처럼 형식이 고정되고 문자 종류가 적은 칸에는 **부분 검색을 켜지 말고, 검색이 필요하면 정확 일치만 사용한다**(`search: { exact: true }`, `substring` 생략). 일부 원문이나 선택 삽입으로 조각 대응을 학습하면 사전에 없는 값도 조립할 수 있다. 정확 일치에도 동일성·빈도 누출은 남는다. 어휘가 적은 필드(상태값, 짧은 선택지)와 빈도가 민감한 짧은 필드도 부분 검색을 켜지 않는다. 정확한 DB 계산이 필요한 필드는 암호화하지 않는다. 검토했다가 기각한 완화안(더미 값, 비트 축소, 패딩, MongoDB식)과 타 제품 비교는 [결정 025](decisions/025-leakage-reevaluation-and-rejected-mitigations.md)에 있다.
