# 위협 모델

현재 제품(`standard`: AES-256-GCM 필드 암호화 + HMAC 조각 토큰 + GIN + 라이브러리 내부 재확인)의 공격자, 누출, 말할 수 있는 보안 문장, 운영자가 해야 할 조치를 정리한다. 수치 근거는 [010](decisions/010-security-claim-limits.md), 측정 방법은 [attack-simulation.md](attack-simulation.md)에 있다.

## 1. 전제

- 키는 앱의 비밀 저장소에만 있다. DB는 키를 모른다. 토큰 계산과 복호화는 앱 프로세스에서만 한다.
- 검색 토큰은 키 있는 HMAC(SHA-384) 절단값이다. 키 없는 해시 경로는 제공하지 않는다.
- 결과는 항상 인증 복호화와 조건 재확인을 거친다. 토큰 충돌(오탐)은 결과에 나오지 않는다.
- scope(테넌트) 권한 확인은 앱의 책임이다. 라이브러리는 받은 scope를 SQL 격리 조건과 AAD에 쓴다.

## 2. 공격자 유형

| 유형 | 가진 것 | 예 |
|---|---|---|
| T1 정적 스냅샷 (키 없음) | 덤프·백업 1회: 암호문, 토큰 배열, 행 수, 암호문 길이, 평문 컬럼, FK | 백업 유출, 덤프 탈취 |
| T2 물리 파일·WAL·다중 스냅샷 | T1 + 쓰기 시점, 갱신 전후 비교, MVCC dead tuple | 복제본·WAL 보관소 유출, 시점이 다른 백업 두 개 |
| T3 알려진 평문·공개 부가 정보 | 일부 행의 원문, 같은 종류의 공개 자료(언어 빈도, 이름·주소 분포, 형식) | 공격자가 직접 입력한 행, 다른 경로로 샌 기록 |
| T4 질의 관찰 | 검색 토큰, 결과 행 집합·수·순서, 반복 질의 | DB 내부자, 쿼리 로그, `pg_stat_statements` |
| T5 앱·키 탈취 | 루트 키 또는 토큰 계산 기능 | 비밀 유출, 앱 서버 침해 |
| T6 적대적 DB | 결과를 누락·재생하거나 행을 바꿔치기 | 악의적 DB 운영자 |

## 3. 누출 매트릭스

| 유형 | 드러나는 것 | 막는 것 |
|---|---|---|
| T1 | (scope, 필드, 조각)별 결정적 토큰의 동일성·빈도·행 안 동시출현, 행별 토큰 수, 암호문 길이(평문 UTF-8 + 29 B), 정확 일치 토큰의 동치류, 색인 정의(어느 열이 검색 필드인지) | 평문 값의 직접 복호화, 후보 값 대입 확인 |
| T2 | T1 + 어떤 행이 언제 바뀌었는지, 갱신된 행과 토큰의 연결 | 같음. **이 채널은 측정하지 않았다** |
| T3 | 알려진 행 1개가 그 행의 모든 토큰에 이름을 붙이고, 같은 조각을 가진 모든 행을 연결한다. 5% 원문을 알 때 제품 토큰 10만 행에서 모르는 행 80%+ 해독 0.03–3.64%(구성별), 어휘가 적은 합성 메모 19.33%. 길이 + 고유값 사전만으로 16종 회사명 69.875% | 완전 레코드 복원은 측정 범위에서 0건이지만 **방어의 증거가 아니다** |
| T4 | 질의 토큰 = 조각 라벨 집합, 일치 행 집합, 결과 수, 반복 질의 연결 | 암호로는 막지 못한다. 접근 최소화·감사·탐지 |
| T5 | 전부 | 어떤 제품도 막지 못한다. 비밀 관리와 탐지 |
| T6 | 토큰을 지우거나 바꿔 행을 조용히 누락시킬 수 있다(V1 재현). 커서는 여러 요청에 걸친 스냅샷이 아니다 | 변조·이동한 암호문은 인증 실패. **누락은 탐지하지 못한다** |

- 16비트 조각 토큰의 충돌은 scope당 수천 조각 규모에서 사실상 흐림을 주지 않는다. 비트를 늘리면 누출만 커진다([004](decisions/004-token-layout-16bit.md)).
- 다중 컬럼 GIN은 필드별 GIN과 논리적 토큰·행 관계가 같다(10만 행 차이 0건). 물리 GIN 페이지는 분석하지 않았다.
- AI는 대입 공격을 바꾸지 못한다(HMAC-SHA-384). 통계 추론(주소 구조, 성씨 분포, 조각 조립)은 강화한다. 존재하는 누출을 증폭할 뿐 없는 신호를 만들지는 못한다.

## 4. 보안 문장

허용:

> SealQL은 선택한 필드를 앱이 가진 키로 AES-256-GCM 암호화하고, 행·필드·scope에 결속한다. 키가 없는 사람은 암호문을 복호화할 수 없고, 검색 토큰은 키 있는 HMAC이라 후보 값을 대입해 확인할 수 없다. 그러나 DB를 볼 수 있는 사람은 검색 토큰의 빈도와 동시출현, 값의 길이, 검색 결과 수와 시점을 볼 수 있으며, 이를 이용한 부분 복원 공격이 측정됐다. 키 없는 DB 탈취에서 완전한 레코드의 대량 복원이 어렵다는 것은 입증되지 않았다.

불허:

- "DB를 훔쳐도 복원이 어렵다", "안전하다", "N배 안전", 복원률 수치를 안전의 근거로 쓰는 것, 블라인드 복원 0건 인용.
- "평문보다 빠르다".
- "개인정보 보호 법적 의무 준수". 이름·연락처·주소·메모 암호화는 자발적 보호 조치다(「개인정보의 안전성 확보조치 기준」 제7조의 의무 대상은 고유식별정보, 비밀번호, 생체인식정보, 신용카드·계좌번호).
- 로컬 실험 결과를 보안 인증이나 운영 보장으로 표현하는 것.

## 5. 운영 필수 조치 (라이브러리 밖)

- **로그:** PostgreSQL 파라미터 로깅을 끈다(`log_statement`, `log_min_duration_statement`, `auto_explain`). 검색 토큰이 로그에 쌓이면 T4와 같아진다. `pg_stat_statements`의 보관 범위를 확인한다.
- **WAL·복제본·백업:** 본 DB와 같은 등급으로 접근을 통제하고 암호화해 보관한다. 시점이 다른 백업 여러 개가 함께 새면 T2가 된다.
- **키:** 루트 키는 비밀 저장소(Workers Secret 등)에만 둔다. 코드, CI 로그, 에러 리포팅, 크래시 덤프에 남기지 않는다. 키를 바꾸면 전체를 재암호화·재색인한다.
- **키별 암호화 호출 수:** 한 필드 키(shard 포함)의 암호화 호출은 모든 테넌트를 합쳐 2³² 이하여야 한다(NIST SP 800-38D). 대량 쓰기 서비스는 감시한다([003](decisions/003-field-cipher-key-cache-aad.md)).
- **복호화 접근 감사:** 가능하면 복호화 경로를 분리하고 접근을 기록한다.
- **쓰기 경로:** 관리형 쓰기만 암호문과 토큰을 한 트랜잭션에서 맞춘다. 원시 SQL로 암호문 칸을 쓰면 색인이 어긋난다.
- **필드 선택:** 어휘가 적은 필드(상태값, 짧은 선택지)와 빈도가 민감한 짧은 필드는 부분 검색을 켜지 않는다. 정확한 DB 계산이 필요한 필드는 암호화하지 않는다.
