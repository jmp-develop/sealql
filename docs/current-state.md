# SealQL current state and code map

As of 2026-09-27, the product uses one search mode: `standard` HMAC pieces, PostgreSQL GIN/B-tree companion indexes, and internal authenticated predicate verification. Stateful search, V2 encrypted posting pages, and keyed bucket search were rejected research lines; their code was removed and only result reports remain ([decision 011](decisions/011-rejected-research-lines.md)). None is a product mode.

Start with the [integration guide](llm-integration.md), [threat model](threat-model.md), and [examples](../examples/standard-consumer.ts). The design decisions and their measurements are in [`decisions/`](decisions/README.md): search scheme [001](decisions/001-search-hmac-pieces-gin-verify.md), fixed keys [002](decisions/002-fixed-keys-no-db-policy.md), cipher [003](decisions/003-field-cipher-key-cache-aad.md), tokens [004](decisions/004-token-layout-16bit.md)–[005](decisions/005-skip-grams-default-on.md), engine [006](decisions/006-query-engine.md), indexes [007](decisions/007-multicolumn-gin-not-combined-array.md), non-goals [009](decisions/009-scope-and-non-goals.md), and security claim limits [010](decisions/010-security-claim-limits.md). Measurement rules are in [measurement.md](measurement.md).

**Planned, not implemented:** a Drizzle-native API: per-column `sealed.text(...)` field options plus one `sealed.register(table, { row, scope })` line, `sealed.insert/update/upsert` write helpers (parent and companion in one transaction, companion table kept, no triggers), `sealed.open`/`openRaw` for plain Drizzle query results, and `findMany`/`count`/`search` with `m.sql` for OR between plain and encrypted columns. See [plan/001](../plan/001-drizzle-native-api.md) and decisions [008](decisions/008-drizzle-integration.md) and [012](decisions/012-drizzle-companion-and-column-options.md). The shipped Drizzle API is still `defineSealed`/`bindSealed` with a companion table, as described below.

The app defines a model and per-table companion schema through Drizzle or raw PostgreSQL. Code supplies a fixed 32-byte root key (global default, optional per model) before creating the sealer. There are no DB policy, scope, canary, or state tables. The AES-GCM envelope has a one-byte format header and no key version. Derived field keys are cached per key scope, model, field, codec, and 8-bit row shard; data scope and row ID remain authenticated AAD. Search token profile keys are cached across data scopes. Scope prefixes are calculated for each token operation and are not retained in server-lifetime caches.

Managed inserts and updates commit parent CAS and companion changes in one transaction; delete cascades. Each companion has one row per scope and row ID, and a partial update changes only the affected token columns. Exact token columns retain their B-tree expression indexes; all substring token columns share one multicolumn GIN index (one-column GIN for a single substring field). Raw DDL retains the elevated statistics target per substring column. Adding or removing a searchable field requires a replacement GIN; see the [integration guide](llm-integration.md) for the staged column, backfill, and index procedure. Search makes one candidate SQL call per page batch, uses one companion semi-join for the whole Boolean expression, decrypts condition fields concurrently, verifies them, and decrypts selected fields for accepted rows with a shared configurable concurrency cap. JOIN/raw `decryptRows` uses the same bounded field concurrency setting. A short page fetches further keyset batches. `count` requires a candidate bound. Raw SQL and Drizzle adapters share the engine. If the fixed key must change, the application must re-encrypt and reindex all data.

For ordinary ID-ordered substring pages, candidate SQL checks a bounded 256-row companion prefix in row-ID order. If that prefix contains the requested number of token matches, PostgreSQL need not materialize and sort every matching token row; otherwise the same SQL statement falls back to the GIN candidate search. Exact-token searches, custom ordering, public filters, advanced queries, and large count batches retain their direct indexed path. Authenticated predicate verification still decides which rows are returned. When a page remains short after verification, its next candidate batch grows from the pass rate observed within that call, up to the existing budgets; batches above 200 rows use the direct candidate path. No pass-rate state is retained. Count fetches up to 2,000 candidates per internal batch while retaining its exact numeric result and candidate bound. The local comparisons and remaining slow Boolean cases are recorded in [the SQL-plan follow-up](../bench/results/2026-09-27-standard-next-sqlplan/report-ko.md) and [the batching follow-up](../bench/results/2026-09-27-candidate-batching/report-ko.md).

**Security status:** keyless database theft resistance for full records remains unproven. Search tokens leak frequency and co-occurrence, ciphertext length reveals plaintext byte length, and a hostile database may omit results. The [threat model](threat-model.md), [decision 010](decisions/010-security-claim-limits.md), and [mechanical attack method](attack-simulation.md) delimit claims. Encrypted field range queries, ordering, and database aggregation are unsupported. Exact database calculations need plaintext fields. OR between a plain column and an encrypted condition is not expressible in `findMany` yet. Local experimental results are not deployment guarantees.

The [implementation review](../bench/results/standard-core-implementation-2026-09-27.md) records focused tests. The [full 100,000-row review](../bench/results/2026-09-27-standard-next/report-ko.md) re-encrypted all customers and tickets in a separate disposable schema and authenticated all 1.2 million fields against source plaintext. The [core verification](../bench/results/2026-09-27-core-verification/v1/report-ko.md) found no false negatives or positives in 1,000 random queries and full cursor traversals; its [performance section](../bench/results/2026-09-27-core-verification/v3/report-ko.md) found candidate SQL near plaintext (about 1.9x on average) but total 20-row page time 5.3–12.9x plaintext (mostly 10–13x), dominated by authenticated decryption and verification. Substring profiles store one-character-gap skip grams by default, including `substring: true` and objects omitting `skipGrams`; `substring: { skipGrams: false }` disables them. Changing the profile requires reindexing. In a 100,000-row fixture with the former per-field GIN layout, companion size rose from 211 MB off to 305 MB on ([storage data](../bench/results/2026-09-27-combined-gin/storage.json)), and median single-row insert time rose from 4.65 ms to 6.16 ms ([write data](../bench/results/2026-09-27-skip-write-cost/report-ko.md)). The [current multicolumn GIN DDL check](../bench/results/2026-09-27-product-multicolumn-gin/report-ko.md) covers 21 searches and a nine-term sweep. These are local experimental measurements, not deployment guarantees.
