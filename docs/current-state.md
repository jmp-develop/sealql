# SealQL current state and code map

Limited pages grow finite candidate batches according to the observed match rate. Count applies SQL `LIMIT maxCandidates + 1` when the caller supplies that budget. Reindex uses a fixed internal default of 1,000 rows per batch, with caller override and no maximum. Date and timestamp cursor positions use DateStyle-independent JSON text; earlier cursors are invalid.

The installed declaration check now runs with `skipLibCheck: false` and reports SealQL or consumer diagnostics; independent Drizzle 0.45 declaration diagnostics are excluded. `open` and `openRaw` reject unawaited thenables with `INVALID_VALUE`. Wrapped database errors expose a sanitized driver summary in `cause`, without Drizzle SQL parameters or server detail; SQLSTATE and constraint remain available. New or changed searchable profiles require a completed `reindex` before search code is deployed, since existing companion rows do not record a profile version. The integration guide gives the migration order and warns that premature queries can silently omit old rows.

For `search` positions containing text, nullable, or other database ordered values, one additional SQL request per nonempty candidate batch verifies strict increase using database comparison and collation; malformed ordering or invalid position casts raise `INVALID_CANDIDATE_SHAPE`. This request checks cancellation and caller deadline before and after execution. Nonnull UUID and integer positions retain the in-process check without an extra request. Drivers that explicitly reject transactions before managed write or reindex callbacks run raise `UNSUPPORTED_DRIVER` only when no server SQLSTATE is present.

As of 2026-09-27, the product has one search mode: `standard` HMAC pieces, PostgreSQL companion GIN/B-tree indexes, and internal authenticated predicate verification. Stateful search, V2 posting pages, and bucket search are rejected research lines ([decision 011](decisions/011-rejected-research-lines.md)). They are not product modes.

The public database integration is `sealql/drizzle/v0.45`. `createSealed({ sealer })` provides encrypted field builders, `register(table, { row, scope? })`, managed `insert/update/upsert`, `open/openRaw`, `findMany/count/search`, and `reindex`. The parent and returned companion are ordinary Drizzle tables and both must be exported to drizzle-kit. SealQL does not wrap `drizzle()` or the driver. The former raw PostgreSQL export, repository binding API, and row revision have been removed. Read the [integration guide](llm-integration.md) and [examples](../examples/standard-consumer.ts).

The app supplies a fixed 32-byte global key and may supply fixed model keys. No key version or DB policy table exists. AES-GCM binds a field to model, field ID, codec, key scope, scope, and row ID. Derived field and token-profile keys are cached; row values, plaintext, ciphertext, and frequency information are not retained in server-lifetime caches. The companion stores one row per `(scope,row)`. Exact token columns use B-tree expression indexes and substring columns share a multicolumn GIN index. The parent has no search tokens or trigger. A partial managed update changes only affected token columns, while a parent delete cascades. Scope-free tables use `_` consistently in AAD, tokens, and cursors.

Search first asks PostgreSQL for token candidates, then authenticates condition fields before opening selected fields for matches. A call-scoped cache avoids repeated authentication for duplicate 1:N JOIN rows. `m.sql` permits ordinary SQL conditions inside Boolean matches, including OR with encrypted conditions. `findMany` and `search` use keyset cursors; in `search`, the first table listed in `match` sets the page order, and a one-to-many JOIN requires a unique many-side keyset. `count` computes candidates in one SQL request and returns an exact number; a caller budget that prevents proof raises `LIMIT_EXCEEDED`. Candidate, byte, and deadline budgets are optional, have no library maximum, and can return a short page with a cursor after the last fully processed row. Omitting a page limit returns all matches. Cursors bind scope, match, where, and order; page size and projection may change, and cursors do not expire. Plaintext sortable columns support multiple and nullable order keys. There is no offset pagination or encrypted field range, sort, or DB aggregate support. A cursor spans separate requests and is not a snapshot. Plain Drizzle encrypted-column writes raise `SEAL_REQUIRED`; raw SQL encrypted-column writes bypass token maintenance and can cause omissions, repaired by `reindex`. Managed writes omit `undefined` properties. UUID and text row IDs, text scopes, and scope-free companions pass drizzle-kit generate, migrate, and repeated push; text row comparisons and keyset ordering follow the database column collation and can use its indexes.

**Security status:** keyless database theft resistance for full records is unproven. The database sees deterministic token frequency and co-occurrence, ciphertext length, and query/update patterns; a hostile database can omit rows. See the [threat model](threat-model.md), [claim limits](decisions/010-security-claim-limits.md), and [mechanical attack method](attack-simulation.md). Avoid substring indexes for low-vocabulary fields.
