# 설계·제품 검증 절차

SealQL 변경은 가설, 반증 조건, 재현 가능한 실험, 제품 게이트를 순서대로 통과해야 한다. 데이터와 반복 측정은 [측정 규칙](measurement.md), 누출 판단은 [기계적 공격 시뮬레이션](attack-simulation.md), 실행 도구와 환경 구성은 [bench 안내](../bench/README.md)를 따른다. 결과는 로컬 증거이며 운영 성능 보장이나 보안 인증이 아니다.

## 1. 변경 전에 고정할 것

변경 문서나 실험 스크립트에 다음을 먼저 적는다.

- 해결할 사용자 문제와 현재 제품 기준선
- 후보가 바꾸는 저장물, 쓰기 경로, SQL, 공개 API
- 정확성·무결성·보안 불변 조건
- 후보를 기각할 관찰값과 수치 기준
- 사용할 데이터, 질의, 시드, 반복 수, 비교 경로
- 관리형 쓰기, 부분 수정, 삭제, 동시성, 검색 누락, 누출 경계에 미치는 영향

보안이나 저장 형식을 바꾸는 후보는 구현 전에 기계적 공격을 실행한다. 구현이 가장 값싼 증거인 작은 변경은 최소 시제품으로 시작할 수 있지만, 기각 조건과 비교 기준은 먼저 고정한다.

## 2. 안전한 실험 환경

DB 실험은 `127.0.0.1:56439`의 일회용 클러스터만 사용한다. 스크립트는 연결 전에 `test/disposable.ts`의 `assertDisposable`과 포트를 확인해야 한다. `bench_realistic_100k` 원본은 읽기 전용이며, 후보 데이터는 별도 임시 스키마에 파생하고 실험 뒤 제거한다. 운영 DB, 포트 5432, 기존 사용자 데이터에는 테스트나 마이그레이션을 실행하지 않는다.

메모리 시뮬레이션도 실제 제품 형식과 같은 정규화·토큰 규칙을 사용하고, 제품 암호 출력과 표본 대조한다. 합성 fixture만으로 자연어 누출이나 오탐을 결론 내리지 않는다.

## 3. 반증과 수치 판정

평문, 현재 제품, 후보를 같은 데이터·질의·정렬·LIMIT·투영으로 비교한다. 모든 반복에서 반환 ID 순서, 투영 값, exact count가 평문과 같아야 한다. 한 건이라도 다르면 성능 측정을 중단하고 정확성 실패로 기록한다.

정상 경로 외에도 다음을 확인한다.

- 암호문이나 proof 손상 및 행 바꿔치기
- 관리형 insert/update/upsert, 부분 수정, 삭제 cascade, reindex
- 트랜잭션 충돌과 결과 불명 상태
- NULL, 빈 값, 한 글자, 긴 반복 값, LIKE 와일드카드와 이스케이프
- 유한·무제한 목록, 전체 커서 순회, count, Boolean 조건, JOIN keyset
- 두 scope와 scope-free 모델, UUID와 text ID, 데이터베이스 정렬 순서
- raw SQL 오용과 companion 불일치

쿼리 시간 목표는 평문 대비 약 2배 이내지만 보안이나 정확성을 희생해 맞추지 않는다. [측정 규칙](measurement.md)에 따라 SQL 요청~응답, 전체 시간, 토큰 후보·최종 반환 행, 인증 복호화 필드 수를 분리한다. 측정하지 않은 값은 `측정 안 함`, 계산값은 `추정`으로 표시한다.

## 4. 제품 게이트

| 게이트 | 합격 조건 |
|---|---|
| V1 정확성·무결성 | 평문과 ID 순서·투영 값·count가 같고, 관리형 쓰기·부분 수정·삭제·reindex·커서·JOIN·오류 경로가 자동 시험을 통과한다. |
| V2 보안 | 기획 중과 구현 후에 같은 공격자 조건과 시드로 기계적 공격을 실행한다. 성공률은 누출 하한이고 실패는 안전 증명이 아니다. [위협 모델](threat-model.md)의 허용 문장만 사용한다. |
| V3 성능·자원 | 예열 2회, 순서 교차 7회 중앙값으로 평문·제품·후보를 비교하고 시간, SQL 회수, 후보·반환 행, 복호화, 저장·쓰기 비용을 분리한다. C 로캘의 한글 평문 전체 스캔 배율은 판정에서 제외한다. |
| V4 설치·통합 | 새 checkout과 소비자 설치에서 build, types, schema generate/migrate/push, `extraMigrationSql`, reindex, Node/지원 드라이버 흐름을 확인한다. 문서의 설치 순서가 실제 명령과 일치해야 한다. |

저장소 최종 게이트는 다음과 같다.

```sh
rtk npm run build
rtk npm run check
rtk npm test
rtk npm run docs:check
rtk npm run test:install
```

작업 범위에 맞는 실험·DB 게이트도 별도로 실행한다. 실패를 우회하거나 관련 없는 전체 파일을 수정해 통과시키지 않는다.

## 5. 기록과 종료

결과는 `bench/results/<날짜>-<주제>/`에 한국어 보고서와 기계 판독 가능한 원본으로 둔다. 보고서에는 조건, 소스 파일, 명령, 표, 기각안, 제한, 재현 시드를 포함한다. 결정이 확정되면 새 [결정 기록](decisions/README.md)에 선택과 근거를 남기고 완료한 계획 파일을 제거한다. 기존 결정 기록은 덮어쓰지 않는다.

제품 상태가 바뀌면 [current-state](current-state.md), 공개 API나 사용법이 바뀌면 `README.md`, `llms.txt`, [integration guide](llm-integration.md), `examples/`를 함께 검토한다. 문서에 과거 구현을 현재 동작처럼 남기지 않고, 역사와 대체 관계는 결정 기록에만 둔다.
