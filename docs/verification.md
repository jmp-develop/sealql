# 설계 검증 절차

SealQL의 설계는 가설, 반증 실험, 수치 게이트, 구현 검증을 순서대로 통과시킨 뒤 [결정 기록](decisions/README.md)에 남긴다. 실행 데이터와 측정 방법은 [bench/README.md](../bench/README.md), [측정 규칙](measurement.md), [공격 시뮬레이션](attack-simulation.md)에 따른다.

1. **가설과 기각 조건을 적는다.** 해결하려는 사용 문제, 현재 방식, 후보, 보안·정확성 불변 조건을 명시한다. 무엇이 관찰되면 후보를 버릴지도 실험 전에 적는다. Drizzle 통합 [결정 008](decisions/008-drizzle-integration.md)은 H1–H7과 E1–E7로 동기 암호화, 행 결속, 트리거, 드라이버 통합을 분리했다.
2. **일회용 DB에 시제품을 만든다.** `127.0.0.1:56439`의 소유 클러스터만 사용하고, 원본 `bench_realistic_100k`는 읽기만 한다. 같은 행·질의를 쓰는 별도 스키마에서 후보를 시험한다. 필요하면 [fixture 재현 절차](../bench/README.md#처음부터-환경-만들기)로 환경을 복구한다.
3. **반증 실험을 실행한다.** 정상 경로뿐 아니라 무결성 손상, 부분 수정, 동시성, 누락, API 오용, 인덱스 선택을 시험한다. 기각 조건이 생기면 후보를 수정하거나 버린다. [결정 008](decisions/008-drizzle-integration.md)은 행 ID 없는 AAD의 암호문 교체와 `push --force`의 DROP 시도를 확인해 해당 안을 제외했다. [결정 007](decisions/007-multicolumn-gin-not-combined-array.md)은 통합 배열과 다중 컬럼 GIN을 같은 fixture에서 비교했다.
4. **수치 기준으로 게이트를 판정한다.** 쿼리 시간은 평문 대비 약 2배 이내가 목표이며 보안을 희생해서 맞추지 않는다. 정확성·누출·시간·공간·쓰기 비용을 함께 기록한다. 목표를 못 맞추면 통과로 표현하지 않는다. [결정 006](decisions/006-query-engine.md)의 후보 SQL과 전체 API 시간을 분리한 결과처럼, 한 구간의 개선을 전체 성능으로 대체하지 않는다.
5. **구현 뒤 세 종류를 다시 검증한다.** 설계 시제품의 통과가 제품 코드의 통과를 뜻하지 않는다.

| 게이트 | 확인할 것 |
|---|---|
| V1 정확성·무결성 | 평문과 반환 ID 순서·필드 값·정확한 count가 같음. 무작위 질의, 전체 커서 순회, 암호문 변조, 관리형 쓰기·부분 수정·삭제·동시성을 확인한다. [코어 V1 결과](../bench/results/2026-09-27-core-verification/v1/report-ko.md)처럼 누락과 오탐을 모두 기록한다. |
| V2 보안 | [기계적 공격 시뮬레이션](attack-simulation.md)을 기획 중과 구현 후에 같은 조건으로 실행한다. 사용한 공격은 누출의 하한만 보인다. [결정 010](decisions/010-security-claim-limits.md)의 미입증 경계를 유지한다. |
| V3 성능 | [측정 규칙](measurement.md)에 따라 평문·제품·후보를 같은 데이터와 질의로 비교한다. 예열 2회, 순서 교차 7회 중앙값. SQL 요청~응답, 전체 시간, 후보·반환 행 수, 인증 복호화 필드 수를 분리한다. C 로캘에서 한글 평문 전체 스캔의 배율은 성능 판정에서 뺀다. |

마지막으로 결정 기록에 선택, 수치와 원본 결과 파일, 기각안, 대체 관계를 남긴다. 측정하지 않은 값은 “추정”으로 표시한다. 합성 fixture는 자연어 오탐과 누출을 대표하지 못하므로 실제 문장 자료에서도 확인한다. 로컬 실험은 운영 성능 보장이나 보안 인증이 아니다.
