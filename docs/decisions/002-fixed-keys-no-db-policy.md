# 002. 고정 키(전역 또는 모델), DB 정책 테이블 없음

- 상태: 확정 (2026-09-27, 사용자 결정)

## 결정

- 키는 앱 코드가 공급한다: `createSealer({ key, models?: { [modelId]: { key } } })`. 기본은 전역 32바이트 키, 선택적으로 모델(테이블) 단위 키.
- 키는 설계 시 확정한 **고정 키**다. 키 버전, 키 교체(rotation), DB 정책·세대·canary 테이블, admin provisioning API가 없다. 암호문 머리는 1바이트 형식 번호뿐이다.
- 키를 바꾸려면 앱이 모든 데이터를 재암호화·재색인한다.
- 사용자·그룹 단위 키는 **그 키 범위 안에서만** 검색한다. 여러 키에 걸친 검색은 키 수만큼 토큰이 필요하므로 지원하지 않는다.
- 서버 수명 캐시는 고정 키에서 파생한 키만 둔다([003](003-field-cipher-key-cache-aad.md)).

## 근거

- 이전 설계는 호출마다 준비 단계에 **3.7–4.4 ms**를 썼다. 정책 SQL 2회, 정의 해시, canary 복호화 때문이다. 20행 페이지 전체 20–23 ms 중 준비가 약 4 ms였다 ([stages.json](../../bench/results/standard-review-2026-09-26/stages.json)의 `current.prepare`). 정책을 코드로 옮긴 뒤 준비는 0이다(같은 파일의 `improved*`).
- 이전 제품은 단건·0건 조회에도 정책 SQL을 포함해 SQL 3–5회를 썼다. 새 구조는 모든 케이스에서 페이지당 1회였다 ([10만 행 검증](../../bench/results/2026-09-27-standard-next/report-ko.md)).
- 버전·정책을 DB에 두는 것은 쓰이지 않는 운영 기능이었다(사용자 판단). 운영 데이터가 없어 이전 형식을 보존할 의무도 없다.

## 기각안

| 안 | 기각 이유 |
|---|---|
| DB 정책 테이블 + 세대 + canary + 온라인 회전 상태 기계 | 호출당 3.7–4.4 ms, 운영 복잡성. [011](011-rejected-research-lines.md) |
| 키 ID(이름, UUID)를 암호문 머리에 둠 | 검색 토큰은 조회 **전에** 키를 알아야 만들 수 있어 머리의 단서가 필터에 쓸모없다. 행의 키는 행의 평문 컬럼(팀, 사용자)으로 이미 정해진다. UUID 반복 저장은 낭비다 |
| 암호문 머리에 짧은 키 버전 + `activeVersion`/`readableVersions` 설정 | "버전 관리는 과잉"이라는 사용자 원칙을 좁게 해석한 오류였다. 폐기했다 |
| 여러 키에 걸친 검색 | 키 수만큼 토큰과 쿼리가 커진다(AWS "bounded fan-out"). 범위 설계로 해결한다 |
