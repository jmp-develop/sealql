# 012. Drizzle 통합: 보조 테이블 유지와 칸마다 옵션

- 상태: 확정 (2026-09-27, 사용자 결정). 구현 전. 상세는 [plan/001](../../plan/001-drizzle-native-api.md).
- 대체: [008](008-drizzle-integration.md)의 "부모 테이블의 Drizzle 미선언 토큰 칸 + BEFORE 트리거" 채택 부분과 `sealedTable` 선언 모양. 008의 연구·반증·실측 기록은 그대로 근거로 유지한다.

## 결정

1. **검색 목록(토큰)은 별도 보조 테이블(companion)에 둔다.** DB 트리거를 쓰지 않는다. 부모와 보조 테이블 쓰기는 SealQL 쓰기 함수(`sealed.insert/update/upsert`)가 한 트랜잭션으로 한다. 조회, 조건, JOIN, 관계형 조회, 삭제, 일반 칸 수정은 Drizzle 그대로다.
2. **스키마는 칸마다 옵션을 붙인다**(`name: sealed.text('name', { search })`). 테이블 단위로는 `sealed.register(table, { row, scope })` 한 줄만 쓰고, 그 반환값(보조 테이블 정의)을 export한다.

## 이유

- 부모 테이블 숨은 칸 안은 검색·쓰기가 빨랐지만(G0·X2: 검색 30–40%, 쓰기 16–44%), 트리거와 커스텀 마이그레이션이 필요하고 drizzle-kit `push`를 쓸 수 없었다. 사용자는 단순한 구조와 익숙한 운영(generate·migrate·push 모두 가능)을 택했다. 대가는 쓰기에 전용 함수를 쓰는 것이다.
- `sealedTable` 선언은 테이블 정보(행 식별 칸, 테넌트 칸) 두 가지 때문에 생긴 불필요한 개념이었다. 칸마다 옵션이 Drizzle 작성 습관에 맞고, 테이블 정보는 등록 한 줄로 충분하다.

## 교훈

설계 검증 에이전트의 제안(`sealedTable`, 부모 테이블 숨은 칸)을 사용자의 원래 요구와 대조하지 않고 채택했다가 되돌렸다. 계획은 확정 전에 사용자 요구 대조표(plan/001 §6)를 통과해야 한다.
