# 029 — 정규화 옵션 공개 이름과 필드 선택 주체

2026-10-02. 검색 정규화 옵션의 공개 이름을 동작이 드러나게 정하고, 암호화·검색·정규화·hardened 적용의 결정 주체를 문서에 명시한다.

## 정규화 옵션

- 기본 규칙(옵션 생략): NFC, 전각 ASCII → 반각, ASCII 소문자, 공백 제거. 값과 검색어에 같은 규칙을 적용하고 암호문은 원문을 그대로 보관한다. 내부 파생 이름 `legacy-text-v1`과 기본 필드의 SQL·파라미터는 1.2.0과 같다.
- `'digits'`(구 `phone-v1`): 기본 규칙에 더해 `-`·`(`·`)`·`.`·맨 앞 `+`를 무시하고 남은 문자가 숫자가 아니면 `INVALID_VALUE`. 전화 전용이 아니라 구분자가 섞인 번호 전반(유선·휴대·계좌·등록번호)에 쓴다. 국가별 자리 구분은 해석하지 않는다. 형식이 나라·회선마다 달라서이며, 숫자열 부분 검색으로 앞·중간·끝을 모두 찾는다.
- `'keep-spaces'`(구 `nfc-v1`): 정확 일치에서만 공백을 남긴다. 부분 검색은 compact 단일 스트림([019](019-compact-only-search.md))이라 공백을 계속 무시한다. 공백만 다른 값을 구분해야 하는 중복 확인용으로 유지한다.
- 공개 이름에 `-v1`을 두지 않는다. SealQL에는 프로필 버전 개념이 없다. 이름은 검색 키 파생에 들어가므로 규칙을 바꿀 때는 새 이름을 쓰고 변경 기록에 재색인을 명시한다. 이번 이름 변경으로 두 옵션의 파생값이 바뀌므로 그 옵션을 쓰던 칸은 재색인이 필요하다(사용처 없음).
- 구분자를 저장 전에 지우게 하는 안내나, 질의에서 구분자 위치를 나열하는 방식은 쓰지 않는다. 후자는 암호화 상태에서 쓰기 시점 정규화를 대체하지 못한다. 구분자 위치 조합이 늘고(8자리·구분자 최대 2개에 29개 패턴), `_`가 숫자도 맞춰 오탐이 생기며, 1글자 구간은 거부된다.

## 결정 주체

어떤 칼럼을 암호화할지, 어떤 검색을 켤지, `normalizer`와 `hardened`를 쓸지는 애플리케이션 소유자가 정한다. AI 도우미는 요청받은 칸에만 적용하고, 기준에 맞는 칸은 이유와 비용을 설명해 권하되 선택은 사용자에게 맡긴다. 사용 기준은 [`examples/README.md`](../../examples/README.md)의 한 곳(정규화 표, 필드 선택 표, Hardened fields)에 둔다.

검증: `test/normalizer-postgres.test.ts`가 일반·hardened 칸에서 두 옵션의 정확·포함·LIKE 결과를 독립 참조와 비교하고, 원문 보존과 숫자 외 문자 거부를 확인한다.
