# 007. 부분 검색 색인은 다중 컬럼 GIN, 통합 배열 기각

- 상태: 확정 (2026-09-27)

## 결정

- companion의 토큰 열은 필드·프로필별로 둔다. **부분 검색 토큰 열 전체를 덮는 다중 컬럼 GIN 하나**를 만든다(부분 검색 필드가 하나면 단일 열 GIN). 정확 일치 토큰은 열별 B-tree 식 색인을 유지한다. 부분 검색 열의 통계 목표 상향은 유지한다.
- 검색 필드를 추가하거나 제거하면 대체 GIN을 `CREATE INDEX CONCURRENTLY`로 **먼저** 만들고 옛 GIN을 지운 뒤 열을 추가·제거한다. 추가 필드는 전체 복호화로 토큰을 채운 뒤에 검색을 연다(그 전에 열면 누락이 생긴다).

## 근거 (10만 행, 공개 API, 교차 7회 중앙값, 전체 ms)

| 검색 | 기본 필드별 | 기본 다중 | 건너뜀 필드별 | 건너뜀 다중 |
|---|---:|---:|---:|---:|
| AND 4 | 30.04 | **15.83** | 64.25 | **17.91** |
| AND 6 | 23.46 | 17.16 | 24.70 | 17.44 |
| 단일 필드, OR, 빈도 스윕 9개 | 차이 없음 | | 차이 없음 | |
| memo update 중앙값 | 1.80 | 1.56 | 1.81 | 1.77 |
| insert 중앙값 | 4.92 | 5.85 | 7.79 | 7.70 |
| companion 총 크기 | 184.84 MB | 184.86 MB | 278.05 MB | 278.18 MB |

- 출처: [다중 컬럼 GIN 비교](../../bench/results/2026-09-27-multicolumn-gin/report-ko.md). 제품 DDL 적용 뒤 21개 케이스와 스윕이 평문과 일치했고 AND 4/6이 새 GIN을 썼다 ([제품 DDL 검증](../../bench/results/2026-09-27-product-multicolumn-gin/report-ko.md)).
- 비용: 필드를 추가·제거하면 색인 하나 전체를 다시 만든다. 10만 행 빈 열 기준 **1.5–2.7초**(기본 1,538 ms, 건너뜀 2,724 ms)였다. 실제 토큰 채우기와 잠금 비용은 포함하지 않는다.
- PostgreSQL은 색인에 포함된 열을 `DROP COLUMN`하면 그 색인도 지운다 [공식 문서]. 그래서 대체 색인을 먼저 만든다.
- 다중 컬럼 GIN 전후 10만 행 토큰 열 차이 0건. DB에 남는 논리적 토큰·행 관계는 같다 ([V2](../../bench/results/2026-09-27-core-verification/v2/report-ko.md)).

## 기각안: 통합 배열(모든 부분 검색 토큰을 한 배열 열 + GIN 하나)

통합 배열도 AND 4를 빠르게 했다(건너뜀 67.43 → 18.58 ms, [통합 GIN 실험](../../bench/results/2026-09-27-combined-gin/report-ko.md)). 그러나 이득은 여러 필드 부분 검색의 AND에 한정되고, 비용과 위험은 쓰기 경로 전체에 걸친다.

1. **부분 수정이 복잡하다.** 한 필드를 바꾸려면 다른 필드를 모두 복호화해 토큰을 다시 만들거나, 토큰 앞 32비트(필드 키와 scope로 만든 값)로 그 필드의 토큰을 골라내야 한다.
2. **골라내기는 검색 누락 위험이 있다.** 한 scope 안에서 서로 다른 두 필드의 앞 32비트가 우연히 같을 수 있다. 필드 6개 기준 scope당 약 **15/2³²**, scope 1억 개면 기대값 약 0.35건, 한 건 이상 생길 확률 **약 30%**다(계산값). 그런 scope에서 수정하면 다른 필드 토큰까지 지워져 **검색 누락**이 생긴다. 필드별 열에서는 무해하다. (10만 행 fixture에서 관측된 필드 간 prefix 중복은 0건이었다.)
3. 필드 제거·옵션 변경이 전체 행 배열의 재작성이 된다.
4. 필드별 토큰 수·통계 같은 운영 점검이 불투명하다.

다중 컬럼 GIN은 열을 그대로 두고 **색인만** 합쳐 같은 AND 이득을 얻는다.
