# 010. 보안 주장의 한계

- 상태: 확정 (2026-09-27)

## 결정

SealQL 문서·README·대외 설명은 아래 **허용 문장** 범위 안에서만 보안을 말한다. 위협별 누출과 운영 조치는 [위협 모델](../threat-model.md)에 있다.

허용 문장:

> SealQL은 선택한 필드를 앱이 가진 키로 AES-256-GCM 암호화하고, 행·필드·scope에 결속한다. 키가 없는 사람은 암호문을 복호화할 수 없고, 검색 토큰은 키 있는 HMAC이라 후보 값을 대입해 확인할 수 없다. 그러나 DB를 볼 수 있는 사람은 검색 토큰의 빈도와 동시출현, 값의 길이, 검색 결과 수와 시점을 볼 수 있으며, 이를 이용한 부분 복원 공격이 측정됐다. 키 없는 DB 탈취에서 완전한 레코드의 대량 복원이 어렵다는 것은 입증되지 않았다.

쓰지 않는 문장:

- "DB를 훔쳐도 복원이 어렵다", "안전하다", "N배 안전", 어떤 복원률 수치를 안전의 근거로 쓰는 것.
- "평문보다 빠르다"(C 로캘 평문 전체 스캔과의 비교에서 나온 배율).
- "개인정보 보호 법적 의무 준수". 「개인정보의 안전성 확보조치 기준」 제7조의 의무 암호화 대상은 고유식별정보, 비밀번호, 생체인식정보, 신용카드·계좌번호다. 이름·연락처·주소·메모의 암호화는 자발적 보호 조치다.
- 실험 결과를 보안 인증이나 운영 보장으로 표현하는 것.

## 근거

| 한계 | 수치와 출처 |
|---|---|
| **키 없는 탈취 저항은 미입증.** 블라인드 복원 0건은 공격자 사전 지식(prior)이 틀렸다는 뜻일 뿐 방어의 증거가 아니다 | 같은 관찰자·같은 1만 행에서 사전 없이 0건, 정답 사전을 주자 기본 색인의 메모 **8,594/10,000행**이 정밀도 1.0으로 복원 ([score-report.json](../../bench/results/confidentiality-diverse-100k/score-report.json) 대 [known-dictionary](../../bench/results/confidentiality-diverse-100k/score-report-known-dictionary.json), [snapshot-only](../../bench/results/confidentiality-diverse-100k/score-report-snapshot-only.json), [v2 평가](../../bench/results/reconstruction-blind/v2-evaluation-ko.md)) |
| **암호문 길이 = 평문 UTF-8 길이 + 머리** | 현재 형식 +29 B ([V2](../../bench/results/2026-09-27-core-verification/v2/report-ko.md)). 옛 형식(+33 B)에서 길이 + 고유값 목록만으로 16종 회사명 **69.875%** 복원, 여섯 필드 완전 레코드 0/100,000 ([길이 공격](../../bench/results/keyless-snapshot-length-attack-ko.md)) |
| **어휘가 적은 필드는 크게 샌다** | 최종 기본 조각, 5% 원문 + 일관성 공격에서 모르는 행 80%+ 해독: 합성 메모(어휘 적음) **19.33%**, 실제 리뷰 **0.43%** ([V2](../../bench/results/2026-09-27-core-verification/v2/report-ko.md)). 어휘가 적은 필드는 부분 검색을 권하지 않는다 |
| **짧은·형식 있는 필드는 길이와 동치류가 드러난다** | 전화·이메일·이름 각 2만 행에서 암호문 길이 종류 1/7/3, 16비트 정확 토큰 충돌 묶음 약 2,500개. 알려진 행 전파 복원은 0행이었지만 형식·길이가 안전하다는 증명이 아니다 (같은 보고서) |
| **WAL·다중 스냅샷은 시험하지 않았다** | 두 시점 스냅샷이나 WAL은 갱신된 행과 토큰을 연결한다. 어떤 실험도 이 채널을 재지 않았다 |
| **적대적 DB는 결과를 누락할 수 있다** | companion 토큰을 NULL로 바꾸자 해당 행이 오류 없이 검색에서 빠졌다. 라이브러리는 탐지하지 못한다(설계상 한계). 변조된 암호문은 `AUTHENTICATION_FAILED` ([V1](../../bench/results/2026-09-27-core-verification/v1/report-ko.md)) |
| 조각 토큰의 기계적 공격 하한 | 제품 토큰 10만 행, 5% 원문: 인접만 3.64%, 기본 구성 0.03% ([scale-ko.md](../../bench/results/2026-09-27-layout-attack/scale-ko.md), [004](004-token-layout-16bit.md), [005](005-skip-grams-default-on.md)) |

- 사용한 공격(빈도 순위, 알려진 원문 행집합 대조, 제한된 일관성 전파, 알려진 행의 정확 토큰 전파, 형식 후보 열거)은 누출의 **하한**이다. 쓰지 않은 공격: 강한 동시출현·문자열 전체 복원, 쿼리 관찰, 다중 스냅샷·WAL 추적, 키 탈취, 물리 GIN 페이지 분석.
- 합성 fixture는 템플릿 반복이 많아 자연어 결과와 다르다. 두 방향 모두로 틀릴 수 있다(위 19.33% 대 0.43%).

## 기각안

| 안 | 기각 이유 |
|---|---|
| "키 없이 DB 파일을 훔쳐도 완전 레코드 대량 복원이 어렵다"는 고객 진술 | 위 근거로 뒷받침되지 않는다 |
| 블라인드 복원 0건을 안전 근거로 인용 | prior 포괄률 실패일 뿐이다 |
| AI에게 "뚫어 보라"고 맡긴 결과를 보안 판단으로 사용 | 재현 불가. 기계적 공격 시뮬레이션만 쓴다([attack-simulation.md](../attack-simulation.md)) |
