# 022 — 일반 LIKE를 고정 길이 구간 순서로 판정

2026-09-29.

## 결정

일반 LIKE는 `%` 사이를 고정 길이 구간으로 나눈다. literal의 도장 창을 구간 offset에 배치하고 `_`는 폭 1을 더한다. 왼쪽부터 앞 구간 끝 이후의 가장 이른 성립 위치를 찾는다. 앞에 `%`가 없으면 시작 위치를 고정하고, 뒤에 `%`가 없으면 마지막 구간 끝을 정규화 길이에 고정한다. 고정 길이 구간의 가장 이른 일치는 뒤 구간이 사용할 수 있는 위치를 줄이지 않으므로 별도 되돌아가기가 필요 없다. 겹치는 literal 구간은 앞 구간이 소비한 위치를 재사용하지 않는다.

위치 탐색은 기존 contains/affix와 같은 전진 커서·이진 탐색 알고리즘에서 SQL 본문을 생성한다. 일반 위치 Boolean 판정에 추가 함수 호출을 넣지 않고, LIKE용 함수는 제한된 시작 위치 범위에서 첫 성립 위치를 반환한다. 모든 조각의 등장 위치 목록과 길이별 frontier를 먼저 만드는 작업 및 그 전용 helper는 제거한다. 조각별 등장 순번 탐색은 정규화 길이로 제한하고 첫 후보 실패 뒤에만 커서 배열을 만든다.

저장된 암호문·후보 토큰·salt·도장·compact 위치·질의 파생 키는 바꾸지 않는다. `extraMigrationSql`을 다시 적용해야 하며 compact-only 데이터의 재색인은 필요 없다. SET search_path, MAIN, 위치 판정 COST1900은 유지한다.

## 근거

단일 literal 정규화 뒤에도 일반 LIKE `%te%st`와 `%te__`의 이메일 10만 건 count는 [021 측정](../../bench/results/2026-09-29-final-impl/next-candidates-check.json)에서 각각 1,578.55ms와 1,179.03ms였다. 모든 조각의 모든 등장과 없는 다음 순번까지 확인하는 작업은 첫 구간이 성립한 뒤 다음 구간으로 넘어가면 불필요하다.

`test/like-segments.test.ts`는 겹치는 `%aba%ba%`, `_`/`%` 조합, 이스케이프, 유니코드, 반복 값, 4,002자, 빈 값과 NULL을 PostgreSQL LIKE와 직접 대조해 3,836건이 일치했다. 입력은 임시 질의 인자뿐이며 생성한 레코드를 적재하지 않는다.

[같은 연결의 전후 비교](../../bench/results/2026-09-29-final-impl/like-segments-check.json)는 예열 2회·교차 7회 중앙값이다. `%te%st` count는 1,584.80→654.89ms, 목록300은 18.19→9.64ms였다. `%te__` count는 1,196.11→424.79ms, 목록은 13.79→7.19ms였다. 단일 literal `%est` count는 351.43→352.43ms로 1ms 미만 차이였으며 모든 count·ID순 투영이 평문과 일치했다. 10만 건의 이 세 패턴만 측정했으며 모든 일반 LIKE 패턴에 같은 속도를 보장하지 않는다.

## 기각안

행별 첫 등장 SQL SubPlan 후보 A와 TOAST 목표값 후보 B는 021의 판단을 유지한다. 창 수·특정 연산자·특정 문자열에 대한 성능 분기는 추가하지 않는다. 임시 중단된 시간 측정은 채택 근거로 쓰지 않는다.

017의 일반 LIKE 위치 목록·frontier 선행 계산을 대체한다. 021의 단일 literal 정규화와 020의 일반 위치 판정·후보 계획은 유지한다. 로컬 fixture 결과이며 운영 성능 보장이나 보안 인증이 아니다.
