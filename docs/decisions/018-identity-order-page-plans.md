# 018 — ID 정렬 표현과 무관한 페이지 계획

상태: 채택, 2026-09-29. [017](017-search-proof-review.md)의 ID 정렬 뒤 proof 조회를 유지하고 페이지 경로 선택을 보완한다.

## 결정

`orderBy` 생략과 단일 `id asc` 명시는 SQL 문자열까지 같은 ID순 후보 계획을 사용한다. 연산자·필드·검색어에 따른 특례를 두지 않는다. 다른 정렬, 별도 부모 WHERE, 비암호 SQL 혼합에 기존 일반 경로를 적용하는 안전 조건은 유지한다. SQL용 정렬만 정규화하고 커서의 기존 정렬 결속과 형식은 보존한다. 이전 제품이 만든 명시적 ID 커서의 다음 페이지도 평문과 대조했다.

한 SQL 안에서 ID prefix → quick → fallback을 실행한다. prefix 크기는 요청한 최종 행 수의 4배, 최소256이며 내부 실행 상수다. prefix에 최종 predicate를 적용한 quick 결과가 limit개면 끝내고, 부족하면 전체 후보를 ID순으로 정렬한 뒤 proof를 읽는 fallback을 실행한다. 최상위 OR은 기존 전체 후보 경로를 유지한다. 두 경로 모두 판정 뒤 LIMIT을 적용한다. prefix 크기는 결과·작업 상한이 아니며, 요청을 바꾸거나 일부 결과를 반환하지 않는다. 서버 수명 데이터 캐시, 행 수 추정 조회, 추가 SQL 왕복은 없다.

## 근거

독립 적재한 원문 10만 행의 `email endsWith "biz.test"`에서 명시적 ID 정렬은 기존 조기 종료 경로에서 빠졌다. EXPLAIN은 proof 통과26,598행과 부모 조회26,598회 뒤 top-N 정렬을 보였다. 기본 정렬은 후보 ID 정렬 뒤 proof·부모 조회가300회에서 멈췄다.

기존 bounded를 명시적 ID 정렬 전체에 바로 적용하면 메모가 느려졌다. 원래 Merge Join은 부모746개에서 종료했지만, bounded는 후보40,097개의 ID를 모두 읽어 정렬했다. 45자 0건 질의도 기존 Bitmap Heap에서 바로 탈락하던2,440행을 정렬하고2,440번 재조회했다. 일반 prefix는 흔한 일치에서 전체 후보 정렬을 피하고, 모자랄 때만 fallback 비용을 지불한다.

[전후 측정·계획·게이트](../../bench/results/2026-09-29-r9-email-limit/report-ko.md)에 대표8조건, 두 email suffix, 45자와 푸른달을 같은 세션에서 예열2회·교차7회 비교한 수치를 보존한다. 모든 count·ID·선택값은 원문 fixture의 독립 정규화 oracle과 대조한다. 명시적 ID 정렬과 기본 정렬도 같은 세션에서 비교한다. 희박하거나0건인 조건의 추가 prefix/재조회 비용은 수치로 공개한다.

`biz.test` 목록300 SQL은 679.27→14.92ms, 전체 API는 745.46→77.35ms였다. 메모 SQL은 37.86→8.56ms로 줄었고, 푸른달은 3.22→6.36ms, 45자 0건은 22.60→38.32ms로 늘었다. 현재 제품의 두 정렬 표현만 교차한 별도 측정에서 `biz.test`는 명시11.44ms·기본11.54ms였다. count SQL은 전후 동일하다. 최악 사례 제거를 우선하고 남은 악화를 공개한다는 채택 기준을 적용했다.

## 기각안

- 명시 ID 정렬에 기존 bounded를 그대로 확대: 최악 suffix는 줄지만 메모 전체 후보 정렬을 유발한다.
- 단일 suffix에만 별도 계획 적용: 같은 정렬의 의미를 연산자 특례로 나누므로 기각했다.
- 필드명·검색어별 조건, 지속적인 후보 수 캐시, 데이터 변경이나 물리 재정렬은 사용하지 않는다.

## 대체 관계

[015](015-database-search-proofs.md)·017의 판정·저장·키·누출 경계는 그대로다. 200행 이하만256개 prefix를 확인하던 선택을 요청 크기에 따른 일반 quick/fallback으로 대체한다. 실제 서비스 성능 보장이나 보안 인증은 아니다.
