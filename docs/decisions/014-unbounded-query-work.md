# 014. 호출자 선택 예산과 단일 후보 흐름

- 상태: 확정 (2026-09-28)

## 결정

- `쿼리 작성에 제품 고정 limit·작업량·시간·바이트 상한을 두지 않는다.` limit을 생략한 findMany/search는 일치하는 모든 행을 반환한다. 예산을 전달한 호출에서만 초과를 검사한다. count는 후보를 한 SQL 요청으로 가져와 인증 재확인하며 정확한 number를 반환한다. 호출자 예산으로 증명이 중단되면 LIMIT_EXCEEDED다.
- 제한된 페이지의 첫 후보 묶음이 부족하면 관측 통과율과 남은 필요 행 수에 따라 다음 묶음을 키운다. 묶음 크기에 제품 최대값은 없지만, 매 요청에 유한한 SQL `LIMIT`을 둔다. limit을 생략한 조회와 count만 후보를 한 SQL 요청으로 가져온다. 조건 필드 인증 후 반환 필드를 연다.
- 커서는 scope, match, where, 정렬 위치에 결속한다. limit과 반환 열은 위치를 바꾸지 않아 결속하지 않는다. 날짜·시각 정렬값은 DB의 DateStyle과 무관한 JSON 텍스트로 저장한다. 기존 정렬 커서는 무효다. 커서 유효 시간과 크기 상한은 없다. AES-GCM 봉인·인증은 유지한다.
- 평문 열의 다중·nullable 정렬과 검색 keyset을 허용한다. 행 ID는 마지막 동률 해소 열이다. 암호 열 정렬은 계속 금지한다.
- open/openRaw와 쓰기 returning의 암묵적인 행·바이트·시간 예산을 없앤다. 큰 insert 배열은 전체 테이블 칸 수로 PostgreSQL 매개변수 한도를 보수적으로 계산하여 같은 트랜잭션 안에서 분할한다. reindex는 기본 1,000행씩 처리하며 호출자가 batch를 바꿀 수 있고 최대값은 없다.
- 필드 값, 검색어, ID, 모델·필드 이름의 제품 고정 길이 상한을 없앤다. NUL 금지, 필드 ID의 슬래시 금지, 최소 2글자 부분 검색 등 정확성·보안 조건은 유지한다. 정확 토큰 최소 8비트와 정수 기본 키 미지원도 사용자 지시에 따라 그대로 둔다.

## 근거

- 고정 예산은 사용자 쿼리 작성에 제약을 주며 보안 근거로 정해진 값이 아니다. 기존 구현은 count의 고정 묶음마다 후보 semi-join을 다시 실행했다.
- 바이트·시간 기본 예산 때문에 정상 질의가 실패하고, 쓰기 returning의 커밋 뒤 복호화 제한은 성공한 쓰기를 실패로 보이게 했다. 검색 필드의 문자 제한과 필드 바이트 제한도 서로 충돌했다.
- 구현 당시의 SQL 계획·시간 비교는 로컬 R8 체크리스트에 기록한다. 측정하지 않은 환경의 성능은 추정하지 않는다.

## 기각안

| 안 | 이유 |
|---|---|
| 제품 고정 기본 예산·최대값 유지 | 호출자의 정상 데이터와 쿼리 규모를 라이브러리가 임의로 제한 |
| count 후보를 고정 페이지로 반복 | 같은 보조 테이블 후보 계산을 반복 |
| 커서를 limit·투영·만료 시간에 결속 | 페이지 크기·반환 열 변경과 느린 재개를 막음 |
| companion 내부 LIMIT | [006](006-query-engine.md)의 조밀한 조건 SQL 회귀 관측 때문에 채택하지 않음 |
| 정수 PK용 AAD 타입 태그, 정확 토큰 최소 비트 변경 | 이번 범위에서 보안 코어 변경을 금지한 사용자 지시 |
