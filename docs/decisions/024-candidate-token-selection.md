# 024 — 후보 조건에 정렬 토큰 최대 세 개 사용

2026-09-30. 공개 API·저장 형식·정확 판정은 유지하고 후보 SQL 생성만 바꾼다.

## 결정

부분 검색의 `@>`에는 토큰값으로 정렬된 기존 배열의 앞·중간·끝만 보낸다. 길이 N이 3보다 클 때 인덱스는 `0`, `floor((N-1)/2)`, `N-1`이며, 3개 이하는 그대로다. 문자 위치가 아닌 토큰값 순서다. `candidate-sql.ts`의 공통 토큰 조건 한 곳에서 적용하여 count, 유한 목록의 quick/fallback, 무제한 목록, LIKE, 중첩 AND/OR와 JOIN이 같은 규칙을 쓴다. exact는 바꾸지 않는다.

세 개는 상관된 조각 선택도를 독립적으로 곱하는 플래너의 과소추정을 줄이기 위한 선별 조건 원소 수다. 후보·결과·작업량 상한이 아니다. 전체 조각의 부분집합이므로 실제 일치를 후보에서 누락하지 않으며, 도장 키·offset·길이·LIKE 프로그램을 그대로 전달하여 기존 도장 함수가 최종 판정한다. 후보는 늘 수 있다. 기존 예산과 커서·scope 결속은 유지한다.

암호문, 저장 토큰·도장, 쓰기·부분 수정·삭제·동시성 처리는 바꾸지 않는다. 이 변경 자체에는 마이그레이션, `extraMigrationSql` 재적용, reindex 또는 재암호화가 필요 없다. 사용자 API도 그대로다.

## 근거

기존 fixture 10만 행, 같은 연결의 예열 2회·균형 교차 7회 중앙값, 57조건의 count/목록300 총 114경우다. [원 측정과 보고](../../bench/results/2026-09-29-lasthour/r9-impl/report-ko.md)는 평문과 P0–P4의 정답 대조 6,840회를 기록한다. 다음 값은 P1 벤치 변형의 SQL 시간이며, 배포 환경의 성능 보장이 아니다.

| 지표 | 기존 P0 | 채택 P1 |
|---|---:|---:|
| 전체 SQL 평균 | 66.15ms | 55.43ms |
| count 평균 | 115.38ms | 93.71ms |
| 목록 평균 | 16.92ms | 17.14ms |
| 이메일 biz.test 끝 count | 447.95ms | 162.90ms |
| 서비스상담 count | 491.48ms | 204.47ms |
| 가장 큰 절대 증가: LIKE %est count | 238.09ms | 249.56ms |

이메일 조건의 후보 추정은 82→26,840, 실제 후보는 26,598→26,840(+0.91%)으로 바뀌어 병렬 계획을 선택했다. 서비스상담도 후보 29,843을 유지하면서 추정 51→3,571로 개선됐다. 드문 이메일 iae의 후보는 6→29지만 SQL count 증가는 약 0.25ms였다. 다른 자연어 분포·키·운영 데이터의 후보 증가는 미검증이다. 모든 조건의 무퇴행을 주장하지 않는다.

[기계적 관찰 공격](../../bench/results/2026-09-29-lasthour/m1-astra/report-ko.md)에서 후보 토큰 전송은 4,419→2,446(-44.65%)이지만 값 복원율은 줄지 않았다. 도장 키·위치 채널이 그대로이므로 보안 개선으로 주장하지 않는다. DB에 새 정보나 저장물을 추가하지 않으며 기존 T4 누출·악성 DB의 누락/위조 한계는 유지한다.

구현 게이트는 `npm run build`, `npm run check`, `npm test`(40/40), `npm run docs:check`, `npm run test:install`을 통과했다. [SQL 인자 시험](../../test/candidate-sql.test.ts)은 선택 규칙·전체 도장 인자 보존을, [DB 시험](../../test/standard-r9.test.ts)은 긴 검색·긴 0건 복합·다구간 LIKE·중첩 AND/OR·keyset·두 scope·JOIN과 실제 전송 토큰 수를 검증한다. 기존 4,002자 근접 불일치와 Node pg·postgres-js·workerd pg 흐름도 통과했다. 설치 시험은 기존 정책대로 Drizzle 자체 선언 진단 70개를 제외하고 SealQL과 소비자 선언을 검사했다.

## 기각안

P2(나머지 토큰을 별도 함수로 확인)는 함수와 전송물을 늘리며 목록 평균이 19.90ms로 나빠졌다. P3/P4의 테이블 병렬 worker 설정은 일부 목록에서 병렬 시작 비용을 늘렸다. 추가 함수·연산자 특례·별도 경로·저장 형식 변경은 채택하지 않는다.

## 대체 관계
